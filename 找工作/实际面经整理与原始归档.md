## 一、基于当前简历的复习导航

### 1. FastDFS 云存储项目主线

- 项目定位：Linux 环境下使用 C++ 开发的网盘式云存储服务，支持注册登录、普通上传下载、秒传、大文件分片与断点续传、删除、分享、转存和取消分享。
- 服务链路：Nginx 统一接入 HTTP 请求并按 `location` 路由；普通动态 API 通过 FastCGI 进入 C++ 业务进程，上传模块先把正文保存到临时目录，下载由 FastDFS 相关 Nginx 模块返回。
- 数据分工：FastDFS 保存文件正文；MySQL 持久化用户、文件实体、用户关系、普通分享、图片分享与计数；Redis 保存登录 Token、真实上传的短期 MD5 校验值以及共享文件 ZSet/Hash；Storage 进程内的 LRU-K 缓存负责热点文件下载加速。

## 四、项目基本功能统一回答口径

### 1. 两分钟项目介绍

> 这是一个运行在 Linux 上、使用 C++ 开发的网盘和图床后台。Nginx 是统一 HTTP 入口，通过 `location` 完成路由和动静分离；普通动态 API 通过 FastCGI 交给常驻 C++ 业务进程，上传先落到临时目录，下载由 FastDFS 相关 Nginx 模块返回。FastDFS 保存文件正文，MySQL 保存用户、文件实体、用户拥有关系、普通分享和图片分享记录，Redis 保存登录 Token、共享文件排行及辅助缓存。项目实现了注册登录、普通上传下载、MD5 秒传、大文件分片与断点续传、删除、分享、转存、取消分享和图片外链浏览；Storage 下载侧还增加了 LRU-K 热点文件缓存。负载均衡部分来自论文，我完成的是学习性复现和逻辑验证，不把它表述为原创算法或个人真实性能结论。

### 2. Nginx 与 FastCGI

- Nginx Master 负责读取配置、管理 Worker、重载和异常拉起；Worker 使用事件驱动模型处理连接。
- 配置按 `main → events → http → server → location` 理解，`server_name` 选择虚拟主机，`location` 根据 URI 选择静态响应、FastCGI 或上传/下载模块。
- 客户端与 Nginx 之间是 HTTP；Nginx 把动态请求的参数和请求体编码成 FastCGI 记录交给常驻 C++ 进程，业务处理完成后再由 Nginx 返回 HTTP 响应。
- FastCGI 的主要价值是标准化 Web 服务器与常驻业务进程之间的接口，并避免传统 CGI 每个请求创建进程；不能说成“压缩 HTTP 后直接交给 FastDFS”。
- `proxy_pass` 面向 HTTP 上游，`fastcgi_pass` 面向 FastCGI 上游。是否使用轮询、权重或最少连接等 Nginx 负载算法必须按真实 `upstream` 配置回答。

### 3. MySQL 数据模型

- `user_info`：账号、昵称、联系方式、密码摘要和创建时间；用户名唯一。
- `file_info`：物理文件 MD5、FastDFS `file_id`、下载 URL、大小、类型和引用计数。
- `user_file_list`：用户、文件 MD5、文件名、分享状态、下载量和创建时间，表达“用户拥有文件”。
- `user_file_count`：保存每个用户的文件总数，项目还使用特殊标识保存共享文件总数；它是冗余计数，需要能从明细重算。
- `share_file_list`：普通文件分享者、MD5、文件名、下载量和分享时间。
- `share_picture_list`：图片分享者、原文件 MD5、文件名、`urlmd5` 不透明分享标识、提取码、浏览量和分享时间。
- 当前教学实现把密码保存为 MD5 后的值；面试时应主动说明无盐 MD5 不适合生产密码存储，改进应使用 Argon2、bcrypt 或 scrypt 加随机盐。

### 4. Redis Token 与业务缓存

- 登录成功后以用户名作为 Key、Token 作为 Value 写入 Redis，资料给出的 TTL 为 24 小时；该 Token 是服务端状态型不透明字符串，不是 JWT。
- 资料描述用户每次通过 Token 校验后延长 TTL，属于滑动过期。它实现简单，但会增加 Redis 写操作，被盗 Token 也可能被持续续期。
- 更合理的后续方案是短期 Access Token 加可撤销、可轮换的 Refresh Token，并使用密码学安全随机数生成 Token。
- Redis 还用 `SETEX` 暂存真实上传前的预期 MD5，用 ZSet 保存共享排行、Hash 保存共享文件展示字段；MySQL 是分享关系事实源，缓存异常时从 MySQL 重建。
- Storage 的 LRU-K 缓存保存热点文件内容，与 Redis Token 和业务索引不是同一层。

### 5. 普通上传与秒传

- 客户端上传前计算文件 MD5，服务端先查 `file_info`，再查 `user_file_list`。
- 当前用户已经拥有文件时直接返回；物理文件存在但用户未拥有时，新增用户文件关系，并增加文件引用计数和用户文件数量，不传正文。
- 物理文件不存在时，用 Redis `SETEX` 短期保存“用户名和文件名对应的预期 MD5”，随后执行真实上传。
- 上传请求经 Nginx 和 FastCGI 进入 C++ 业务进程；教学代码版本通过 `fork/exec` 调用 `fdfs_upload_file`，由这个 FastDFS 客户端工具向 Tracker 查询可用 Storage、完成上传并返回 `file_id`。
- 上传后重新计算接收文件的 MD5，与 Redis 中的预期值比较；校验通过后更新文件信息、用户文件关系和计数。
- 该 MD5 比对主要检查传输前后内容是否变化，不等于彻底解决 MD5 碰撞。进一步改进可结合文件大小和 SHA-256。

### 6. 大文件分片与断点续传

- 当前项目以 10 MB 作为进入分片上传的阈值。
- 初始化时发送文件大小、文件名、分片总数和文件 MD5，服务端建立分片记录，并创建以文件 MD5 标识的临时目录。
- 每个固定大小分片携带文件 MD5 和分片索引；服务端按索引保存，分片记录可用于发现缺片和继续补传。
- 最后一片上传后由客户端请求合并；服务端先检查索引集合、分片数量和总大小，再按索引顺序调用 FastDFS 追加上传接口。
- 合并完成后删除临时分片和分片记录并更新最终文件信息。当前实现使用 MD5 作为会话目录且缺少严格合并状态机，是可以继续改进的并发边界。

### 7. 分享、取消分享、转存与删除

- 分享状态优先从 Redis ZSet 查询，缓存未命中时回查 MySQL；数据库已有记录则回填 Redis，数据库也没有时才创建分享。
- 创建分享会更新 `user_file_list` 的分享状态，插入 `share_file_list`，增加共享文件数量，并写入 Redis ZSet 与 Hash。
- 取消分享会恢复用户文件的非分享状态、减少共享数量，并删除 MySQL 分享记录及 Redis 的 ZSet、Hash 记录，不删除用户拥有关系。
- 转存先检查目标用户是否已拥有相同 MD5 和文件名；未拥有时新增用户文件关系，增加物理文件引用计数和目标用户文件数量，不重复上传正文。
- 删除会先清理分享状态，再删除当前用户关系并减少引用计数；只有引用计数归零时才删除 `file_info` 和 FastDFS 物理文件。
- 图片分享使用 `share_picture_list` 保存 `urlmd5` 不透明标识和提取码；访问页面根据 `urlmd5` 查询真实下载 URL。普通列表仍可能直接返回完整 URL，不能声称已经全面隐藏 Storage 地址。
- 图片分享中的 `pv` 是浏览统计，不是最大访问次数；现有资料也未证明已经实现分享过期或限次下载。

### 8. Storage 侧 LRU-K 缓存

- Storage 响应下载前先查询进程内内存缓存，未命中再从磁盘读取。
- 文件第一次访问进入历史队列，访问次数达到 K 后才晋升到正式缓存，避免一次性冷文件污染缓存。
- 缓存命中后更新访问时间并调整顺序；空间不足时淘汰第 K 次历史访问距离当前最久的数据。
- 该缓存保存热点文件内容；Redis 保存 Token、共享排行和业务缓存，二者不能混为一谈。

### 11. 并发上传同一文件的解决方法

- 单纯“先查 MD5、未命中再上传”存在检查与写入之间的竞态，两个用户可能同时完成真实上传。
- 为内容摘要和文件大小建立唯一约束，并创建带 `UPLOADING/READY/FAILED` 状态、所有者、更新时间和租约的上传占位记录。
- 两个请求通过条件插入原子争夺上传权；成功者上传，失败者等待或轮询，文件就绪后再建立各自的用户文件关系。
- 用户文件关系设置唯一约束，只有关系首次插入成功时才增加引用计数和用户文件数量。
- 如果重复正文已经落到 FastDFS，唯一键冲突的一方改为引用已经发布的文件，并把自己上传的 `file_id` 交给可重试清理任务，避免孤儿文件。
- 同一用户从两台设备上传也使用相同幂等逻辑，不需要通过 WebSocket 强制踢掉旧设备。单设备登录策略与上传幂等是两个不同问题。

### 12. 分片上传的线程模型

- 项目设计上由多个客户端工作线程并发发送不同分片；单个分片内部仍顺序读取和上传，主要收益来自网络传输重叠。
- 切分阶段不要让多个线程共享会变化的文件游标；可以由单线程读取后分发缓冲区，或由工作线程使用 `pread` 按固定偏移读取。
- 分片数不等于线程数。即使有 1000 个分片，也使用固定大小线程池和有限并发窗口，一个完成后再补充一个。
- 服务端以分片索引保证最终顺序，并限制单用户并发、全局并发和临时空间。
- 没有真实对照压测时，只能说明使用多线程的原因，不能声称具体提升倍数。

### 13. 为什么选择 FastDFS

- 项目需要面向文件对象的上传、下载、去重与扩容，不需要完整 POSIX 文件系统语义。
- FastDFS 的 Tracker 负责调度，文件正文由 Client 与 Storage 直传；不同 Group 扩展容量，同组 Storage 提供副本，适合当前 Linux C/C++ 项目范围。
- FastDFS 核心主要使用 C 实现，不能说成“因为它是 C++ 框架所以选择”。
- TFS 更偏大规模小文件场景，MooseFS 提供更接近 POSIX 的文件系统语义，MogileFS 的元数据与技术生态也不同；这里只能说明需求匹配，不宣称 FastDFS 全面优于其他框架。
- FastDFS 的局限包括生态较旧、缺少完整 POSIX 语义，以及同组异步同步带来的短暂不一致窗口。

## 五、负载均衡算法专项面经回答归档

### 1. 主问题：FastDFS 默认策略有什么局限？你做了什么？

**面试回答：**

FastDFS 原有策略主要包括轮询、选择剩余空间较大的组以及指定服务器等。轮询能够大致均衡请求数量，但不同文件的大小和请求成本不同；只看剩余空间也不能反映节点当前的 CPU、内存、磁盘 I/O 和网络压力。

这部分算法不是我原创的。我通过查阅《基于 FastDFS 的云存储文件系统性能优化设计与实现》，在本地学习环境中复现了论文提出的动态反馈负载均衡算法。它先根据 CPU、内存、磁盘和网络的当前使用率计算节点负载，负载值越小表示越空闲；再根据 CPU 数量与频率、内存容量、磁盘容量和网络吞吐能力计算处理能力。Storage 通过心跳向 Tracker 上报状态，Tracker 先在每个 Group 内选择负载较低的节点形成预评价队列，再通过负载阈值筛选候选集，最后按照处理能力进行带权随机选择。

我完成的是节点状态结构、两类评分、候选节点筛选和概率选择的学习性复现，并用构造数据验证选择方向是否符合预期。目前没有把它表述为我原创的算法、已经合入 FastDFS 官方源码或完成了生产级压测。

### 2. 追问：当前负载与处理能力分别怎样计算？

**面试回答：**

当前负载综合 CPU 使用率、内存使用率、磁盘使用率和网络带宽使用率，可表示为：

`L(Si)=r1L(Ci)+r2L(Mi)+r3L(Di)+r4L(Ni)`

各权重之和为 1，结果越小表示节点越空闲。处理能力综合 CPU 数量与频率、内存容量、磁盘容量和网络吞吐能力，可表示为：

`C(Si)=k1·n·C(Ci)+k2C(Mi)+k3C(Di)+k4C(Ni)`

各权重之和也为 1，结果越大表示机器的基础处理能力越强。前者描述节点现在有多忙，后者描述机器大致能承担多少工作。旧口径中的“磁盘使用率加任务使用率”不符合这篇论文，应停止使用。

### 3. 追问：Tracker 具体如何选择 Storage？

**面试回答：**

Tracker 根据 Storage 心跳信息计算各节点负载，并在每个 Group 内按负载排序，论文实现取负载最低的两个节点进入预评价队列。然后找到最低负载节点 `Sm`，把满足 `L(Si) < L(Sm) + f` 的节点放入最终候选集，其中 `f` 是允许的负载差阈值。最后按照 `P(Sk)=C(Sk)/ΣC(Si)` 计算候选节点的选择概率并进行带权选择。

这样没有把所有请求都压到瞬间负载最低的同一台机器上，同时又能让处理能力较强的低负载节点承担更多请求。对于下载请求，还必须先根据 `file_id` 确定文件所属 Group，只能在该组中已经同步且可读的副本之间选择，不能跨 Group 调度。

### 4. 追问：你怎样验证复现正确？有真实性能数据吗？

**面试回答：**

我目前完成的是逻辑验证：构造多组节点状态，提高某个节点的资源使用率后，它的综合负载应升高、被选择概率应下降；当候选节点负载接近时，提高某个节点的处理能力后，它的选择概率应上升；条件相同的节点经过多次选择后，结果应大致均匀。这能验证复现的计算和选择方向，但不能代替真实系统压测。

论文在 VMware 中使用一台 Client、一台 Tracker 和四台 Storage，四台 Storage 分成三个 Group，使用不同线程数下载 50 MB 文件并与轮询策略比较平均响应时间。论文结论是低并发时动态计算存在额外开销，优势不明显；并发提高后更有利于减少负载不均并降低平均响应时间。这是论文的实验结论，不是我的个人实测。此前“实测提升约 30%”没有真实数据依据，面试中不再使用。

### 5. 高频诚信追问

- **这是你自己提出的算法吗？** 不是。我通过查阅论文理解并复现了他人提出的算法，个人工作是编码还原选择流程和进行逻辑验证。
