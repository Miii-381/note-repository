## 四、项目基本功能统一回答口径

### 1. 两分钟项目介绍

> 这是一个运行在 Linux 上的学习型云存储系统，使用 Docker Compose 做单机三容器部署。React 前端通过 Nginx 访问静态资源和 API，传统业务后端由多个常驻 C FastCGI 模块组成。FastDFS 保存文件正文，MySQL 用 6 张主链路表保存用户、物理文件、用户目录项和分享关系，Redis 保存用户名到 Token、分片会话以及公共分享排行。项目实现了注册登录、基于 MD5 的秒传、普通上传、10 MiB 分片与 FastDFS appender 合并、文件列表、分享、取消分享、转存、下载计数和引用计数删除。当前部署只有一个 Tracker 和一个 Storage，不是高可用集群。代码复核还暴露了普通上传和分片上传鉴权不足、服务端未复算摘要、多表更新无事务、分片合并无状态机等边界。LRU-K 和动态负载均衡在当前仓库没有实现，所以不作为项目成果。

### 2. Nginx 与 FastCGI

- Nginx 配置为 2 个 worker，负责 HTTP 到 HTTPS 跳转、TLS、React 静态资源、API 路由和 FastDFS 文件响应。
- 13 条 API 路由分别 `fastcgi_pass` 到 `10000`～`10012`；当前没有 `upstream`，所以没有应用层负载均衡。
- 传统业务模块是常驻 C FastCGI 程序，使用 `FCGI_Accept()` 循环处理请求；启动脚本每个模块只起一个实例。
- FastCGI 避免传统 CGI 每请求创建进程，但不等于项目自动拥有线程池、多实例或无状态高可用。

### 3. MySQL 数据模型

- 主回答说 6 张传统业务表：`user_info`、`file_info`、`user_file_list`、`user_file_count`、`share_file_list`、`share_picture_list`。
- `file_info` 表示物理正文，`user_file_list` 表示用户目录项；拆开后才能支持秒传、转存和引用计数。
- `user_file_count` 和公共分享总数是冗余计数，理论上应能从明细表重建。
- 当前回答只展开 6 张传统云存储主链路表；后续迭代数据不纳入本轮口径。
- 当前没有外键、关键关系的完整唯一约束和多表事务，是并发一致性缺口。

### 4. Redis Token 与缓存

- 登录写入 `用户名 -> Token`，TTL 固定 86400 秒；校验只读不续期。
- Token 是服务端状态型不透明字符串，不是 JWT；同用户再次登录会覆盖旧值。
- Redis 还保存分片会话 Hash、公共分享 ZSet 与文件名 Hash。
- 普通上传没有 Redis “预期 MD5”；不要把分片 Hash 与秒传链路混为一谈。
- 分享缓存可从 MySQL 重建；登录 Token 没有 MySQL 等价副本，Redis 丢失就需要重新登录。

### 5. 普通上传与秒传

- 前端按 2 MiB 块计算完整 MD5，先调用 `/api/md5`。
- 用户已有同名同 MD5 关系则返回已存在；物理正文存在但用户未拥有则新增关系、引用数和用户计数；物理正文不存在才上传。
- 小文件 `/api/upload` 全量读取 multipart，写本地临时文件，再通过 `fork/exec` 调用 `fdfs_upload_file`。
- 上传接口不校验 Token，也不重新计算正文 MD5；只检查正文长度等于客户端声明大小。
- 写入 FastDFS 与三张 MySQL 表不是一个事务，失败会产生孤儿正文或错计数。

### 6. 大文件分片

- 大于 10 MiB 时按 10 MiB 切片，前端逐片顺序上传。
- 初始化校验 Token，Redis Hash 保存文件名、大小、片数、用户和已传编号，TTL 24 小时；临时片存在 `/tmp/chunks/{md5}`。
- 单片上传不校验 Token、所有者、编号范围、大小或摘要；`uploaded` 使用非原子逗号字符串。
- 合并校验请求 Token，但不核对会话用户；只检查编号文件存在，随后用 appender API 按序追加。
- 没有合并锁、状态机和整体摘要复核；边追加边删分片会使失败恢复困难。
- 只能说支持同一应用容器生命周期内的缺片补传，不能说跨容器可靠续传。

### 7. 分享、取消、转存与删除

- 创建分享会更新用户目录项分享状态、插入 MySQL 分享行、更新公共计数和 Redis ZSet/Hash。
- Redis 未命中时会回查 MySQL 并可回填，因此分享表是持久事实源。
- `dealsharefile` 的取消、转存和公共下载计数没有 Token，是明确越权风险。
- 转存只新增目标用户关系并增加引用数，不上传正文。
- 删除用户关系后减少引用计数，归零才删除物理记录和 FastDFS 文件；当前跨存储操作无事务和补偿表。
- 图片分享生成 `urlmd5` 和 4 位 Key，但响应不返回 Key，浏览也不校验 Key，不能说提取码已生效。

### 8. 实际部署与性能

- 只有三容器单机部署：MySQL；Nginx + 单 Tracker + 单 Storage；FastCGI + Redis。
- Nginx 和 FastDFS 理论上的集群能力不能冒充本项目实际拓扑。
- 当前没有可信系统压测、并发对照实验或生产用户数据，不能给出吞吐、延迟和提升比例。
- 源码中没有 LRU-K、动态反馈负载均衡、线程池、数据库连接池或内存池实现。
- 若被问优化，先说当前缺口，再说怎样设计与验证，不要用理想方案替代现状。

### 9. 项目来源与个人贡献

> 这是学习型项目。我能按代码讲清三容器部署、13 条 FastCGI 路由、秒传、普通上传、分片 appender 合并、分享和引用计数删除的真实链路，也能指出代码中的鉴权、摘要、事务、幂等和持久化缺口。FastDFS 自身的存储和调度能力属于开源框架；LRU-K 与动态负载均衡在当前仓库没有项目代码，因此不会表述为个人已实现成果。

## 五、LRU-K 与动态负载均衡：仅作理论备考

### 1. FastDFS 默认策略的理论局限

轮询可大致均衡请求数，但文件大小和处理成本不同；按剩余空间选择也不能反映 CPU、内存、磁盘 I/O 和网络的实时压力。理论上可采集节点状态、筛选低负载候选，再按处理能力带权选择，但这需要修改或扩展 Tracker 的状态采集与调度逻辑，并通过真实集群对照实验验证。

### 2. 诚信回答

> 我学习过论文中的动态反馈调度思路，也理解 LRU-K 用第 K 次历史访问抑制一次性扫描污染的原理；但在当前复核仓库里没有找到它们的源文件、构建目标、接入配置或测试。因此我只把它们作为设计讨论，不说成已合入 FastDFS、已用于 Storage 下载或取得了性能提升。

### 3. 如果后续正式实现，需要什么证据

- 明确的源文件与构建目标；
- 在 Tracker 或 Storage 请求路径中的实际接入点；
- 配置开关、指标和错误处理；
- 固定硬件、数据集、并发模型和缓存状态的基线/改进对照；
- 原始吞吐、P50/P95/P99 延迟、错误率和资源数据；
- 故障、并发和回退测试。

没有这些证据，不给“提升 30%”之类个人结论。

## 六、代码复核后的改进答法

### 1. 如果重新设计，优先改什么

1. 统一所有写接口鉴权，从 Token 会话取用户身份。
2. 服务端复算 SHA-256，建立内容占位与用户关系唯一键。
3. 用 `upload_id`、原子分片状态和合并状态机重做续传。
4. 把关联 MySQL 更新放入事务，并引入 FastDFS outbox/补偿清理。
5. 持久化 Redis 和临时目录，增加过期垃圾回收。
6. 修复图片提取码、签名下载、SQL 参数化与敏感日志。

### 2. 如果问最大难点

> 最大难点不是“把文件切开”，而是让分片状态、临时文件、远端 appender 和数据库发布在失败与重试下保持可恢复。当前实现跑通了顺序分片和按序追加，但缺少会话隔离、分片摘要、合并抢占和补偿；这正是我复核后最明确的工程化改进点。

### 3. 如果问并发上传同一文件

> 当前“先查 MD5、未命中再上传”存在检查—执行竞态，两个请求可能都上传正文。改进应为摘要和大小建立唯一内容记录，使用 `UPLOADING/READY/FAILED` 占位与租约原子争抢上传权；用户关系也加唯一键，只有首次插入才增加引用计数。失败的重复正文交给可重试清理任务。
