## 一、项目整体与架构

### 1. 介绍一下这个项目，它解决什么问题？

这是一个局域网内的点对点文件传输工具。两台设备连到同一个局域网之后，不需要服务器、不需要登录、不需要配置 IP，就能互相发现并直接传文件。

我做的是其中的内核部分：**设备发现、自定义传输协议、TCP 收发和任务调度**，取消握手是在 AI 初版上重构的。界面和 C ABI / JNI 桥接层是 AI 生成的，我做了简单修改。

整个系统分四层：最上面是界面层，中间是 C ABI 和 JNI 桥接层，下面是 C++ 内核。桥接层不是我写的，但它解决的问题很明确——C++ 没有稳定 ABI，而 Python 的 `ctypes` 和 Java 的 JNI 只能对接 C 接口。

### 2. 内核的分层结构是怎样的？为什么要这样分？

内核的入口是 `AppCore`，它是一个门面（Facade），本身不写任何网络代码，只负责按正确顺序组装三个子服务：

- `IdentityValidator`：设备身份的生成、持久化和校验。
- `DiscoveryService`：UDP 设备发现。
- `TransferManager`：TCP 传输的调度中心，下面是 `TransferSession`、`TcpAcceptor`、`TcpConnector`、`TcpSender`、`TcpReceiver`。

这样分层的核心原则是**每层只做一件事**。`TransferSession` 不知道“文件”是什么，它只负责收发帧；文件语义（元数据、进度、完成状态）由 `TcpSender` 和 `TcpReceiver` 维护。好处是每一层都能独立做单元测试——比如协议层的测试完全不需要网络。

### 3. 初始化顺序是怎样的？为什么不能交换？

顺序是固定的：

```text
init_resource()   → 加载配置
init_identity()   → 生成或加载本机 fingerprint
init_discovery()  → 构造 UDP 发现服务并注册回调
init_receiver()   → 绑定 TCP 端口，回写给发现服务
```

有两处依赖关系。

**身份必须先于发现**：发现服务收到报文后要用本机 fingerprint 过滤掉自己的广播，如果身份还没生成，就没有可比较的值。

**接收端必须先于公告**：广播报文里携带 `tcp_port` 字段，对端靠这个字段知道该连哪个端口。

这里有一个容易被看错的细节，值得主动讲清楚：广播包里那个端口是**动态分配**的——`init_receiver()` 创建 `TcpAcceptor` 时传的端口是 `0`，绑定完成后才读出真实端口回写给发现服务。但这两个动作不会冲突，因为**绑定是同步的，公告是延后的**：`init_receiver()` 内部同步完成 bind，所以函数返回时端口已经确定、也已经回写完；而真正的周期公告发生在 `AppCore::run()` 里调 `discovery_service_->run()` 的时候，那时四个 `init_*` 早就全跑完了。

### 4. 一次文件发送的完整链路是怎样的？

我从发送端往下讲。

上层调用 `send_file` 之后，`TransferManager` 先生成一个 `transfer_id`（UUID v4），构造传输上下文并放进待启动队列。调度器检查三级并发上限，有空槽位才真正启动。

启动之后，`TcpConnector` 异步连接目标的 `ip:port`。连接建立后创建 `TransferSession`，`TcpSender` 打开文件流、算出总块数、分配已确认位图，然后发出 `FILE_REQUEST` 帧——这是一个 JSON 帧，携带文件名、大小、块大小和任务信息。

对端回复 `FILE_RESPONSE`。收到接受响应后状态转成 `Sending`，`slide_window_send()` 开始按窗口投递 `FILE_DATA` 帧。每收到一个 ACK，窗口左边界就往前推进，然后继续填满窗口。最后一块带上 `LAST_CHUNK` 标志，全部确认后进入 `Completed`。

接收端是镜像的：acceptor 收到连接后创建 session 和 `TcpReceiver`，解析出 `FILE_REQUEST` 后向上层抛 `IncomingRequest` 事件；用户确认后内核创建 `.part` 文件并回响应，随后循环接收数据写入磁盘，最后一块到达时把 `.part` 重命名成正式文件名。

### 5. 为什么不用 HTTP 或者 WebSocket，要自己定一套二进制协议？

主要有两方面的考虑。

**发现层不能用 HTTP**。HTTP 基于 TCP，发请求之前必须已经知道对方的 IP 和端口。而设备发现要解决的前提恰恰是“我不知道谁在线”，所以只能靠 UDP 广播或组播。这也是 `PROTOCOL.md` 里明确写下的设计决定。

**传输层选择了更小、更直接的私有帧格式**。HTTP 确实有头部和请求语义开销，但传文件可以直接发送二进制正文，并不必然使用 Base64；WebSocket 需要 HTTP Upgrade，客户端帧还要 masking；gRPC 则引入 Protobuf 和相应工具链。这个项目更看重固定 24 字节头、可控状态机和较少依赖，所以选择自定义协议。代价是要自行处理版本兼容、安全、错误语义和互操作性，不能只讲性能收益。

自定义协议的优势是头部只有 24 字节且定长，解析时不需要扫描分隔符；控制消息用 JSON，人可读、跨语言零依赖、抓包方便；文件数据用原始二进制，没有任何编码开销。

### 6. 这个项目和 LocalSend 是什么关系？能互通吗？

设计思路上参考了 LocalSend：同样用 UDP 做局域网发现、TCP 直传文件、用任务组表达“一次发送多个文件”。C ABI 里发送文件的接口也明确写了要与 LocalSend 的任务组功能对齐。

但**通信协议本身是我自己定的**，不是 LocalSend 的 HTTP 协议。我实现的是 24 字节定长二进制帧头加 JSON/二进制负载的私有格式。

所以要如实说：**当前版本不能和官方 LocalSend 客户端互通**，“对齐”指的是数据模型层面的对齐，不是协议兼容，而且我没有做过真实的互通测试。

### 7. 你在这个项目里主要负责什么？

我自己做的是这几块：**UDP 设备发现服务、自定义 TCP 帧协议、传输会话与收发（滑动窗口和 ACK）、任务调度与并发控制**。另外取消握手协议是在 AI 初版的基础上发现问题之后我重构的。

有几块我要讲清楚来源：桌面端和 Android 端的 UI 是 AI 工具生成的，我在生成结果上做了简单修改；**C ABI 和 JNI 桥接层也是 AI 生成的**。

但我想强调一点：**这不影响我能讲清楚整个系统怎么跑起来**。桥接层解决的是一件事——C++ 没有稳定 ABI，而 `ctypes` 和 JNI 只能对接 C 接口，所以内核要暴露一层不透明句柄加错误码的 C 接口。至于界面，它只是通过这层拿到事件、再把状态渲染出来。

真正的复杂度不在这一层，而在这三个地方，我都自己写过也踩过坑：**一是取消握手怎么保证双方收敛，二是滑动窗口和 ACK 怎么配合，三是三级并发调度怎么约束大任务。** 如果面试官想往下挖，我更希望从这三个地方开始。

开发笔记和提交历史记录了双端联调、抓包排查、取消语义重构、Debug/Release 差异、Docker 双端测试和一次 SIGSEGV 定位。面试时这些内容应当按“开发记录中的复盘”来讲；其中当前仍存在的机制可以回到代码验证，历史测试现场则不能仅凭现有源码复原。

如果面试官问“这个项目是不是 AI 写的”，正面回答：**界面和桥接层是 AI 生成，内核的发现、协议、传输和调度是我自己实现的，取消握手是我在 AI 初版上重构的。** 与其含糊其辞，不如把边界划清楚——因为划清楚之后，对方会去问内核，而内核经得起问。

## 二、线程模型与并发

### 8. 项目用了什么线程模型？

**单 `io_context` 加单 I/O 执行线程**。

`AppCore::run()` 是阻塞接口：先注册发现异步操作，再创建一条线程执行 `io_ctx.run()`，随后等待这条线程结束。C ABI 为了让 `fakesend_core_start()` 立即返回，会再建一条 `runner` 包装线程调用 `AppCore::run()`；该线程主要阻塞在等待上。真正执行网络回调的仍只有一条 I/O 线程，三个子服务共享同一个 `io_context`，所以异步回调、定时器和事件派发在这条线程上串行执行。

代码没有显式创建 `asio::strand`。由于这个 `io_context` 只由一条 I/O 线程执行，异步网络回调在当前模型下自然串行，`peers_`、传输上下文和单个 session 的 `write_queue_` 因而主要由同一条线程修改。准确说法是“单消费者串行执行”，不要把不存在的 strand 对象说成实现细节。

### 9. 为什么不用多线程加锁？

三个理由。

第一，当前工作负载以磁盘和网络 I/O 为主，单线程事件循环可以同时挂起多条连接，而不需要给每条连接分配线程。是否增加线程能提升吞吐仍需基准测试，代码本身不能证明“多线程一定无效”。

第二，**ASIO 的 Proactor 模型在单线程下已经能处理大量并发连接**。事件驱动本身就是为高并发 I/O 设计的，不需要靠线程数堆并发。

第三，网络状态集中到一条 I/O 线程后，确实减少了这部分状态的数据竞争和加锁需求。但调用方线程、停止流程、配置、日志以及桥接回调仍然存在并发同步，不能说整个项目不存在数据竞争或死锁风险。

所以更准确的说法是：这个项目用单线程串行化换来了状态管理的简单性，而不是“没考虑并发”。

### 10. 那项目里到底有没有锁？

有，而且不止三处。当前代码中比较重要的同步点包括：

- `AppCore::io_thread_mutex` 保护 I/O 线程对象的启动、停止和 `join`。
- `DiscoveryService::refresh_mutex_` 保护手动刷新限流状态。
- `ResourceMgr::mutex_` 保护配置、路径和缓存。
- `Logger::mtx_` 串行化日志器状态与文件输出。
- C ABI 的 `callback_mutex` 保护回调指针和 `user_data`。
- JNI 的 `g_sinks_mutex` 保护事件 sink 注册表。

此外，`AppCore::is_running` 和 C ABI 的 `started` 使用原子变量表达生命周期状态。

准确的说法是：**网络状态机主要依靠单 I/O 线程串行化；生命周期、配置、日志和桥接回调仍然使用显式同步。**

### 11. `work_guard` 是干什么的？不用会怎样？

`io_context::run()` 在没有待处理异步操作的时候会**立即返回**。如果启动那一刻恰好没有任何排队的回调，`run()` 会马上退出，整个服务看起来像“启动后瞬间消失”。

`executor_work_guard` 在构造时向 `io_context` 注册了一个“持续有工作”的信号，让 `run()` 一直阻塞，直到显式调用 `work_guard.reset()`。

停止流程的顺序是：先停子服务、关套接字、取消定时器，再 `reset()` 让 `run()` 退出，最后 `join()` 等 I/O 线程结束。顺序不能反，否则可能出现回调还在跑但对象已经被销毁的情况。

### 12. 事件回调在哪个线程执行？上层要注意什么？

**在 I/O 线程上执行，不是调用方的线程。** 这一条在 C ABI 头文件、JNI 适配层和 Kotlin 侧都反复声明过。

所以上层有两条硬性约束。第一，**不能在回调里做阻塞操作**，否则整条事件循环会被卡住，所有连接都停摆。第二，**不能直接在回调里修改 UI 状态**，必须把数据派发到主线程。

还有一条容易踩的：**事件结构体里的字符串指针只在回调期间有效**，回调返回后可能被释放或覆写。要保留就必须在回调内部当场拷贝。

## 三、UDP 设备发现

### 13. 设备发现是怎么实现的？

用 IPv4 的 **UDP 组播加定向广播**，端口固定是 `53317`，组播地址是 `239.255.77.77`。

启动时先发一个 `QUERY` 广播，请求局域网内所有设备立即回复。之后每 3 秒发一次 `ANNOUNCE` 广播，声明自己还在线。对端收到 `QUERY` 之后会**单播**回一个 `REPLY`，这样发起方不用等下一个公告周期就能立刻发现设备。

**内核不发送 `255.255.255.255` 全局广播。** 代码注释给出的理由是避免扩大广播域压力。至于不同 Android 版本和设备对全局广播的具体处理，当前代码无法证明，因此不把“必然被内核禁止或静默丢弃”作为项目事实来回答。

所以内核的做法是遍历系统网卡，对每个符合条件的接口（IPv4、已启用、非回环、有广播能力）算出它的子网广播地址，去重之后加入发送目标列表。定向广播端点列表上限是 64 个端点。

### 14. 三种消息类型分别做什么？

| 消息 | 发送时机 | 发送方式 | 作用 |
| --- | --- | --- | --- |
| `ANNOUNCE` | 每 3 秒 | 组播 + 定向广播 | 声明在线，刷新对端的 `last_update` |
| `QUERY` | 启动时、手动刷新时 | 组播 + 定向广播 | 请求所有设备立即回复 |
| `REPLY` | 收到 `QUERY` 后 | 单播，只回给查询者 | 加速首次发现 |

三种消息**复用同一个载荷结构** `AnnouncedData`，靠 `type` 字段区分处理方式。载荷有五个字段：`type`、`device_name`、`public_key`、`fingerprint`、`tcp_port`。

这是一个典型的“周期心跳 + 主动探测”组合。心跳负责保活，探测负责快速收敛。

### 15. 为什么公告间隔取 3 秒、超时取 15 秒？

这两个值有明确的比例关系：**15 秒正好是 5 个公告周期**。

五个名义公告周期给偶发丢包留出了余量，但“连续丢四个后第五个一定赶上”不是严格保证，因为公告和超时检查的调度时刻、网络抖动都会影响边界。准确说法是：3 秒公告、15 秒超时降低了单次丢包造成误下线的概率。

超时检查每秒轮询一次；在事件循环没有被阻塞、定时器按期调度的前提下，通常会在超过 15 秒后的下一个检查周期发现离线。代码不提供硬实时保证，因此不要说“16 秒内一定”。

### 16. 怎么防止设备“发现自己”？

收到报文之后，先拿报文里的 `fingerprint` 和本机 `fingerprint` 比对，相同就丢弃。

用 fingerprint 而不是 IP 做过滤是有原因的：同一台设备可能同时通过有线和 Wi-Fi 可达，会出现多个 IP。如果按 IP 过滤，就会把自己认成两个不同的设备。

### 17. 对端超时是怎么检测的？为什么不用每个节点一个定时器？

用**单个定时器每秒轮询整张对端表**，检查每条的 `last_update` 是否超过 15 秒，超了就标记离线并抛 `PEER_LOST` 事件。

给每个对端各挂一个定时器也能实现同样的效果，但那样在设备频繁上下线的时候要反复创建和取消定时器，代码量和出错概率都更高。单个轮询定时器的实现简单得多，代价只是每秒遍历一次 map——对一个局域网里最多几十台设备来说完全可以忽略。

### 18. 如果局域网里有 100 台设备同时发公告，UDP 会丢包吗？

UDP 本身不保证可靠性，但在这个场景下影响很小，有几个原因。

第一，公告每 3 秒重复一次，单次丢包通常可以由后续周期弥补。第二，15 秒超时给偶发丢包留出了多个公告周期。第三，接收缓冲区固定为 2048 字节；代码没有显式断言发现 JSON 一定小于 500 字节，也没有通用的 MTU/分片保证，所以不要把经验值说成协议约束。

另外代码有两处主动削峰。所有发现报文都经过一个容量上限为 256 的 FIFO 发送队列串行发出，任意时刻只有一个发送操作在途；两个包之间插入 10 到 30 毫秒的随机抖动。队列满时新报文会被丢弃并记录告警。这能平滑单机突发发送，但无法保证 100 台设备同时公告时不丢包。

如果自动发现不可用，上层可以直接提供目标 IP 和端口调用发送接口，从而绕过 UDP 发现；后续仍要经过 TCP 连接、协议握手、接收确认和文件 I/O，仍可能因为端口错误、防火墙、拒绝、超时或磁盘问题失败。

### 19. 手动刷新为什么要做限流？

手动刷新有 **3 秒冷却**。冷却窗口内重复点击不会执行任何网络 I/O，而是直接返回 `FAKESEND_ERROR_REFRESH_RATE_LIMITED`，并通过输出参数告诉调用方还剩多少毫秒。

这个设计是有必要的，因为连续点击**不会提高发现成功率**——发现失败通常是网络路径问题（AP 隔离、防火墙、网卡选择错误），多发几个广播包解决不了。限流能防止用户在焦急的时候制造广播风暴。

## 四、身份与信任

### 20. fingerprint 是什么？为什么不直接用 IP？

先给结论：**fingerprint 是 `generate_uuid_v4()` 随机生成的 UUID v4 字符串**，是设备的稳定标识。

用它而不是 IP 的原因有三个。

**跨网络稳定**：设备从 Wi-Fi 切到有线，IP 变了，但 fingerprint 不变。
**跨重启稳定**：fingerprint 持久化在 `my_info.bin` 里，重启之后仍然是同一台设备。
**防 IP 冲突**：局域网 IP 可以手工设置，两台设备完全可能撞 IP，但 UUID v4 有 122 位随机空间，实际碰撞概率可以忽略。

### 21. fingerprint 是公钥的哈希吗？

**不是，这一条必须说清楚。**

fingerprint 是 `generate_uuid_v4()` 直接生成的随机字符串，**不是 `hash(public_key)`**，也不是任何密码学意义上的密钥指纹。

结构体里确实有一个 `public_key` 字段，但它**目前是预留字段，传输协议完全没有使用**，头文件注释里也写明了这一点。

所以它的能力边界是：**能区分设备，不能认证设备**。它解决的是“重启或换网之后不要重复显示成两台设备”，不解决“如何确认对方真的是上次那台设备”。如果我说这个项目做了“公钥指纹校验”，那是明显超过实际实现的表述。

### 22. 那 validate() 是怎么工作的？

`validate()` 现在只查内存。它从报文里取出 fingerprint，在内存中的对等身份缓存（`peer_identities_cache_`）里按 fingerprint 查找。找不到就直接返回 `NOT_FOUND`；找到之后比对 `device_name`，如果名称没有变化，整个调用不产生任何磁盘 I/O，直接返回 `SUCCESS`。

只有名称确实发生变化时，它才会落盘。这时它先复制出一份候选快照，把新名称写进副本，再通过原子替换写入 `info.bin`；只有写入成功之后，才用这份候选快照替换当前缓存。如果写入失败，它返回 `INVALID_FILE`，内存仍然保留改动前的状态，避免缓存和磁盘出现分叉。

这个缓存是本次持久化优化的重点，目的是把 `info.bin` 的读取从发现心跳中移走。在此之前，`validate()` 每次都会重新打开并解析整个数组；现在缓存只在运行目录确定后加载一次，无身份新增、无设备改名的心跳不会读写 `info.bin`。缓存的数据来源仍然是该文件，加载逻辑集中在 `load_peer_identities_cache()`：文件不存在时只初始化空缓存；有效时读取解析一次；为空、非法 JSON 或非数组时，静默恢复为空数组并原子重写；暂时读不到时，本次运行使用空缓存，且不会在每个心跳上重试。需要补充的是，`on_peer_found()` 仍会无条件全量重写 `discovered_peers.json`，所以整个发现心跳路径还没有做到零磁盘 I/O。

这里还有一个结构性特点值得主动说：`ValidateResult` 枚举保留了 `FAILED`，但当前 `validate()` 没有任何返回该值的语句。实际返回值是 `INVALID_FILE`、`INVALID_IDENTITY`、`NOT_FOUND` 或 `SUCCESS`。

而 `NOT_FOUND` 的处理方式决定了实际语义：发现服务的 `on_peer_found` 会**先保存新 fingerprint，再调用 `validate()`**。`save_device_identity()` 已按缓存去重，只有新增身份时才原子落盘，成功后再提交内存，失败时保留原缓存并允许后续公告重试。所以对新设备来说，第一次报文就会被静默登记。

这个行为类似“首次见到即记录”，但当前实现**没有向用户展示指纹、没有配对确认，也没有密钥认证**。因此它不是完整的可信设备或安全 TOFU 机制。

### 23. 有没有可信设备管理和指纹变更告警？

**都没有。**

`PROTOCOL.md` 里设计了完整的首次连接流程：交换 deviceId 和公钥、界面展示指纹摘要、用户手动确认、保存可信记录；后续如果 fingerprint 变了就告警并要求重新确认。这套设计是有价值的，但**它没有落地**。当前既没有可信设备管理界面，也没有指纹变更检测。

我在讲解文档里把这一条列进了“未实现”清单，面试时应该主动说明，而不是等对方发现 `public_key` 字段是空的再来问。

## 五、TCP 帧协议

### 24. 自定义的帧格式是怎样的？

**24 字节定长头 + 变长负载**：

```text
偏移 0    4 字节   magic          固定 0x4C465431
偏移 4    2 字节   version        当前 0x0001
偏移 6    2 字节   type           消息类型
偏移 8    4 字节   flags          位掩码
偏移 12   8 字节   requestId      请求/响应关联 ID
偏移 20   4 字节   payloadLength  负载字节数
偏移 24   N 字节   payload        JSON 或原始二进制
```

所有多字节整数一律用**大端序**。头部定长带来的好处是解析时直接按固定偏移取值，不需要扫描分隔符，也不用担心分隔符和正文内容冲突。

当前解析器会校验 `magic` 和 2 MiB 负载上限，但**不会校验 `version`**。所以版本字段目前只完成了序列化和反序列化，还没有版本协商或“不支持版本”的错误处理。

### 25. TCP 是字节流，你怎么处理粘包和拆包？

用“先读固定长度头部，再按头部声明的长度读负载”的两段式读法。

`do_read_header()` 用 `asio::async_read` 配 `transfer_exactly(24)` 精确读满 24 字节；解析出 `payloadLength` 之后，再用 `transfer_exactly(N)` 读满负载。这样无论 TCP 把字节流怎么切分和合并，帧边界都是确定的。

整个读取是**串行链式**的：读头部 → 读负载 → 回调上层 → 再读头部。这不是可以优化的地方，而是唯一正确的做法——要读第 N 帧的负载，必须先知道它的长度；要知道长度，必须先读完第 N 帧的头部；而头部的位置又取决于第 N-1 帧的负载有多长。

### 26. 魔数 `0x4C465431` 是什么意思？有什么用？

它是 ASCII 字符串 `"LFT1"` 按大端序解释成 `uint32` 的结果：`'L'=0x4C`、`'F'=0x46`、`'T'=0x54`、`'1'=0x31`，表示 LocalSend File Transfer v1。

有两个作用。第一是**协议识别**：收到的前 4 个字节不对，可以立刻判断这不是本协议的连接，直接关闭并告警。第二是**帧同步保护**：如果字节流因为某种原因错位了，魔数校验会直接失败，而不是把随机数据当成帧头去解析——否则会用一个完全错误的 `payloadLength` 去申请内存。

### 27. 为什么大端序序列化要手写，不用 htonl？

`tcp_frame.hpp` 通过移位和掩码逐字节实现 16、32、64 位整数的大端序读写。这样所有字段共用一套明确规则，行为不依赖宿主机自身字节序。当前仓库没有反汇编或基准结果，因此不要承诺一定生成单条 `bswap/rev`，也不要说手写实现让项目摆脱了 Winsock 依赖——网络层本来就使用 Asio/Winsock。

### 28. 单帧负载有没有上限？

有，`MAX_PAYLOAD_SIZE = 2 MiB`，常量定义在 `transfer_session.cpp`。读头部之后如果发现 `payloadLength` 超过这个值，直接判失败并关闭连接。

这是防御性设计。`payloadLength` 是网络来的数据，如果攻击者发一个声称负载是 4 GB 的帧头，而代码直接拿它去 `resize()`，内存瞬间就爆了。2 MiB 对 JSON 控制帧来说绰绰有余（实际通常不到 1 KB），对 64 KiB 的文件数据块也留了足够余量。

### 29. requestId 是干什么的？怎么生成的？

`requestId` 用于把响应关联回请求。发送端发 `FILE_REQUEST` 时带一个 ID，接收端的 `FILE_RESPONSE` 带同一个 ID，发送端据此知道这个响应对应哪次请求。

正常路径的 `file_id` 是 UUID v4。`try_make_request_id()` 会跳过连字符和其他非十六进制字符，依次收集前 16 个有效字符并折叠成 64 位整数；只要至少存在一个十六进制字符就会成功。因此它并不严格验证 UUID。映射到 64 位后仍存在非零碰撞概率，当前代码没有碰撞检测，不能用“回绕时间”替代碰撞分析。

### 30. 标志位里 COMPRESSED 和 ENCRYPTED 用了吗？

**没有，两个都是预留的。**

当前只是给两个位分配了数值，收发状态机没有启用它们，也不会拒绝未知标志，更没有“不支持加密”的错误响应。预留位可以作为未来扩展入口，但**当前代码尚未实现向后兼容或能力协商**。

这个设计本身是合理的，但必须说清楚：**当前传输是明文的，没有任何加密。**

## 六、传输会话与滑动窗口

### 31. 为什么设计成“一个 session 一个文件一条连接”？

这样切分是为了让状态简单。

`TransferSession` 只负责收发帧，完全不知道“文件”是什么；文件级的语义——元数据、进度、完成状态——由 `TcpSender` 和 `TcpReceiver` 维护。职责清晰之后，会话层可以独立测试，也可以复用到将来的其他传输类型上。

代价是发送 10 个文件就要建 10 条连接，连接建立的开销没法摊薄。不过在局域网里 RTT 很小，三次握手成本可以忽略，这个代价是可以接受的。同时它也**不支持单 session 多文件或单文件多连接**，这是当前实现的明确边界。

### 32. 滑动窗口是怎么工作的？

默认配置是：块大小 64 KiB、窗口 32、ACK 阈值 16，配置结构还包含 `ack_timeout_ms = 200`。但当前收发状态机没有读取这个超时字段，也没有创建 ACK 定时器，所以 200 毫秒不是已生效机制。

发送端的核心循环是 `slide_window_send()`：只要窗口没满（`next_to_send_ - send_base_ < window_size`）且还有未发送的块，就继续投递 `FILE_DATA`。每收到一个 ACK，就把 `send_base_` 推进到 ACK 声明的最大连续块号，然后再次填充窗口。

按默认参数，单个发送 session 最多允许约 2 MiB（64 KiB × 32）尚未被 ACK。开发笔记用 BDP 解释过这个取值，但代码不测 RTT 或带宽，也不动态调窗，因此不能保证它能跑满任意链路。

### 33. ACK 是每块都回吗？

**不是，只有第一块立即回。**

这样设计的原因是：如果每收一块就回一个 ACK，ACK 控制帧本身会占掉相当比例的带宽，块越小这个比例越夸张。

具体策略是：**第一块立即确认**，之后累计到 `ack_threshold`（默认 16）块回一个 ACK，收到 `LAST_CHUNK` 时再发最终 ACK。`ack_timeout_ms` 当前没有参与这套逻辑。

ACK 的负载里带 `chunk_index` 和累计接收字节数。发送端把这个块号按“最大连续已确认块”处理；接收端实际填的是最近写入块号，所以该语义依赖当前严格按序发送。

### 34. 文件数据是怎么编码进帧里的？

`FILE_DATA` 的负载格式是 `[4 字节大端 chunk_index][原始文件字节]`。

也就是说**块号是内嵌在负载里的，不是放在帧头里**。这样控制帧和文件帧可以共用同一套头部，不用为文件数据单独加字段。

尾块的帧头会带上 `LAST_CHUNK` 标志，当前接收端看到它就进入提交流程。代码没有同时核对块数、块号连续性、累计字节数或最终哈希，所以这个标志只是发送端声明“这是最后一块”，不是接收端对完整性的独立证明。

### 35. 接收端会把整个文件读进内存吗？

**不会。**

收到 `FILE_REQUEST` 并且用户接受之后，接收端创建 `<文件名>.part`，然后按块号算出文件偏移量（`offset = chunk_index × chunk_size`），用 `seekp` 定位之后直接写入。因此单个接收 session 的数据缓冲不随文件总大小线性增长；整个进程的内存仍会随并发连接和排队数据变化。

这也和讲解文档里说的“落盘用临时文件加原子重命名”是配套的：中途失败时不会在用户目录留下一个看起来完整、实际损坏的同名文件。

### 36. 为什么要先写 `.part` 再重命名？

因为直接写目标文件的话，中途失败会在用户目录里留下一个名字正确、内容不完整的文件。用户看到文件在那儿，会以为传输成功了，只有打开的时候才发现损坏——这种失败很难排查。

用 `.part` 后，目标文件名只在 `rename` 成功时出现；取消和受控失败会尝试清理临时文件。这个设计隔离的是“可见名称”和“写入中的文件”，并不验证内容完整性；进程崩溃仍可能留下 `.part`，错误的 `LAST_CHUNK` 也可能让不完整内容被重命名。

### 37. 读写都是串行的，为什么不并发？

要分两个方向看。

**读端的串行由协议决定**，理由和粘包处理一样：变长帧必须按顺序解析，不可能同时读两个帧头。

**写端的串行是主动设计的**。上层可以在任意时刻调用 `send()`，如果放任两个 `async_write` 同时往同一个 socket 写，两个帧的字节会交错，对端解出来就是垃圾。所以 `send()` 只把打包好的帧推进 `write_queue_`，如果队列原本为空且当前没有写入在进行，才启动 `do_write()`。`do_write()` 用 `write_in_progress_` 标志保证同一时刻只有一个 `async_write` 在跑，写完之后弹出队首，队列非空就继续写下一帧。

这里要区分两个层次的“串行”：TCP 是全双工的，**读写两个方向本来就互相独立**，可以同时进行。串行只约束同一个方向。

另外我用的是 `async_write` 而不是 `async_write_some`。后者不保证一次写完整个缓冲区，需要自己处理部分写入的偏移量，状态会复杂很多。

### 38. 接收端支持乱序接收吗？

**协议状态机不支持可靠的乱序确认，这是一个已知约束。**

`TcpReceiver` 用 `expected_chunk_` 追踪最近写入的块号，并据此生成 ACK。头文件里明确写了：如果数据块乱序到达，**下一块仍然会写到正确的位置**（因为偏移量是按块号算的），**但 ACK 的块号会不准确**——它报告的是“最后写入的块”，而不是“最大连续已接收的块”。

在当前发送端路径中，数据帧按块号顺序进入同一 TCP 连接的写队列，TCP 保持字节顺序，所以该约束通常不会触发；这依赖当前单连接、顺序投递模型，不是通用乱序能力。

但如果将来要做多连接并行拉取同一个文件，或者做乱序重传，就必须先把 `expected_chunk_` 换成真正的位图，并把 ACK 改成能表达空洞的格式（比如区间列表）。

## 七、传输调度与并发控制

### 39. 三级并发限制是什么？为什么是三层？

```text
active_total     < max_parallel_total      默认 4
active_for_peer  < max_parallel_per_peer   默认 2
active_for_task  < max_parallel_per_task   默认 2
```

三个条件必须同时满足才能启动新传输，任何一个到顶就进 `pending_task_queue_` 排队。

三层的作用各不相同。**全局上限（4）** 约束所有出站连接。**每对端上限（2）** 在当前代码中实际按 `peer_ip` 计数，不是按 fingerprint 或设备对象计数。**每任务上限（2）** 约束同一 `task_id` 的活跃文件数。

`TransferConfig::normalize()` 会保证三个值至少为 1，并且任务内上限不超过单设备上限，单设备上限不超过全局上限，避免配置互相矛盾导致调度器死锁。

### 40. 接收端受这个限制吗？

**不受。** 这三级限制**只约束本地主动发起的出站任务**。

接收端可以同时处理多个入站连接。这个区分是必要的：如果接收端也受限制，别人发来的文件就会被拒绝，而用户并没有主动做任何操作。限制的目的是防止自己发起的任务把资源占满，不是限制别人发给你。

### 41. 任务（Task）和传输（Transfer）是什么关系？

```text
Task (task_id = "abc", task_name = "假期照片")
  ├── Transfer 0: "报告.pdf"   transfer_id = uuid-1
  ├── Transfer 1: "数据.xlsx"  transfer_id = uuid-2
  └── Transfer 2: "照片.zip"   transfer_id = uuid-3
```

**Transfer 是单个文件的传输会话**，有自己的 `transfer_id`，对应一条独立 TCP 连接。**Task 是一组相关 Transfer 的逻辑分组**，共享 `task_id`、`task_name` 和每任务并发配额。

分组的价值在接收端最明显。第一个处于 `Offered` 状态的文件被接受或拒绝时，任务会记录这次决策；当时已经处于 `Offered` 的同组文件会一起应用，后续到达的同组请求也会自动沿用该决策。因此从内核语义上可以做到“一次决定作用于一个任务”，但具体展示成几个弹窗取决于上层 UI，不能由内核代码直接保证。

任务失败或取消时，同任务里还没完成的文件会被一起取消，已经完成的保持完成状态。

## 八、取消握手与连接关闭

### 42. 取消操作为什么要二阶段握手，直接关连接不行吗？

直接 `close(socket)` 会有两个问题。

第一，**接收方无法区分取消和故障**。它只看到一个 socket 层错误，没法判断这是“用户主动取消”、“网络断了”还是“对方程序崩了”，只能统一按失败处理。结果就是双方对这次传输的最终状态认知不一致。

第二，**上层状态可能无法按取消语义收敛**。开发笔记记录过这个现象：手机端停止发送之后，PC 端先看到 socket 异常，`do_read_header()` 直接拿到错误码并走 `fail() → close()`，上层还没把状态收敛为取消，底层就已经按失败清场，双端 UI 因而停在“传输中”。这是历史联调记录；当前代码层面可以直接确认的是后来加入了 `cancel_request`/`cancel_ack` 和超时兜底。

所以设计原则是：**取消必须先在协议层成立，再在连接层收尾。**

### 43. 二阶段握手具体是怎么做的？

**先说来源**：最初的实现是 AI 写的单向取消——只发一个取消通知就完事，没有确认。是**我在联调中发现这个做法站不住**，才重构现在的二阶段握手。所以这一块我可以讲设计取舍，但准确的定位是“发现并修复了一个协议设计缺陷”，不是“我从零设计了取消协议”。

实现上，发起方发一个 `CONTROL` 帧，action 是 `"cancel_request"`。对端收到后标记 `cancel_requested_remote_`，停止数据写入、清理 `.part` 文件，然后回一个 action 为 `"cancel_ack"` 的控制帧。发起方收到 ack 后标记 `cancel_ack_received_`，双方各自进入 `Canceled` 终态，然后走优雅关闭。

双方各自维护一组取消状态标志：`cancel_requested_local_`、`cancel_requested_remote_`、`cancel_ack_sent_`、`cancel_ack_received_`，还有一个 `cancel_terminal_` 表示握手已经收敛。

有个细节：**同一个取消请求只回一次 ack**，靠 `cancel_ack_sent_` 去重，避免重复确认把状态机搞乱。

### 44. 如果对端不回 cancel_ack，会不会永远挂起？

不会，有超时兜底。`TransferManager` 里挂了一个取消确认超时定时器，超时之后强制推进到终态并关闭连接。

这是“乐观等待、悲观超时”的写法：正常情况下期待对端礼貌回复，但绝不死等。没有这个兜底，取消操作本身就会变成一个可能永久挂起的操作——这就本末倒置了。

### 45. 优雅关闭为什么要先排空写队列？

`close_after_flush()` 的顺序是：先标记进入优雅关闭状态（之后新的 `send()` 被静默忽略），启动超时定时器，然后等写队列排空；队列空了才调用 `socket_.shutdown(send)` 做 TCP 半关闭，继续读端循环等对端 FIN；收到 FIN 正常关闭，超时则强制关闭。

**必须先排空的原因在取消场景下最清楚**：最关键的一帧就是 `cancel_ack`。如果在这帧还在队列里的时候就 `close()`，对端永远收不到确认，只能一直走到超时兜底。所以排空队列是保证取消语义成立的必要条件。

排空超时取 500 毫秒。这个值是权衡的结果：正常情况下列表里只有少量帧，500 毫秒足够；异常情况下能快速强制关闭，不会长时间挂着一个已经取消的任务。

## 九、C ABI / JNI 桥接（AI 生成，讲到调用关系就收）

**这一节是怎么把话题引开的练习，不是忏悔。** C ABI 和 JNI 桥接层是 AI 生成的，但这段经历的价值在于：**你在联调和排错时绕过它很多次，所以你知道它为什么长这样。**

面试官问到桥接层，通常不是想考你 JNI 语法，而是想确认你是不是真的调过自己的系统。所以策略是：**用两句话把这一层说清楚，然后立刻把话题引到内核。**

可以直接照这个说：

> “这一层是 AI 生成的，我了解它的设计意图——C++ 没有稳定 ABI，Python 的 ctypes 和 JNI 只能对接 C 接口，所以内核暴露了一层不透明句柄加错误码的 C 接口，事件通过函数指针回调回上层。
>
> 我实际打交道最多的不是这一层本身，而是它的**线程约束**：回调跑在 I/O 线程上，字符串指针只在回调期间有效。我在对接的时候踩过这个坑，上层必须在回调里当场拷贝数据，不能直接改 UI 状态。
>
> 真正复杂的状态机在内核那边，比如 `TransferSession` 的读写串行化和 `TcpSender` 的取消状态字段。”

这样处理的好处是：既没有回避 AI 生成这件事，又展示了你确实理解并且实际对接过，最后还主动把战场换到了自己熟的地方。**面试官通常会顺着你给的钩子往下问。**

### 46. 为什么设计 C ABI，不直接用 C++ 接口给上层调用？

> 这层是 AI 生成的。按“我理解它为什么这么设计、并且实际对接过”的口径讲，讲完就把话题带到线程约束或内核状态机上。

因为 **C++ 没有稳定的 ABI**。不同编译器（MSVC、Clang、GCC）的名字修饰规则、虚表布局、异常处理实现都不一样；`std::string`、`std::vector` 这类 STL 类型也不能安全地跨语言边界传递。而 Python 的 `ctypes`、Java 的 JNI、C# 的 P/Invoke 都只能理解 C ABI。

设计上有几个要点：

**不透明句柄**：`fakesend_core_t` 在 C 侧是不完整类型，调用方只能持有指针，不能解引用，内部结构完全不暴露。

**字符串统一 UTF-8**：所有 `const char*` 都是 UTF-8，编码正确性由调用方保证。

**异常边界还不完整**：大多数会调用业务逻辑并返回错误码的 API 有 `try/catch`，但 `fakesend_core_stop`、`fakesend_core_destroy` 和回调注册等简单入口没有统一异常屏障。设计目标是不让异常跨 C ABI，当前实现不能说成“所有函数绝对做到”。

**结构体布局需要维护纪律**：`fakesend_event_t` 是平坦 C 字段，ctypes/JNI 可以按固定布局读取；但它没有 `size` 或 ABI 版本字段，也没有运行时协商。“新增字段只追加、不重排”可以降低风险，却不能保证任意新旧二进制组合都兼容。

### 47. 事件是怎么回传到上层的？

通过一个 C 函数指针回调：

```c
typedef void (*fakesend_event_cb)(const fakesend_event_t* event, void* user_data);
```

`user_data` 是经典的 C 回调模式，允许调用方传入自己的上下文——Python 侧可以是上下文对象，Java 侧可以是全局引用——回调触发时原样传回。

事件覆盖三大类：发现（`PEER_FOUND`、`PEER_LOST`）、传输请求（`TRANSFER_INCOMING`）、传输生命周期（`STARTED`、`PROGRESS`、`COMPLETED`、`FAILED`、`CANCELED`）。

两条硬性约定：**回调在 I/O 线程执行**，**回调里的字符串指针只在本次调用期间有效**。上层必须当场拷贝需要保留的内容，也不能直接在回调里操作 UI。

### 48. JNI 那边是怎么注册的？

用的是**动态注册**，在 `JNI_OnLoad` 里调 `RegisterNatives`，方法签名集中写在 `k_methods` 表里，不是 `javah` 那种 `Java_com_fakesend_xxx` 的静态命名约定。

好处有三个：C++ 侧的函数名不用遵循冗长的包名约定，重构包名时不会把函数名搞乱；注册集中在一处，一眼能看全 JNI 边界上有哪些方法；签名写错的话在动态注册时就立即失败，而不是等第一次调用才崩溃。

还有一处和线程相关：JNI 层用一把 `g_sinks_mutex` 保护事件回调注册表，防止 `set_event_sink` 和 `destroy` 竞争。这把锁在适配层，不在内核业务逻辑里。

### 49. 界面是怎么调用内核的？

桌面端通过 Python 的 `ctypes` 直接调 C ABI；Android 端通过 JNI 调同一套 C ABI，Kotlin 侧再包一层 Repository 和 ViewModel。

界面和桥接层的来源可以直接说：**两套 UI 和 C ABI / JNI 桥接层是 AI 工具生成的，我做了简单修改**，主要是对接事件回调、绑定配置项和修状态显示的问题。

**但这个问题有一个更好的回答方向**：我会顺势讲“对接过程中真正要注意的是什么”——回调在 I/O 线程上执行、字符串指针只在回调期间有效、必须派发到主线程才能改 UI。这些是我实际踩过的，比讲界面怎么布局有价值得多。讲完自然就引到内核的状态机上了。

## 十一、我发现的缺陷与边界（主动坦白区）

这一节的内容**不适合等面试官挖出来再答，主动说反而更好**，因为它证明我看得懂自己的代码。但也不要一次全倒出来，按对方问到的方向挑一两个讲。

### 缺陷 1 身份层没有任何密码学保障

**现象**：新设备第一次广播就会被自动信任，没有确认步骤，也没有指纹变更告警。

**原因**：fingerprint 是 UUID v4 随机生成的，不是公钥哈希，所以它本身不携带任何可验证的秘密。发现服务的 `on_peer_found` 又是**先保存再校验**，等于对新设备无条件信任。

**更隐蔽的一点**：`ValidateResult` 枚举保留了 `FAILED`，但当前 `validate()` 没有返回它的代码；实际可能返回 `INVALID_FILE`、`INVALID_IDENTITY`、`NOT_FOUND` 或 `SUCCESS`。

**改进方向**：把 fingerprint 改成真正的 `hash(public_key)`，启用已经预留的 `public_key` 字段，落实 `PROTOCOL.md` 里设计的首次连接确认流程——界面展示指纹摘要、用户手动确认、保存可信记录、指纹变化时告警。**这些都是设计好的方向，不是已经具备的能力。**

### 缺陷 2 传输完全明文

`ENCRYPTED` 标志位定义好了但没启用，项目里没有任何加密库。

**风险**：在受信任的家庭或办公局域网里可以接受，但在公共 Wi-Fi 或不可信网络上，同网段的第三方抓包就能还原文件内容。

**改进方向**：基于已经预留的公钥字段做密钥协商，然后对负载加密，并补上能力协商、未知标志拒绝和版本兼容处理。当前代码只有标志位数值预留，兼容机制本身还没有实现。

### 缺陷 3 没有完整性校验

接收端**不做最终文件哈希比对，也不做块级校验**。它只依赖 TCP 的校验和保证字节在传输过程中没错，以及 `LAST_CHUNK` 标志判断传输结束。

**这意味着**：如果出现磁盘写入错误、内存位翻转、应用层逻辑缺陷，或者错误的 `LAST_CHUNK`，协议层都可能发现不了；接收端甚至没有在提交前验证实际大小等于声明大小。

`PROTOCOL.md` 里设计了 piece 级 hash 和最终 hash 校验，但没有落地。

### 缺陷 4 接收端只支持顺序数据块

`TcpReceiver` 用 `expected_chunk_` 追踪最后写入的块号并据此生成 ACK，所以乱序到达时 ACK 的语义会不准确。

当前发送端按块号顺序把帧加入同一 TCP 写队列，TCP 保持字节顺序，所以正常路径满足这个假设。但只要将来引入单文件多连接或乱序重传，就必须换成真正的位图加区间 ACK。

### 缺陷 5 端口默认值三处不一致

`AnnouncedData::tcp_port` 的结构体默认值是 `11451`，`DiscoveryService::tcp_port_` 的默认值是 `53317`，而实际生效的是操作系统动态分配的临时端口。**三个值互不相同。**

目前不影响运行，因为启动时都会被真实值覆盖，但这是应该清理的技术债。而且 `PROTOCOL.md` 里“固定发现端口 53317”的写法容易被误读成“传输端口也是 53317”，实际上传输端口是每次启动都可能变的。

### 缺陷 6 发现功能对网络环境高度敏感

发现失败的原因往往不在应用层。Windows 的“公用网络”配置文件会收紧入站流量；路由器的 AP 隔离、组播抑制、访客网络都会阻断发现报文；VPN 和虚拟网卡会干扰网卡枚举。

我吃过一次亏：电脑端日志里明明有发送记录，但收不到任何回复，一开始怀疑是代码问题，后来抓包才确认是入站流量被拦了。

**沉淀下来的排查顺序是**：先看日志有没有发送记录 → 再用 Wireshark 过滤 `udp.port == 53317` 确认数据报是否真的到达 → 最后才怀疑应用代码。这个顺序很重要，因为跳到最后一步会在应用层白改很久。

### 缺陷 7 `ack_timeout_ms` 是未生效配置

配置结构和 C ABI JSON 都暴露了 `ack_timeout_ms = 200`，但 `TcpSender`/`TcpReceiver` 没有读取该字段，也没有 ACK 定时器。当前最终 ACK 依赖 `LAST_CHUNK` 分支，不能把 200 毫秒说成已经落地的超时兜底。

### 缺陷 8 协议版本只写不验

帧头包含 `version = 0x0001`，解析器却只校验 `magic` 和负载上限。不同版本只要魔数相同就会继续解析，没有版本协商或“不支持版本”的错误。

### 缺陷 9 发现心跳仍会写诊断快照

`info.bin` 已经缓存到内存，只有身份新增或名称实际变化才原子落盘；但 `on_peer_found()` 仍无条件调用 `write_peer_snapshot()`，以截断重写方式全量保存 `discovered_peers.json`。所以身份库的周期性 I/O 已消除，整个发现心跳路径仍有非原子的磁盘写入。

### 缺陷 10 空文件发送不会结束

`total_chunks_` 按 `ceil(file_size / chunk_size)` 计算。零字节文件得到 0 个块，发送端在对方接受后不会发送 `FILE_DATA`/`LAST_CHUNK`，也就不会收到 ACK 并进入 `Completed`。当前测试没有覆盖空文件。

### 这些缺陷的共同点

前四条其实指向同一个事实：**这个项目的安全与可靠性保障是薄弱的，主要靠“局域网可信”这个假设**。身份不认证、传输不加密、内容不校验、乱序不支持——单独看每一条都可以接受，但合在一起说明当前定位就是一个“可信局域网内的便捷传输工具”，不是面向不可信网络的产品。

主动把这层定位说清楚，比逐条辩解更有说服力。

| 用的什么协议 | 自定义二进制帧协议，24 字节大端定长头 + JSON/二进制负载 | Q24 |
| 为什么不用 HTTP | 发现层必须用 UDP；传输层不需要 HTTP 的头部和编码开销 | Q5 |
| 用的什么线程模型 | 单 `io_context`、单 I/O 线程，网络状态机主要串行执行 | Q8 |
| 那有没有锁 | 有；生命周期、配置、日志、C ABI 回调和 JNI sink 都有同步点 | Q10 |
| 发现端口和协议 | UDP 53317，组播 `239.255.77.77` 加定向广播，不发全局广播 | Q13 |
| 传输端口是固定的吗 | 不是，绑定时传 0 让系统分配，再广播出去 | 缺陷 5 |
| fingerprint 是什么 | 随机 UUID v4，**不是公钥哈希** | Q20 Q21 |
| 做了设备认证吗 | 没有，只是首次见到就静默登记，没有确认、密钥认证和告警 | Q22 Q23 |
| ACK 是每块都回吗 | 不是，首块立即回，之后累计到阈值才回 | Q33 |
| 窗口大小为什么是 32 | 默认允许约 2 MiB 未确认数据；BDP 是笔记中的取值解释，代码不会动态调窗 | Q32 |
| 支持乱序接收吗 | 不支持，`expected_chunk_` 假定严格递增 | Q38 |
| 断点续传呢 | 没有，块重传、piece 位图、最终哈希都没实现 | 高危项 |
| 有加密吗 | 没有，`ENCRYPTED` 标志预留未启用 | 缺陷 2 |
| 有完整性校验吗 | 没有，只依赖 TCP 校验和和 `LAST_CHUNK` | 缺陷 3 |
| 取消为什么要握手 | 否则接收方分不清“取消”和“故障”，状态收敛不了 | Q42 |
| 并发上限是几层 | 三层：全局 4、每对端 IP 2、每任务 2，**只限制出站** | Q39 Q40 |
| 任务和传输什么关系 | Task 是逻辑分组，Transfer 是单文件单连接的会话 | Q41 |
| 界面怎么做的 | AI 生成 + 简单修改，通过 C ABI / JNI 调内核 | Q49 |
| 实测速度多少 | 提交和笔记记录做过 10 GiB 级双端测试；笔记记录 iperf3 超 50 MB/s、应用初始约 18 MB/s、Release 后明显提升，但没有 Release 的精确值 | 讲解文档 11.2 |
| 最大的技术难点 | 取消握手的完整性与超时兜底的交互 | Q42 Q44 Q45 |

## 最后：这份文档该怎么用

面试时不要按顺序背。**按对方问到的方向，挑对应的那一节讲。**

回答结构统一是：先给结论，再讲实现过程，最后说边界。如果这个问题涉及我发现的缺陷，讲完正常流程之后主动补一句“不过这里有一个我知道的问题”，然后**停下来等对方接**。

不要一口气把缺陷全讲完。讲一个、停住；对方继续追问说明这个方向他感兴趣，再往下展开；如果他换话题，说明这个点已经够了。

**主动说出来的是加分，被挖出来的是减分。** 两者的技术内容完全一样，区别只在于谁先开口。
