# 中文技术笔记润色

在不改变技术事实的前提下，将简略、跳跃或信息密度过高的中文技术记录改写为完整、连贯、便于阅读和复述的书面表达。

## 核心目标

润色后的文本需要同时满足以下要求：

- 原有技术事实、数据、代码标识和结论保持不变。
- 每句话具有明确的动作主体，不让读者反复猜测“谁做了什么”。
- 操作顺序、调用关系、因果关系和问题处理过程能够自然衔接。
- 措辞保持书面化，但不过分正式，也不刻意堆叠专业术语。
- 文字读起来像人在完整描述一件事，而不是由关键词、箭头和结论拼成的速记。
- 保留适量的“首先……然后……”“我们需要……”“随后……”“因此……”等连接方式，但不机械重复。
- 减少连续使用祈使句，优先说明行为、原因、影响和建议。

## 内容边界

开始修改前，先确认用户指定的章节、段落或文件范围。修改只能发生在该范围内，除非用户明确要求同步调整其他内容。

把原文中的内容区分为以下几类：

1. 已由代码或配置确认的实现事实。
2. 已由部署、测试或日志确认的实测结果。
3. 根据现状得出的缺陷、风险或边界。
4. 尚未实现的改进方案或理想设计。

润色时不得把“改进方案”写成“当前能力”，也不得把推测写成已经验证的事实。原文已经使用“实测”“精确化”“修正”“改进”等标签时，应保留这些事实边界。

如果某项内容疑似存在技术错误，但用户只要求润色，应保留原意并指出疑点，不擅自改写技术结论。

## 润色方法

### 1. 补全主语与动作

先找出省略的动作主体，再把句子补充完整。

常见主体包括：

- 浏览器、前端或客户端；
- Nginx、服务端或具体接口；
- FastCGI 进程；
- MySQL、Redis、FastDFS 等组件；
- 用户、开发者或运维人员；
- 当前项目或当前实现；
- “我们”，用于描述实际测试、排查和修复过程。

不要为了避免重复而持续省略主语。相邻句子的主体发生变化时，应明确写出新的主体。

### 2. 展开操作动线

遇到由箭头、斜杠、加号或连续短语组成的调用链时，按照真实顺序展开描述。

可以使用以下叙述方式：

> 浏览器首先发起请求。请求进入 Nginx 后，会匹配对应的路由。随后，Nginx 将请求转发给 FastCGI 模块。该模块完成数据库和缓存操作后，再把结果返回给客户端。

连接词应服务于逻辑关系：

- 表示顺序：首先、接着、随后、然后、最后；
- 表示原因：因为、由于、问题在于；
- 表示结果：因此、所以、最终、这意味着；
- 表示转折：不过、但是、与此同时；
- 表示补充：另外、除此之外；
- 表示条件：如果、只有……才……、一旦。

不需要给每句话都添加连接词。只有在顺序、因果或转折关系不够清楚时才使用。

### 3. 降低单句信息密度

一句话只承担一个主要任务。原文同时包含以下多类信息时，应拆成两句或多句：

- 当前行为；
- 实现方式；
- 产生原因；
- 直接结果；
- 风险或缺陷；
- 改进方案。

例如，不要把“配置是什么、程序如何执行、失败会怎样、应该如何改进”全部压进同一句话。

拆分时保持逻辑连续，避免把有关联的内容切成互不相干的短句。通常可以按照以下顺序组织：

> 当前实现是什么 → 系统如何执行 → 为什么会这样 → 会产生什么影响 → 后续可以如何改进

### 4. 将速记表达改成完整句子

重点处理以下形式：

- “组件 A → 组件 B → 数据库 → 返回结果”；
- “无 Token / 无事务 / 有风险”；
- “成功留什么 / 失败怎么办”；
- “现象：……；根因：……；修复：……”全部挤在一行；
- 多个名词通过斜杠或加号连接；
- 只有结论，没有解释主体和推导过程；
- 使用括号承载完整论点。

箭头、斜杠和加号可以保留在表格、公式、映射关系或非常短的摘要中，但正文应优先使用完整语句。

括号适合补充文件位置、代码行号、单位和简短解释，不应承载一整段关键推理。

### 5. 保持自然的书面语

语言风格应接近开发者向他人说明项目的方式：

- 可以使用“我们首先检查……”“随后发现……”“当前项目采用……”。
- 可以保留适量口语化连接，但避免网络化、情绪化或过度随意的表达。
- 避免为了显得专业而使用空泛抽象词，例如没有必要时不使用“赋能”“闭环”“抓手”“范式”“体系化”等词。
- 专业术语确实能够准确表达技术含义时，应正常保留。
- 英文模块名、函数名、配置项和命令不需要强行翻译成中文。

### 6. 减少祈使语气

将“不要说……”“别把……”“必须先……”等直接命令，改写为说明性表达。

例如：

- “不要说成 13 进程高并发”可以改为“更准确的说法是项目运行了 13 个常驻进程，但单个模块内部仍然串行处理请求”。
- “别只盯 Docker”可以改为“排查时还需要检查宿主机端口的实际监听进程，不能只根据容器状态判断”。
- “必须重建镜像”可以改为“由于旧文件已经进入镜像层，因此只有重新构建镜像后，修改才会真正生效”。

如果某个步骤确实属于不可省略的技术前提，可以保留“必须”，但需要同时解释原因。

## 不同内容的推荐组织方式

### 架构与调用链

先交代整体环境，再从请求发起方开始，按照组件实际经过顺序描述：

> 请求来源 → 入口服务 → 路由匹配 → 业务模块 → 数据组件 → 返回结果

容器、端口、IP、模块等映射关系可以继续使用表格。表格后应补充必要解释，说明容易误解的部署关系和能力边界。

### 技术 Q&A

问题标题应尽量写成完整问题，回答则按照“直接结论—实现过程—原因或影响”的顺序展开。

推荐形式：

> **普通上传是否会重新计算文件摘要？** 当前不会。服务端只会比较文件正文长度与请求声明的长度，并不会根据实际内容重新计算摘要。因此，当前实现直接信任了客户端提交的 MD5。

不要只写“是否校验：无”“原因：未调用函数”之类的速记答案。

### 故障复盘

故障记录优先使用以下顺序：

1. **故障现象：** 用户或系统实际观察到了什么。
2. **问题根因：** 哪个条件或执行顺序导致了故障。
3. **排查过程：** 如何逐步缩小范围并验证判断。
4. **修复过程：** 实际修改了什么，修复后如何验证。
5. **复盘结论：** 这次问题揭示了哪些可复用的经验。

如果原文没有某一阶段的事实，不应为了套用结构而虚构内容。

### 安全问题与改进方案

先说明当前行为，再解释风险，最后介绍改进方向：

> 当前接口没有校验 Token，因此请求方可能绕过正常身份检查。后续可以为写接口补充统一鉴权，并由服务端根据 Token 推导用户身份。

不要只罗列“无鉴权、越权点、需修复”，也不要把尚未落地的方案写成现有功能。

### 实测证据

先说明测试对象和操作，再写响应、日志或数据库结果，最后说明这些结果能够证明什么。

数据、状态码和文件标识应保持精确，不要为了语句顺畅而模糊化：

- 端口、IP 和容器名称；
- HTTP 状态码；
- 文件大小与分片数量；
- Redis key、字段和 TTL；
- `file_id`、URL 和返回码；
- 函数名、配置项和命令；
- 日志中的关键错误信息。

## 格式处理

- 保留原有 Markdown 标题层级、列表结构、表格和代码块，除非原结构明显妨碍阅读。
- 命令、路径、接口、字段名、函数名和代码值继续使用反引号。
- 表格单元格可以保持简洁，不强制改成完整长句。
- 普通段落不应依赖大量加粗来维持结构。
- 标题应准确描述内容，避免“真数据、非编造”“一坑”“启动即崩”等过度口语或情绪化表达；如果用户希望保留个人笔记风格，可以适度保留。
- 不应为了追求统一格式而重新组织用户未要求修改的全部章节。

## 复查与消融

修改完成后，至少进行一次事实复查和一次消融式精简。

### 事实复查

逐项确认：

- 数字、端口、地址、文件大小和状态码没有发生变化；
- 函数名、接口名、字段名和命令没有被误改；
- 已实现能力与改进方案仍然明确区分；
- 因果关系没有在润色过程中被倒置；
- 指定范围之外的内容没有发生变化；
- Markdown 标题、列表、表格和代码块仍然完整。

### 消融式精简

重新阅读改写后的内容，并尝试删除：

- 不提供新信息的重复句；
- 只为显得正式而增加的抽象词；
- 连续重复的连接词；
- 与上下文已经完全重复的解释；
- 不影响理解的过度铺垫；
- 没有事实依据的推测和扩展设计。

如果删除某句话后，技术含义、逻辑动线和阅读体验都没有受损，就应删除或合并这句话。

消融的目标不是把文字重新压缩成速记，而是在“完整表达”和“避免冗余”之间取得平衡。

## 完成标准

最终文本应让读者能够顺着文字回答以下问题：

- 谁在执行这个动作？
- 首先发生了什么，随后又发生了什么？
- 为什么会出现这个结果？
- 当前实现的边界在哪里？
- 哪些内容已经验证，哪些只是改进建议？
- 如果发生故障，问题是如何被发现、验证和解决的？

如果读者仍然需要根据关键词自行补全这些关系，就需要继续修改。

完成后应向用户简要说明：

- 实际修改了哪些章节或文件；
- 主要改善了哪些表达问题；
- 是否保留了全部技术事实；
- 是否确认指定范围之外的内容没有变化；
- 进行了哪些与文档修改相称的检查。
