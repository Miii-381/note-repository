### 二、核心框架收获:Redis 数据的 A / B 权威源判断

这是本轮最有价值的方法论,必须内化。

#### 判断标准(唯一一条)

> **Redis 里这份数据,MySQL 此刻查得到权威版本吗?**
> 查得到 = A(缓存副本);查不到 = B(Redis 自己就是权威)。

#### 两种角色

| | A — 缓存副本 | B — 中间状态 / 独立权威 |
| --- | --- | --- |
| 例子 | 共享文件排行(ZSet),是 share_file_list 的投影 | 登录 Token；分片会话元数据与进度（两者均无 MySQL 等价记录） |
| 丢了会怎样 | 回源 MySQL 重建即可 | 真丢了,只能靠重试 / 超时 / 清理任务兜底,**没有回源重建这条路** |
| "回查 MySQL 确认"有效吗 | 有效 | 无效——MySQL 无米下锅,权威版本尚未产生或根本不存 |

#### 正确理解"Redis 是缓存"

- MySQL 是权威,Redis 是副本,可随时清空重建。
- "缓存未命中 ≠ 不存在",未命中必须回源,绝不把"未命中"当结论。
- 判断"是否已分享"唯一正确答案在 MySQL;查 Redis 只是加速。

#### 本轮三个实例(含我的错误示范,均已掰正)

1. **分享(蒙对)**:MySQL 提交成功、写 Redis 前崩溃 → 不危险,因 ZSet 未命中会回查 MySQL 命中并回填。Redis 只存"已分享文件",没有"未分享"状态位。
2. **分片会话 Hash（代码复核后更正）**：Redis 保存文件名、大小、片数、用户和已上传编号，`/tmp/chunks` 保存正文分片，两者都没有 MySQL 权威副本。Redis 丢失后服务端无法知道片数和进度；临时片丢失则只能补传。若 FastDFS appender 已创建但合并或数据库落库失败，还可能产生远端半成品或孤儿文件。
3. **登录 Token(错)**:MySQL 里无 Token 的权威投影 → 不是 A。Token 是 Redis 作为权威的状态存储,Redis 崩溃 → 所有在线用户掉线,只能重新登录。

> 代码复核结论：普通秒传/上传没有预期 MD5 `SETEX`；分片会话使用 Redis Hash 并设置 24 小时 TTL。该待办已关闭。

### 五、八股摸底:四题表现记录

> 水位判断:C++ 主战场扎实,操作系统有一处硬伤,网络是强项。

#### 1. C++ 移动语义(std::move)

- 答对:move 只做无条件类型转换 `static_cast<T&&>`(贴"可移动"标签),移动动作由移动构造/赋值执行;move 后对象"有效但未指定",可析构可重新赋值,不能假设内部值。
- 需补:
	  - 标签的准确类型叫**右值引用 `T&&`**。
	  - "未指定"≠乱,保证可析构、可重新赋值;但标准不保证移动后还能做有意义的"比较"。
	  - 价值 = 避免深拷贝:move 是移交内部指针,拷贝是复制整段数据,大对象省一次 O(n) 拷贝。
	  - `std::move` 本身零运行时开销,是编译期类型转换。

#### 2. vector 扩容 + 迭代器失效

- 答对:cap 满时申请更大内存(1.5~2 倍几何增长),旧元素移/拷到新址,原地构造新元素,释放旧内存;整块新地址 → 迭代器/指针/引用全部失效。string:任何触发重分配的操作使 c_str() 指针失效。
- 需补:
	  - 扩容时"移动还是拷贝"取决于元素移动构造是否 **noexcept**:有则移动,可能抛异常则退化为拷贝(强异常安全保证)。
	  - 几何增长(而非线性)目的是让 push_back **摊还 O(1)**。
	  - C++17 保证 c_str() 与 data() 同地址,不触发重分配则一直有效。

#### 3. 进程 / 线程(含一处硬伤,必纠)

- 答对:进程=资源分配单位,线程=CPU 调度单位;进程切换开销大线程小;共享代码段/堆/文件描述符,各自拥有栈/寄存器/局部数据。
	- **硬伤 1(重点纠错)**:线程切换"全程用户态"是**错的**。标准库线程是内核线程,调度由内核负责,**同样陷入内核做上下文切换**。线程轻 ≠ 不进入内核,而是**切换时地址空间不变、不用换页表,省掉换页表 + TLB 冲刷**。说"全程用户态"的是**协程/用户态线程**的特征,别和普通线程搞混。
	- **硬伤 2**:通信简单是共享地址空间的便利,不是线程"轻"的原因;"轻"指创建和切换开销低,两个维度别搅一起。
	- 补精确:两线程不共享栈,共享堆、代码段、全局/静态数据、fd 表、信号处理等;各自独占栈、寄存器上下文、TLS。
- 备注:教材"状态转换=变态"是正规术语,此词无误(指状态变换)。

#### 4. TCP 三次握手(四题中答得最深入)

- 答对核心:**历史连接**问题——旧 SYN 迟到,两次握手会让服务端建立无效连接;三次握手让客户端能回 RST 拒绝。
- 需补,三点合一才是满配:
  1. 历史连接:服务端资源被一个永远等不到确认的无效半开连接占住(不是"白白发数据",是资源占用)。
  2. 双向通信确认:三次让两端都确认收发通;两次只确认了客户端→服务端方向。
  3. 资源浪费早回收:第三次握手让服务端有机会及早回收无效连接资源。

### 三、Redis 持久化专项(RDB / AOF 完整口径)

**主线问题表现**:只答了结论层,且有两处表述问题,需按以下口径重答(30 秒版)。

**主答案结构**
- RDB = **内存快照**:fork 出一致时刻的二进制快照,不是"可能不完整",而是**保存粒度**——按规则/手动触发才存,两次快照之间的写命令会丢。
- AOF = **命令追加日志** + fsync 频率可配(每秒/每次写/交给 OS)。
- **都开启时重启优先 AOF**,因为 AOF 数据更接近崩溃点(Redis 4.0 后混合持久化:文件头 RDB + 增量命令,先快载 RDB 再重放增量)。

**三个追问的满分口径**(本轮现场已能答对结论,补细节):
1. **RDB + fork / COW**:子进程写 fork 时刻的一致快照,父进程改页触发 COW、在副本上改 → RDB 不含 fork 后新写入;代价 = 快照期间写入越多、复制页越多、内存峰值越高;被跳过的写由下次 RDB / AOF 兜住。
2. **AOF 重写(必须补 rewrite buffer)**:重写期间父进程仍把新命令**追加进旧 AOF**,同时缓存到内存 **rewrite buffer**;子进程写完新文件后,父进程把 buffer 补到新文件末尾,再 **rename 原子替换** → 零丢窗口。
3. **主从全量同步走 RDB**:即使未开启 RDB 持久化,全量同步也走 RDB(二进制直接载入快、压缩省传输);之后靠 **replication backlog** 补增量;Redis 7 支持 diskless(无盘)复制直接流式发送不落盘。

**答题行为提醒**:面试中不要主动说"项目里只是简单用了 Redis"——会引导面试官按最低水平考。可改口径为"项目中用到的是 Redis 的基础能力",再主动讲深度,让面试官来探。
