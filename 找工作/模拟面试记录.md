### 二、核心框架收获:Redis 数据的 A / B 权威源判断

这是本轮最有价值的方法论,必须内化。

#### 判断标准(唯一一条)

> **Redis 里这份数据,MySQL 此刻查得到权威版本吗?**
> 查得到 = A(缓存副本);查不到 = B(Redis 自己就是权威)。

#### 两种角色

|                  | A — 缓存副本                           | B — 中间状态 / 独立权威                       |
| ---------------- | ---------------------------------- | ------------------------------------- |
| 例子               | 共享文件排行(ZSet),是 share_file_list 的投影 | 登录 Token；分片会话元数据与进度（两者均无 MySQL 等价记录）  |
| 丢了会怎样            | 回源 MySQL 重建即可                      | 真丢了,只能靠重试 / 超时 / 清理任务兜底,**没有回源重建这条路** |
| "回查 MySQL 确认"有效吗 | 有效                                 | 无效——MySQL 无米下锅,权威版本尚未产生或根本不存          |

#### 正确理解"Redis 是缓存"

- MySQL 是权威,Redis 是副本,可随时清空重建。
- "缓存未命中 ≠ 不存在",未命中必须回源,绝不把"未命中"当结论。
- 判断"是否已分享"唯一正确答案在 MySQL;查 Redis 只是加速。

#### 本轮三个实例(含我的错误示范,均已掰正)

1. **分享(蒙对)**:MySQL 提交成功、写 Redis 前崩溃 → 不危险,因 ZSet 未命中会回查 MySQL 命中并回填。Redis 只存"已分享文件",没有"未分享"状态位。
2. **分片会话 Hash（代码复核后更正）**：Redis 保存文件名、大小、片数、用户和已上传编号，`/tmp/chunks` 保存正文分片，两者都没有 MySQL 权威副本。Redis 丢失后服务端无法知道片数和进度；临时片丢失则只能补传。若 FastDFS appender 已创建但合并或数据库落库失败，还可能产生远端半成品或孤儿文件。
3. **登录 Token(错)**:MySQL 里无 Token 的权威投影 → 不是 A。Token 是 Redis 作为权威的状态存储,Redis 崩溃 → 所有在线用户掉线,只能重新登录。

> 代码复核结论：普通秒传/上传没有预期 MD5 `SETEX`；分片会话使用 Redis Hash 并设置 24 小时 TTL。该待办已关闭。

### 五、八股摸底:四题表现记录

> 水位判断:C++ 主战场扎实,操作系统有一处硬伤,网络是强项。

#### 1. C++ 移动语义(std::move)

- 答对:move 只做无条件类型转换 `static_cast<T&&>`(贴"可移动"标签),移动动作由移动构造/赋值执行;move 后对象"有效但未指定",可析构可重新赋值,不能假设内部值。
- 需补:
	  - 标签的准确类型叫**右值引用 `T&&`**。
	  - "未指定"≠乱,保证可析构、可重新赋值;但标准不保证移动后还能做有意义的"比较"。
	  - 价值 = 避免深拷贝:move 是移交内部指针,拷贝是复制整段数据,大对象省一次 O(n) 拷贝。
	  - `std::move` 本身零运行时开销,是编译期类型转换。

#### 2. vector 扩容 + 迭代器失效

- 答对:cap 满时申请更大内存(1.5~2 倍几何增长),旧元素移/拷到新址,原地构造新元素,释放旧内存;整块新地址 → 迭代器/指针/引用全部失效。string:任何触发重分配的操作使 c_str() 指针失效。
- 需补:
	  - 扩容时"移动还是拷贝"取决于元素移动构造是否 **noexcept**:有则移动,可能抛异常则退化为拷贝(强异常安全保证)。
	  - 几何增长(而非线性)目的是让 push_back **摊还 O(1)**。
	  - C++17 保证 c_str() 与 data() 同地址,不触发重分配则一直有效。

#### 3. 进程 / 线程(含一处硬伤,必纠)

- 答对:进程=资源分配单位,线程=CPU 调度单位;进程切换开销大线程小;共享代码段/堆/文件描述符,各自拥有栈/寄存器/局部数据。
	- **硬伤 1(重点纠错)**:线程切换"全程用户态"是**错的**。标准库线程是内核线程,调度由内核负责,**同样陷入内核做上下文切换**。线程轻 ≠ 不进入内核,而是**切换时地址空间不变、不用换页表,省掉换页表 + TLB 冲刷**。说"全程用户态"的是**协程/用户态线程**的特征,别和普通线程搞混。
	- **硬伤 2**:通信简单是共享地址空间的便利,不是线程"轻"的原因;"轻"指创建和切换开销低,两个维度别搅一起。
	- 补精确:两线程不共享栈,共享堆、代码段、全局/静态数据、fd 表、信号处理等;各自独占栈、寄存器上下文、TLS。
- 备注:教材"状态转换=变态"是正规术语,此词无误(指状态变换)。

#### 4. TCP 三次握手(四题中答得最深入)

- 答对核心:**历史连接**问题——旧 SYN 迟到,两次握手会让服务端建立无效连接;三次握手让客户端能回 RST 拒绝。
- 需补,三点合一才是满配:
  1. 历史连接:服务端资源被一个永远等不到确认的无效半开连接占住(不是"白白发数据",是资源占用)。
  2. 双向通信确认:三次让两端都确认收发通;两次只确认了客户端→服务端方向。
  3. 资源浪费早回收:第三次握手让服务端有机会及早回收无效连接资源。

### 三、Redis 持久化专项(RDB / AOF 完整口径)

**主线问题表现**:只答了结论层,且有两处表述问题,需按以下口径重答(30 秒版)。

**主答案结构**
- RDB = **内存快照**:fork 出一致时刻的二进制快照,不是"可能不完整",而是**保存粒度**——按规则/手动触发才存,两次快照之间的写命令会丢。
- AOF = **命令追加日志** + fsync 频率可配(每秒/每次写/交给 OS)。
- **都开启时重启优先 AOF**,因为 AOF 数据更接近崩溃点(Redis 4.0 后混合持久化:文件头 RDB + 增量命令,先快载 RDB 再重放增量)。

**三个追问的满分口径**(本轮现场已能答对结论,补细节):
1. **RDB + fork / COW**:子进程写 fork 时刻的一致快照,父进程改页触发 COW、在副本上改 → RDB 不含 fork 后新写入;代价 = 快照期间写入越多、复制页越多、内存峰值越高;被跳过的写由下次 RDB / AOF 兜住。
2. **AOF 重写(必须补 rewrite buffer)**:重写期间父进程仍把新命令**追加进旧 AOF**,同时缓存到内存 **rewrite buffer**;子进程写完新文件后,父进程把 buffer 补到新文件末尾,再 **rename 原子替换** → 零丢窗口。
3. **主从全量同步走 RDB**:即使未开启 RDB 持久化,全量同步也走 RDB(二进制直接载入快、压缩省传输);之后靠 **replication backlog** 补增量;Redis 7 支持 diskless(无盘)复制直接流式发送不落盘。

**答题行为提醒**:面试中不要主动说"项目里只是简单用了 Redis"——会引导面试官按最低水平考。可改口径为"项目中用到的是 Redis 的基础能力",再主动讲深度,让面试官来探。

| "UDP 带来数据丢失问题" | 因果反了。UDP 不是"因为不握手所以丢包",而是**不承诺可靠**(不重传/不保序/不保送达)。漏了 **UDP 无流量控制**,可能打爆接收方缓冲区 |
| 首部开销只说"较大/较小" | 必须给数字:**TCP 最小 20 字节,UDP 固定 8 字节** |
| 只说 TCP 的好处,没讲代价 | 补:三次握手多 1 个 RTT、慢启动爬坡、**TCP 层队头阻塞** —— 这正是 HTTP/3 换 QUIC 的动机 |
| 项目侧缺"场景优先级" | 核心口径:**文件上传 正确性 > 时延**(宁可慢不能错一字节);实时音视频 时延 > 正确性。场景优先级决定传输层选择 |

**追问一 · 流量控制 vs 拥塞控制(满分)**

答对:流量控制由**接收端**发 rwnd,防压垮接收方;拥塞控制由**发送端**维护 cwnd,防压垮链路;发送窗口 = **min(cwnd, rwnd)**。

**追问一 · 慢启动(答偏,重点纠错)**

- 原答:"100 MiB 时指数提升导致的传输内容增加是显著的" —— **错**。慢启动是**几何增长,代价对传输大小取对数**:10 MiB ≈ 7180 MSS ≈ **11 个 RTT** 爬完,100 MiB ≈ 71800 MSS ≈ **13 个 RTT**,只多约 **2 个 RTT**。规模翻十倍只多几个 RTT。
- 大分片真正变糟的原因(用户答对第 2 条):①丢包恢复的绝对代价;②**应用层重传粒度**(一次分片失败=重传整个分片);③内存与超时窗口(服务端暂存 + `client_max_body_size`);④用户可见性(进度清零)。
- **"10 MiB 是性能甜点"是断言不是结论**,项目无压测数据,一句"怎么测出来的"就击穿。安全口径:受 `client_max_body_size 12m` 约束、给 multipart 元数据留余量;更大则增大重传代价与内存,更小则增加请求数与合并开销;**未做对照压测,当前取值是工程折中**。

**追问二 · keep-alive(方向对,缺机理)**

- 缺的关键半句:复用连接的核心价值是**保留 cwnd / ssthresh / RTT 估计**,后续分片直接在已探测好的窗口上跑,而不只是"省一次三次握手"。省握手只是省建连延迟,量级不同。
- "很吃服务器性能"表述不准。真开销:服务端**连接状态内存**、**TIME_WAIT 堆积**、弱网下**重复慢启动**。CPU 昂贵的是 **TLS 非对称运算** —— 项目是 HTTPS 入口,每分片新建连接会同时付出 TCP 与 TLS 两层代价。
- **事实核查**:`docker/nginx_fastdfs/nginx.conf:12` 有 `keepalive_timeout 65`(**客户端侧**);**无 `upstream` 块**,13 条路由全是 `fastcgi_pass` 直连(第 70~280 行)。Nginx→FastCGI 默认非长连接。

#### 第 2 题 · 三次握手(本轮最好的一题)

**答对**:完整报文顺序与状态迁移;`listen` 后握手由**内核自主完成**,业务层 `accept` 取的是**全连接队列**里已建好的连接 —— 正是多数人栽的地方;两队列分工正确。

**失分点**:

1. **事实错误:"客户端也要 bind"**。典型客户端只有 `socket()` + `connect()`,**内核在 connect 时隐式 bind**,从 ephemeral port 范围挑一个。显式 bind 仅用于固定源端口/多网卡选出口。
2. **三条理由里第 1 条和第 3 条重复**(历史连接、重复 SYN 建冗余连接,本质都是"防无效连接占资源"),**用户自己也说破了** —— 用数量凑答案会扣分。干净三条应为:①**双向确认收发能力**(最本质,两次握手只验证了客户端→服务端方向);②**同步双方 ISN**;③防止历史连接与重复 SYN 造成资源浪费(合并)。
3. 漏**"为什么不是四次"** —— 服务端把 SYN 与 ACK **合并成 SYN-ACK**,四次压成三次。
4. 漏**半连接队列的超时回收**(SYN-RCVD 下 SYN-ACK 重传次数由 `tcp_syn_retries` 决定,耗尽即丢弃),导致"资源被占住多久"答不出具体值。

**追问 · 队列溢出 / SYN Flood(答得很好,含查证补充)**

- 答对:**`tcp_abort_on_overflow` 两种行为**(=0 丢弃 ACK 等待,=1 回 RST);**syncookies 两种模式**(仅半连接队列满时启用 / 始终启用,对应内核参数 1 与 2);cookie 放在 SYN-ACK 的 **seq** 里。
- 修正:`syn-recv` → **`SYN-RCVD`**。
- 修正(全连接队列满的完整链条):服务端收到第三次 ACK 时**先试图入队**,放不下时**默认丢弃该 ACK**,服务端仍认为连接在 SYN-RCVD,随后**重传 SYN-ACK**;客户端收到重复 SYN-ACK 再回 ACK,如此往复。**客户端全程自认为 ESTABLISHED,`connect()` 正常返回 —— 它根本不知道服务端没接受**,直到第一次写数据才超时。
  > 记忆:**半连接队列满 = 第二步就断,客户端 connect 就失败;全连接队列满 = 握手"看起来"完成,connect 成功但请求石沉大海。**
- 修正(syncookies 的本质):不是"不进队列",而是**不保存任何状态**。cookie = 对(源 IP、源端口、目的 IP、目的端口、时间戳、MSS)做 **HMAC**,信息全部编码进 seq;ACK 回来时用同样输入重算校验。**不存状态 = 无状态 = 洪水打不爆内存** —— 这句才是核心。
- **项目事实核查**:`docker/fastcgi_app/start.sh` 用 `spawn-fcgi` 启了 13 个端口(10000~10012),**未加 `-C` 参数 = 每端口仅 1 个进程串行处理请求**(默认 backlog 1024)。**这才是项目真正的并发瓶颈,比 backlog 严重得多** —— 面试被问"能扛多少并发"时的硬伤:不是 Nginx 扛不住,是后端每条路由只有一个人干活。

#### 第 3 题 · 四次挥手

**答对**:报文顺序与状态迁移完整,**状态名全对**;2MSL 的"保对方收到 ACK"这一条答对。比记录 02 那轮进步明显。

**失分点**:

1. **漏掉 2MSL 的第二个理由(常被追问的那个)**:让**本次连接滞留在网络中的旧报文段自然消亡**。否则立刻用**相同四元组**建新连接,迟到旧报文会被新连接误收,造成数据错乱。**推导:MSL 是报文段最大存活时间,一来一回 2 个 MSL** 才能保证旧报文或到达或消亡。**两个理由缺一不可**。
2. "2MSL 的 TIME_WAIT 可以实现 ACK 的重传" —— 不准。TIME_WAIT **本身不主动重传 ACK**,而是**保留 TCB**,使被动方重传 FIN 时还能再回一次 ACK。
3. MSL 要给数字:**Linux MSL = 30s,2MSL = 60s**(即 Linux 上 TIME_WAIT 实际持续时间)。
4. "短连接时更容易合并" —— **归因错**。能否合并取决于**被动方收到 FIN 时自己还有没有数据要发 + 应用是否立刻 close**;与长短连接无直接因果。
5. 漏 **CLOSING 状态**(同时关闭时双方各进 CLOSING 而非 FIN_WAIT_2,最后都进 TIME_WAIT)。用户当场指出"教材四次挥手模型没体现这个状态" —— 反驳有理,但 `ss`/`netstat` 真会看到,是可用的诊断信号。
6. 补两个实践坑:**FIN_WAIT_2 卡死**(被动方迟迟不 close,由 `tcp_fin_timeout` 默认 60s 兜底);**CLOSE_WAIT 堆积 = 应用 bug / fd 泄漏**(收到 FIN 却没调 close),**比 TIME_WAIT 危险得多** —— TIME_WAIT 内核自动回收,CLOSE_WAIT 应用不管就永不回收。

**追问 · TIME_WAIT 危害与归属**

- **答对一半,漏了"消耗的是什么"**:

  | 主动关闭方 | TIME_WAIT 消耗 | 后果 |
  | --- | --- | --- |
  | 客户端 | **临时端口**(32768–60999,约 2.8 万个) | 同目标连接打满端口池 → `Cannot assign requested address`,**连不出去** |
  | 服务端 | **内核 TCB 内存**(每条约几百字节),**不占端口** | 固定监听端口不受影响,四元组不同仍可建新连接 |

  → **服务端的 TIME_WAIT 几乎无害**(几万条 × 几百字节 = 几 MB)。用户"对性能没有太大影响"这句是对的,但必须能说出**为什么**(不阻塞端口,只占少量内核内存)。
- 三个服务端 TIME_WAIT 场景答对:**短连接**、**`keepalive_timeout` 超时**、**`keepalive_requests` 达上限**。补排查口径:先看是不是 Nginx 主动关了 upstream 连接,而不是急着改内核参数。
- **项目归属那问,结论不认同**。"nginx 是反向代理 ⇒ fastcgi 关闭连接" —— **因果不成立**,谁主动关闭取决于**配置**。配置里**无 `fastcgi_keep_conn`(默认 off)** ⇒ **Nginx 每请求新建连接、收到响应后由 Nginx 关闭** ⇒ 默认堆在 **Nginx 侧**。
  > **正确做法是实测,不是背结论**:
  > ```bash
  > ss -tan state time-wait | wc -l   # 分别在 nginx 容器与 fastcgi 容器执行
  > ```
  > 哪边多,哪边就是主动关闭方。面试可答"我实测过,堆在哪一侧"。
- 漏了一段连接:**Nginx → FastDFS Tracker/Storage**,关闭方同样要看谁主动。

**追问 · SO_REUSEADDR / tcp_tw_reuse(用户答"不了解",已补讲)**

两者**作用层次完全不同**:

| | `SO_REUSEADDR` | `tcp_tw_reuse` |
| --- | --- | --- |
| 层次 | **应用层 socket 选项**(`bind` 前设置) | **内核参数**(`sysctl`) |
| 解决 | 服务重启 `bind()` 报 `Address already in use` | **客户端临时端口耗尽** |
| 范围 | 服务端复用**自己那个监听端口** | 仅**出站连接**,需 `tcp_timestamps` 配合 |
| 不解决 | 端口耗尽 | 服务端 bind 冲突 |

一句话:**`SO_REUSEADDR` 管"我能不能绑这个端口"(服务端),`tcp_tw_reuse` 管"我能不能拿旧连接去连别人"(客户端)。**
另需区分 `SO_REUSEPORT`(多 socket 绑同端口做内核级负载均衡,Nginx 多 worker 抢 accept)。
**避坑**:`tcp_tw_recycle` 已在 Linux 4.12 **被移除**,NAT 环境下会大量丢连接,提它反而暴露知识陈旧。

#### 第 4 题 · TCP 如何保证可靠性

**答对**:六个方向全部点到(序号+ACK、校验和、超时重传、拥塞控制、流量控制、连接管理),无漏项;校验和"只做损坏校验,不保证数据正确性"这句准确;"RTO 不固定是因为网络状态波动"这一概念层答对。

**失分点**:

1. **术语硬伤:全程说"数据报"**。TCP 的传输单位是**报文段(segment)**;"数据报(datagram)"是 UDP 术语,指独立有边界的传输单元。用户上一轮刚讲过"TCP 是流式传输、无边界",此处**自相矛盾**。
2. **漏核心机制:累计确认(cumulative ACK)**。ACK 序号 n 表示 **"n 之前的所有字节都已收到"** ,而非"第 n 个字节收到了"。**累计确认才是 TCP 高效的原因**——丢一个 ACK 报文不出问题,后面的 ACK 会覆盖它。这也是 TCP 只需一个 32 位确认号、而非给每个包维护确认位的原因。
3. **"确认到该包才移动窗口"表述模糊**。发送窗口滑动的依据是**对方通告的确认号**,不是"逐包确认";且**滑动窗口属流量控制**,用户把它归进了"序号+ACK"项,位置不对。
4. 快速重传归入拥塞控制位置对,但未解释触发机理:**收到 3 个重复 ACK**(说明后面有段丢了但网络没完全堵死,于是不等超时直接重传)。
5. 校验和"偏弱"结论对、**原因未答**。弱在三点:①只有 16 位反码求和,检错能力有限;②**只覆盖 TCP 首部+数据,不覆盖 IP 首部**;③**默认假设链路层(以太网 CRC)已挡住大部分错误**,自己不追求强检错。端到端强校验要靠应用层——**这正是项目里要客户端算 MD5 的原因**。

**RTO 计算(用户答"学过但记不清",并反问"业务程序员不会关心 RTO 计算吧")**:

> **教练承认此题超纲**,属网络岗/社招深度。但"RTO 是自适应的、不是固定值"这一**概念层**是校招常见追问,用户已答对,**本题不算失分**。

- 备忘公式:`SRTT = (1-α)·SRTT + α·SampleRTT` (α=1/8) → `RTTVAR = (1-β)·RTTVAR + β·|SRTT - SampleRTT|` (β=1/4) → `RTO = SRTT + 4·RTTVAR`
- 三个设计意图:①指数加权平均抹掉单次采样抖动;②**加方差项**应对网络"忽快忽慢"(方差大 → RTO 大);③系数 4 为工程经验值。
- 配套规则:**Karn 算法**——重传过的报文段不用其 ACK 采样 RTT,否则分不清确认的是首次发送还是重传;RTT 采错会让 RTO 越算越偏。**退避**——超时后 RTO 翻倍,Linux 最小约 200ms、最大 120s。
- 为何不能固定:取小 → 网络抖动时误判丢包、疯狂重传、把网络压得更堵;取大 → 丢包恢复慢、吞吐掉。

#### 第 5 题 · 滑动窗口与拥塞窗口

**核心概念混淆**:用户答"滑动窗口一般认为是发送方的发送窗口,取值为 `min(cwnd, rwnd)`"。

- **滑动窗口是一套机制的名字,两端各有一个窗口**:接收窗口 `rwnd`(接收方维护,我还能接多少)、发送窗口(发送方维护,我最多能发多少未确认字节)。
- **`min(cwnd, rwnd)` 算出来的是"发送窗口",不是"滑动窗口"**。把一个机制名当成一个数值,等于没分清层次。

**归因反复摇摆(本轮最值得警惕的一条)**:用户把 `rwnd` 说成"用于避免网络拥塞",而**上一轮刚答对过**"流量控制防压垮接收方、拥塞控制防压垮链路"。同一知识点在两轮之间反向,说明记的是**两句独立的话,还没形成因果链**。

> **固定口径:滑动窗口看对方还剩多少内存,拥塞窗口看网络还能塞多少,谁也管不着对方的事。**

**rwnd 公式要精确**:`rwnd = RcvBuffer - (LastByteRcvd - LastByteRead)`

关键在于 **"已占用"指的是"已被接收、但还没被应用层 read 走"的数据**,不是"没收到"。这解释了**应用层读取慢会拖垮 TCP 吞吐**:app 不 read → 缓冲区填满 → `rwnd` 归零 → 发送方被迫停。这是"应用层代码写得慢导致网络慢"的完整机理。

**零窗口场景答得好**(持续计时器、探测包、指数退避全部答对),两处需修:

1. **TCP 不会因零窗口强制断开连接**。persist timer 会一直探测,间隔指数退避后**封顶在约 60 秒**(`TCP_RTO_MAX`),之后以固定间隔永远探测,连接**可以无限期挂着**。唯一可能清理它的是 `TCP keepalive`,而它**默认 2 小时**才发第一个探测。
2. **persist timer 真正要解决的场景不是"发送方干等"**,而是:**接收方窗口更新报文丢失** → 发送方不知道可以继续发,接收方等着收数据,**双方互等真死锁**。它的本质是**不让"窗口更新"这个通知成为单点**。

**Silly Window Syndrome(糊涂窗口综合症)**:

- 用户定性正确:接收方缓冲区刚腾出几个字节就通告小窗口,或发送方每次只 write 几个字节,都会导致网络中充斥大量小报文段。
- **接收方一侧 → Clark 算法**;**发送方一侧 → Nagle 算法**。
- **Nagle 判据修正**:用户答"窗口大小 >= MSS 且数据大小 >= MSS"有误。**Nagle 完全不看窗口大小**,规则是:①要发的数据 >= 1 MSS → 立即发;②没有未确认的小段在途 → 立即发;③有未确认小段在途 → 缓存,等 ACK 回来或攒够 MSS 再发。**判据是"在途未确认",不是"窗口大小"。** Nagle 管的是**发送方自己的行为节流**,与接收方通告多少窗口无关。
- **延迟 ACK 不是永久死锁**:Linux 策略是"收到 2 个报文段,或等约 40ms"就发 ACK。Nagle + 延迟 ACK 的实际后果**是每轮多约 40ms**,不是卡死;但这在高频小交互场景(游戏、实时通信)下是灾难性的。解法:`TCP_NODELAY` 关掉 Nagle。
- **项目相关**:Nginx 默认开启 `tcp_nodelay`(http 块默认 on),**Nginx 已经替项目填了 Nagle 这个坑**,面试可主动说。

**项目那问满分**:应用读得慢 → 缓冲区堆积 → `rwnd` 收缩 → 发送窗口收缩 → 客户端降速。**完整因果链,把"应用层拖慢网络"和 rwnd 串起来了**。延伸:大文件上传应**边读边写(流式)**,不要把整个 body 读进内存再处理——分片链路"读一部分写一部分"的设计恰好是对的,app 持续 read 则 `rwnd` 不归零;**若改成"先全读进内存再处理",吞吐会掉**。

> **[教练纠错有误 · 已更正]** Clark 算法阈值一条,教练原写"`min(MSS, Buffer/2)` 方向反了,应取大者",并称用户原文有误。**实为用户正确,教练自相矛盾**(同一段里既写 `min` 又说"取大者",所举数值算例也与结论不符)。**RFC 1122 规定:接收方在可用空间达到 `min(MSS, RcvBuffer/2)` 之前通告窗口为 0**,取**较小**者即更早解锁。**以用户原写法为准。** 用户当场指出"你在左右脑互搏"——反应准确。

#### 第 6 题 · 拥塞控制四阶段

**主线全对**,Tahoe/Reno 数值推演(cwnd=1、ssthresh=8、减半、+3)算得准,能完整走完状态机。

**硬伤 1:TCP 没有"每个包一个重传定时器"** —— 这是典型误区。

> **每条 TCP 连接只有一个重传定时器。** 若每个在途报文段都挂一个定时器,几十万个定时器的维护成本无法接受。
> 真实做法:定时器**只盯最老的那个未被确认报文段**;该段被 ACK 覆盖后,定时器**移到新的最老未确认段**并用新 RTO 重设;超时则重传最老段 + **RTO 翻倍退避**。

**这个机制解释了**:为什么 TCP 重传是"从最老的段开始补"而不是"哪个丢了传哪个"——**它根本不知道哪个丢了**。也正因此,**快速重传靠 3 个重复 ACK 定位丢包,比干等超时精准得多**。

**硬伤 2:快速恢复结束时 `ssthresh` 不"还原"**。用户答"将 ssthresh 还原到原始的 ssthresh"——**无此动作**。NewReno 收到确认新数据的 ACK 时只做 `cwnd = ssthresh` 然后进拥塞避免;`ssthresh` 在进入快速重传时已改为 `cwnd/2` 并**保持不变**。**减半是永久性的**:网络刚刚证明扛不住原来的窗口,这个信息要被记住。

|         | ssthresh         | cwnd                                | 之后             |
| ------- | ---------------- | ----------------------------------- | -------------- |
| 快速重传/恢复 | `cwnd/2`(**保持**) | `ssthresh+3` → 新 ACK 后 `= ssthresh` | 拥塞避免(线性增长)     |
| 超时重传    | `cwnd/2`(**保持**) | `= 1`(现代 Linux `= 10`)              | **慢启动**(重新指数爬) |

**漏答:慢启动的两个结束条件只给了一个**。

```
① cwnd >= ssthresh           → 进入拥塞避免(正常出口)
② 检测到拥塞(超时/3个重复ACK) → 进入丢包恢复(异常出口)
```

漏掉原因:把"慢启动"与"拥塞发生后"当成两个独立阶段,**没意识到慢启动会被中途打断**。教材图里慢启动总是平滑爬到 ssthresh 就转弯,**但真实网络里慢启动多数时候是被丢包打断的**——指数增长太猛,还没爬到 ssthresh 就把网络打爆了。

**精度问题:拥塞避免是"每 RTT +1 MSS",不是"每次发送 +1"**。后者会算成按包线性增长,远比实际快。实现上每收到一个 ACK 加 `SMSS*SMSS/cwnd`,攒够一个 RTT 正好 +1 MSS。**"指数转线性"的拐点就是 ssthresh 的全部意义**——它是"上次出事窗口的一半",代表网络能承受的估计上限,到了就该踩刹车。

**Linux cwnd 初始值**(用户答"没了解过",已补):教材 = 1 MSS;RFC 5681 = 2~4 MSS;**RFC 6928 / 现代 Linux = 10 MSS**(2.6.39 起)。**提到 10 的理由**:cwnd=1 时慢启动起步太慢,**短连接(如一个 HTTP 请求)在连接结束前根本爬不到有效带宽**,大部分时间浪费在爬坡。**这条直接对应项目**——短连接为主的 HTTP 上传正是 initcwnd 提高的受益场景。

**现代语境:Linux 默认拥塞算法是 CUBIC,不是 Reno**。Reno 线性增长、前提是"丢包 = 拥塞";CUBIC 用**三次函数**(先快后慢),认为**丢包 ≠ 必然拥塞**(高带宽长肥管道里丢包常是缓存溢出),减半后**快速爬回上次窗口附近再放缓**。这正好回应了第 1 题里"丢包不一定是网络堵了"的点。

> 用户要求记录:**"经典模型没处理丢包"** —— 教材 Reno 图是理想化的平滑曲线,真实慢启动多被丢包打断。

#### 第 7 题 · 粘包与业务分片乱序

**前两问答得完整**:

- 粘包定性正确:**是 TCP 的特性(字节流无边界),不是 bug**。
- 三种划界方式答对并各自说了优劣:**固定长度**(方便解析,不够灵活,无法处理变长数据)/ **特殊标识符定界**(方便,但数据段中可能含该标识符导致状态机误定界)/ **定长头部 + 长度字段**(最常用)。
- HTTP 划界答对:头部用 `\r\n` 定界 + `Content-Length` 记录 body 长度。

**核心考点未答到:"TCP 有序 ≠ 业务有序"**。

用户答"TCP 保证字节流有序,但发送数据时可能出现**客户端乱序发送**的现象"——**不存在"客户端乱序发送"这回事**。客户端按 0、1、2 顺序调 `send`,TCP 就按这个顺序发,TCP 不会打乱你写的顺序。

| | TCP 的序号 | 业务的分片编号 |
| --- | --- | --- |
| 管什么 | **一条 TCP 连接内**的字节位置 | **多个 HTTP 请求之间**的业务位置 |
| 编号给谁看 | 内核(TCP 层自己维护) | **应用代码** |
| 谁保证顺序 | TCP 保证 | **没人保证,得自己管** |

**关键:分片 0 和分片 1 是两个独立的 HTTP 请求。**

- 客户端**并发**发(多条 TCP 连接)→ 两个请求是独立连接,**TCP 的序号根本管不着它们之间的关系**;
- 即使同一条连接(keep-alive)顺序发 → 服务端也**不一定顺序处理完**,请求 0 可能在等 MySQL/FastDFS,请求 1 已经处理完返回。

> **一句话:TCP 的序号是给内核用的,你的分片号是给应用用的,中间隔着一层 HTTP,TCP 的顺序性传不过来。**

**"按序落盘"的结论错了**:用户答"单线程顺序发送可以保证按序到达和落盘",混淆了两件事:

- **按序送达**——靠单线程 `await` 顺序发请求实现,是**发送逻辑**带来的,不是需求;
- **按序落盘**——分片 0 写 `/tmp/chunks/{md5}/0`、分片 1 写 `.../1`,**本来就是不同文件,谁先落盘根本不重要,因为互不覆盖**。

**所以"按序落盘"这个需求本身不存在**,用户回答了一个不需要保证的东西,而真正需要保证的"**所有分片到齐了才能合并**"没提。

**正确答案应是**:

> 分片乱序到达**本身无害**,因为每个分片写独立的临时文件路径,不会相互覆盖。真正要防的是**"合并时还有分片没到"**——靠 `/api/chunk_merge` 前检查所有编号的临时文件是否存在来兜底。
>
> 且这里有真实风险:**如果分片 0 请求失败但客户端重试、分片 1 已成功,服务端只知"1 存在、0 不存在",无法区分"0 还没上传"和"0 上传失败"**——因为当前代码不校验分片摘要、不校验大小(见记录 01 复核结论),**服务端无法发现分片内容是坏的**。

**追问 · 顺序约束与并发风险(用户答"没想过这么深",已补)**:

顺序发送**没有保证任何"顺序语义"**,它只是用一个更弱的并发模型,**绕开一堆同步问题**:

| | 顺序发送 | 并发发送 |
| --- | --- | --- |
| 分片路径互不覆盖 | ✔ | ✔(本来就写不同文件) |
| `uploaded` 字段更新 | 天然串行,不会丢更新 | **读-改-写竞态,会丢分片记录** |
| 合并时机判断 | 简单 | 需要锁 |
| 服务端压力 | 平缓 | 8 个分片同时进,内存/连接暴涨 |
| 上传速度 | **慢**(付出的代价) | 取决于服务端 |

面试口径:"客户端顺序发送是我主动选择的取舍,主要为了避开服务端 `uploaded` 字段的竞态和合并流程的并发问题。分片本身写独立临时文件,乱序到达不会互相覆盖,所以顺序性不是正确性要求。代价是上传速度受限于单请求往返。"

**改成并发发 8 片会炸在三处**:

1. **`uploaded` 字段丢更新(必现)**:Redis 里 `uploaded` 是逗号字符串,更新方式是"读出来 → 拼编号 → 写回去"。
   ```
   请求A: GET uploaded → "0" → 拼接 → SET "0,1"
   请求B: GET uploaded → "0" → 拼接 → SET "0,2"     ← A 的 "1" 被覆盖
   ```
   两请求几乎同时读,**谁后写谁赢,另一个的编号永久丢失**。结果:分片其实上传成功,但服务端记录里没有,合并时被判"分片缺失"。**修法**:改用 Redis **Set**(`SADD` 天然原子且去重,最小改动),或 `HINCRBY` 计数,或 Lua 脚本保证读改写原子。
2. **`/api/chunk_merge` 无锁 + 边追加边删片**:若客户端在最后一片发完就调 merge,可能有的分片请求仍在处理中,merge 检查存在性会漏判;且一旦中途失败,**已删的分片补不回来**。
3. **并发在当前架构下没有收益**:`spawn-fcgi` 未加 `-C`,**每端口只有 1 个进程串行 accept**,8 个并发请求只能排队。
   > **因果链(面试可讲)**:单进程 → 并发没收益 → 所以顺序发送没暴露问题 → 一旦加多进程提速 → 竞态立刻爆。**能说出这条链就是"真懂项目"的证明。**

**HTTP 并发连接数(用户答对,补两点)**:

- 用户答对:HTTP/1.1 不支持单连接并发,8 个请求需 8 条 TCP 连接;**HTTP/2 支持多路复用,并发请求成为同一连接上的 8 个 stream,支持交错发送和乱序返回,但传输层仍为 TCP,仍存在丢包导致的队头阻塞**。
- 补 ①:**浏览器实际禁用 HTTP/1.1 pipelining**,改用**每域名 6~8 条并行连接**,所以 8 个分片大概率是 6~8 条连接(排队调度),不是严格 8 条。
- 补 ②:**HTTP/2 的队头阻塞可能比 HTTP/1.1 更糟**。

  | | 丢包时的影响 |
  | --- | --- |
  | HTTP/1.1(多连接) | 只影响**那一条**连接上的请求,其他连接照跑 |
  | HTTP/2(单连接多路复用) | **所有 stream 共用一个 TCP,任何丢包,全部 stream 一起等** |

  HTTP/2 是用"多连接的并行"换"单连接的复用",代价是队头阻塞从"一条连接"放大到"全部请求"。**这正是 HTTP/3 换 QUIC 的直接动机**——QUIC 在 UDP 上实现**流级别的独立重传**,丢包只阻塞那一个 stream。

#### 第 8 题 · Socket API 完整流程

**答对**:`socket → bind → listen → accept` 顺序完整;握手在 `listen` 与 `accept` 之间由内核完成;`accept()` 拿到的是全连接队列里已建立好的连接;**上轮"客户端也要 bind"的错误本轮未再犯**。

**关键错误:第 1 问把"数据丢失"说反了(重点)**。

用户答"服务端可能还没 accept,数据会直接丢失"——**错,而且是反的**。

```
客户端 connect() 返回 → 握手完成 → 连接进入服务端全连接队列
客户端 send()        → 数据到达服务端内核
                     → 内核把数据放进【这条连接的接收缓冲区】
服务端调 accept()    → 拿到 fd
服务端 read(fd)      → 从缓冲区读出数据
```

> **TCP 连接的建立和数据接收全部由内核完成,跟应用层有没有 `accept()` 毫无关系。** `accept()` 只是从全连接队列里取出已建好的连接、返回一个 fd。**数据一直在内核缓冲区里等着,直到应用层 `read`。**
> 真正会丢数据的情况:缓冲区满、连接被 RST、超时——**跟 accept 没关系**。

**"这个行为在我的项目中体现为数据丢失"同样不成立**:

| 以为 | 实际 |
| --- | --- |
| 数据丢了 | **数据都在内核缓冲区里,一条没丢** |
| 请求失败 | **请求在排队** |

`FCGI_Accept` 是**阻塞**的,所以请求 2、3 的连接和数据都在内核里好好的,只是进程还没空去 accept。**这是排队等待 + 延迟,不是数据丢失。**

**什么情况下才变成真失败**:①排队太久 → **Nginx `fastcgi_read_timeout` 超时**(默认 60s)→ 断开并返回 504;②**全连接队列满** → `tcp_abort_on_overflow` 行为触发。

> **正确口径:单进程串行导致的不是数据丢失,是请求排队、延迟堆积,严重时触发 Nginx 504。** 面试中不能说"数据会丢失"——代价比"不知道"大。

**两个 fd 的区别(答对要点)**:

| | `listen_fd` | `accept()` 返回的 `conn_fd` |
| --- | --- | --- |
| 状态 | **LISTEN** | **ESTABLISHED** |
| 四元组 | 只有本地地址,**无对端** | **有完整四元组** |
| 收发缓冲 | **无** | **有独立的收发缓冲区**(各占内核内存) |
| 能 send/recv 吗 | **不能**,返回 `ENOTCONN` | 能 |
| 生命周期 | **一直有效**,可反复 accept | 对应**一条**连接,用完 close |
| 数量 | 每个监听端口 1 个 | **每条连接 1 个** |

**每个 `conn_fd` 都占内核内存**(socket 结构 + 收发缓冲区)。这就是高并发服务器要控制连接数、设置 `SO_RCVBUF` 的原因——**一万条空闲连接吃掉几十上百 MB 内核内存,且用户态 `free` 不了**。

**错误:主客体颠倒**。用户写"最后,**客户端**通过 `close(listen_fd)` 关闭监听 socket"——**客户端没有 `listen_fd`**,客户端不调 `listen()`。

```c
// 服务端
close(listen_fd);   // 关闭监听,不再接受新连接(已有连接不受影响)
close(conn_fd);     // 关闭某条具体连接
// 客户端(只有这一个)
close(conn_fd);
```

**两个 `close` 语义完全不同**:关 `listen_fd` 是"停止营业",已建立的连接照常工作;关 `conn_fd` 才是断开某条连接。

**漏掉的实务细节**:

1. **`listen()` 的本质作用**:把 socket 从 CLOSED 转入 **LISTEN 状态**,内核从这里才开始响应 SYN。`listen()` 之前即使端口已 bind,内核收到 SYN 也**不会建立半连接**——对端会超时或收到 RST。
2. **`accept()` 的阻塞语义**:全连接队列为空时默认阻塞(除非设为非阻塞或用 `epoll` 监听 listen_fd 可读)。这是高性能服务器用 **Reactor + epoll** 的原因——把 `listen_fd` 注册进 epoll,有连接才调 `accept`,不空转。**Nginx 就是这套模型**,可直接连到题单第八节的 Nginx 题。
3. **新 fd 的端口号(真正的盲区)**:新 fd 的**本地端口就是监听端口本身**(如 443),**不是新分配的端口**。内核靠**四元组**(源 IP、源端口、目的 IP、目的端口)区分不同连接。**这解释了为什么服务端的 TIME_WAIT 不阻塞端口**——服务端本来就不靠端口区分连接。
4. **`shutdown()` vs `close()`**:

   | | `close(fd)` | `shutdown(fd, how)` |
   | --- | --- | --- |
   | 作用对象 | **fd 引用计数**(多个 fd 指向同一 socket 时才真正关闭) | **连接本身**,立刻生效 |
   | 能否半关 | 不能 | **能**:`SHUT_WR` 只关发送方向 |
   | 他人 fd | 有其他进程持有该 fd 时连接不断 | **不管谁持有,直接断** |

   **`shutdown(SHUT_WR)` 是优雅实现"半关闭"的标准手段**,也正是 `FIN_WAIT_2` 状态要怎么进入——主动方 `shutdown(SHUT_WR)` 发 FIN 进 FIN_WAIT_2,此后仍能收数据。**`close()` 做不到,因为它会连读方向一起断。**

**追问 2 · `SO_REUSEADDR`(用户答对)**:允许 `bind()` 一个**处于 TIME_WAIT 的本地地址**,让服务端重启时**不必等 2MSL** 就能绑回监听端口,避免 `Address already in use`。必须在 `bind()` **之前**设置——因为**检查是在 `bind()` 内部做的**,"入场前买票"。
> 边界:它**不是关闭 TIME_WAIT**,而是"允许 bind 一个处于 TIME_WAIT 的地址"。TIME_WAIT 该持续还是持续。且它**只管服务端自己的监听端口**,不解决客户端临时端口耗尽(那是 `tcp_tw_reuse`)。

**追问 3 · 项目的 IO 模型(查源码确认)**:

全部 13 个 CGI 源文件**无任何 `select`/`poll`/`epoll`/`O_NONBLOCK`**,统一是:

```c
while (FCGI_Accept() >= 0) {   // 阻塞等连接
    // 处理请求,处理完循环回去再阻塞等下一个
}
```

见 `src_cgi/chunk_upload_cgi.c:41`、`src_cgi/upload_cgi.c:1039`、`src_cgi/chunk_merge_cgi.c:478` 等 13 处。

| 维度 | 项目实际 |
| --- | --- |
| IO 模型 | **阻塞 IO** |
| 并发模型 | **单进程串行**(`spawn-fcgi` 无 `-C`) |
| 多路复用 | **没有** |
| 一个请求处理慢 | **后续请求全部排队**,进程阻塞在写 FastDFS 上 |

> **"能扛多少并发"的完整答案:每条路由只有一个进程、阻塞处理,真正的并发度是 1。** 第二个请求必须等第一个处理完。上传大文件分片时(写 FastDFS 最耗时),该端口的后续请求全部排队。
> **这不是 Nginx 的问题**——Nginx 用 epoll 能接住大量连接并转发,但后端每端口只有一个进程阻塞式接活。最小改动是 `spawn-fcgi -C 4` 起多进程。
> **接第 7 题**:一旦加 `-C 4`,`uploaded` 的读-改-写竞态**立刻会爆**。这两题在项目里是同一问题的两面。

#### 第 9 题 · HTTPS / TLS 全流程

**大框架答对**:非对称解决密钥分发、对称解决速度、非对称协商密钥后用对称传数据。用户自己分析的"每用户一个密钥、连接数上来密钥数量爆炸"是主动推导的,不是背的。

**硬伤:RSA 握手是"两个随机数 + 一个预主密钥",不是"三个随机数"**。

TLS 1.2 只有两个随机数:`client_random`(第一次握手明文发)、`server_random`(第二次握手明文发)。**第三个东西不叫随机数,叫 pre-master secret(预主密钥)**,而且**带结构**:

```
pre_master_secret = 客户端版本号(2字节) + 46字节随机数
```

**为什么要带版本号**:防**版本回退攻击**——中间人篡改协商版本降级到弱版本时,这个版本号会和服务端记录的版本对不上,双方算出的密钥不同,握手失败。

```
master_secret = PRF(pre_master_secret, "master secret", client_random + server_random)
会话密钥       = PRF(master_secret, "key expansion", server_random + client_random)
```

**为什么要掺两个随机数**:光有 pre_master 不够,**掺入双方各自生成的随机数保证每次连接的密钥都不同**——即使 pre_master 被猜到,没有这两个随机数也推不出会话密钥。

**表述不准 1:第三个握手的核心机制被模糊掉了**。用户写"加密报文,向服务器发送随机数"。**正确的关键句是**:

> **客户端从证书中取出服务器公钥,用它加密 pre_master_secret 后发出去。**

**整个 RSA 密钥交换的命门就在这一句**:只有**持有服务端私钥的人**能解开这个 pre_master;中间人截获也没用。**这就是"非对称加密协商密钥"的具体实现**——不是泛泛的"用非对称加密",而是**恰好用它传了那 48 字节**。

**表述不准 2:"客户端表明不支持加密则回退到 HTTP"** —— 错。

- 正确逻辑:客户端在 ClientHello 列出**自己支持的一串** cipher suites,服务端**从中挑一个**;**一个都没有交集**才协商失败、连接中断。
- **不是"回退到 HTTP"**。端口都不同(443 vs 80),**TLS 握手失败就是直接断开**,浏览器报错,不会自动降级。**"回退到 HTTP"这个说法最容易让面试官皱眉**,因为它让人联想到降级攻击,而 TLS 恰恰是防降级的。

**哈希在 TLS 里的三个用途(用户答"不清楚",已补)**:

1. **完整性校验(HMAC)—— 防篡改**。记录层每个数据包带 `MAC = HMAC(密钥, 序号 + 记录头 + 数据)`。
   > **为什么需要**:对称加密只保证**机密性**(别人看不懂),**不保证完整性**(别人可以乱改密文;解出来是乱码,但接收方分不清是"被改了"还是"传坏了")。**HMAC 补上这个洞**。**关键区分:加密 ≠ 防篡改,这两件事必须由两个机制分别完成。**
2. **证书签名验证 —— 防伪造**。`签名 = CA 用【CA 私钥】对(证书内容做哈希)的结果`;验证时把证书内容哈希一遍,再用 **CA 公钥**(内置在系统里)解密签名,两边比对。
   > **哈希在此的作用**:把任意长度的证书内容压成定长摘要再签。**为什么不直接对内容签名**——非对称运算很慢,签短摘要快得多。
3. **Finished 报文 —— 防握手被篡改**。`verify_data = PRF(master_secret, "finished", Hash(全部握手消息))`,把之前所有握手报文做哈希再算。任何一步被中间人改过,哈希值就变,校验失败。**这是防"中间人偷改密码套件降级"的最后一道闸。**

> **一句话收束:哈希在 TLS 里不负责"加密",它负责"确认东西没被动过"**——数据没被动过(HMAC)、证书没被伪造(签名)、握手过程没被篡改(Finished)。

**证书那一问答对主干(防中间人、攻击者无私钥),补两块**:

- **"验证证书是否合法"要展开成四条**:

  | 验证什么 | 防什么 |
  | --- | --- |
  | **证书链**能一路验到受信任的根 CA | 自签的假证书 |
  | **域名匹配**(`CN` / `SAN`) | 拿 `evil.com` 的证书冒充 `bank.com` |
  | **有效期**未过期 | 过期证书 / 重放旧证书 |
  | **吊销状态**(CRL / OCSP) | 私钥已泄露但证书未到期的场景 |

- **"只拿公钥、没有证书会怎样"——这才是第 3 问的真正答案**:

  > **没有证书,你拿到的公钥是谁的都无从确认。** 中间人可以把**自己的公钥**发给你,你用它加密 pre_master,他用自己私钥解开,再拿真服务器公钥重新加密转发给服务器——**全程双向透明转发,你完全察觉不到**。
  > **证书的作用不是"提供公钥",而是"证明这个公钥属于谁"。** 公钥谁都能生成,难的是让别人相信这个公钥对应的是 `bank.com`。
  > **公钥解决"加密给谁",证书解决"这个公钥是谁的"。两者缺一不可。**

**现代语境:生产环境早已不用 RSA 密钥交换**。

| | RSA 密钥交换 | (EC)DHE 密钥交换 |
| --- | --- | --- |
| 密钥怎么来 | 客户端生成 pre_master,用服务器公钥加密发过去 | **双方各自算,pre_master 从不在网上传** |
| **前向保密** | **没有** | **有** |
| TLS 1.3 | **已删除** | 唯一方式 |

> **"没有前向保密"的准确含义**:服务器私钥一旦泄露,攻击者可以**解密过去抓到的所有历史流量**——因为 pre_master 是用服务器公钥加密传的,存下流量后拿到私钥就能全部解开。
> **DHE 没这个问题**:pre_master 由双方临时生成的密钥算出来,**从没在网络上传输过**,每次连接用完即弃。即使长期私钥泄露,历史流量也解不开。
> **这就是 TLS 1.3 把 RSA 密钥交换整个删掉的原因——不是性能问题,是前向保密是必须的。**

#### 第 10 题 · DNS 与分层排查

**术语硬伤:递归和迭代说反了(必纠)**。用户写"一般客户端→本地 dns 服务器使用**迭代**查询,本地 dns 服务器发起的查询为**递归**查询"——**正好反了**。

| | 谁在干活 | 正确对应 |
| --- | --- | --- |
| **递归查询** | **被问的人替你去查,直到拿到最终答案** | **客户端 → 本地 DNS 服务器** |
| **迭代查询** | **只告诉你"下一个该问谁"** | **本地 DNS 服务器 → 根 / TLD / 权威** |

> **判断口诀:谁跑腿,谁递归。**
> 客户端对本地 DNS 说"你查清楚再告诉我" → 本地 DNS 全包了 → **递归**。
> 本地 DNS 问根"`baidu.com` 谁管?" 根说"问 `.com` 的去" → **根没替它查,只指路** → **迭代**。

**注意一个矛盾**:用户标签说反了,但**后面描述的流程反而是对的**(本地 DNS 找不到 → 找根 → 根返回 TLD → 再问权威 → 拿到 IP)。说明脑子里流程是通的,只是两个词的标签贴反了。**必须改对**——面试官听到"客户端用迭代"会认为概念没建立,而后续描述又证明会,反而显得背串了。

**DNS 缓存有 4 层,用户只提了本地 DNS 缓存**:

```
① 浏览器自身 DNS 缓存      (Chrome: chrome://net-internals/#dns)
② 操作系统缓存              (Windows: ipconfig /displaydns ｜ Linux: systemd-resolved)
③ hosts 文件                (优先级高于 DNS 查询!)
④ 本地 DNS 服务器缓存        (用户提到的这层)
   ↓ 都没有才走完整解析
```

**`hosts` 文件优先级很高**——"我改了 DNS 但没生效"经常是 hosts 里有一条旧记录。另外,**TTL 到了才过期**,这就是"域名解析改了但还访问到旧 IP"的原因。

**第 2 问 · ping 与 HTTP 的关系**:

用户答了"ICMP 被防火墙挡"和"HTTP 走了代理",都对,但**漏了最根本的那条**:

> **`ping` 根本不走 TCP,它测的东西和 HTTP 需要的东西基本不重叠。**

| | `ping` | HTTP(S) |
| --- | --- | --- |
| 协议 | **ICMP**(网络层) | TCP/UDP + HTTP |
| 要 DNS | 要 | 要 |
| 要 TCP 握手 | **不要** | **要**(443) |
| 要 TLS | 不要 | 要 |
| 要应用进程 | **不需要**,纯内核响应 | **需要**服务进程在监听 |

**ping 不通但 HTTP 通**(用户答 2 条,补 3 条):ICMP 被防火墙/安全组屏蔽(**最常见**);**CDN / 云负载均衡**——ping 到的是 CDN 边缘节点,它不回 ICMP 但 HTTP 正常;**HTTP 走了代理**;目标主机**禁用了 ICMP**(很多云主机默认策略)。

**ping 通但 HTTP 不通**(用户答 3 条,补 2 条):**端口没监听**(进程挂了/没起来/监听错端口);**TLS 证书问题**(过期、域名不匹配)——TCP 层完全正常;**应用层 5xx**;**中间设备只放行 ICMP 封了 80/443**;**DNS 解析到了错误 IP**(ping 的域名与 curl 的解析结果不同)。

> **面试可直接说的总结:`ping` 只能证明"网络层可达",证明不了"传输层端口开放",更证明不了"应用层进程正常"。这三层必须分别用不同工具测:`ping` 测链路,`telnet`/`nc` 测端口,`curl` 测应用。**

**第 3 问(用户未答,已补)**:`ping` 用 **ICMP 协议**,属**网络层**(与 IP 同层),**不是 TCP 也不是 UDP**。

> **本质区别:ICMP 是无连接的、由内核直接处理,不需要任何用户态进程参与。**
> `ping` 的回应由**目标主机内核**发出——**哪怕那台机器一个服务都没跑,只要系统活着、ICMP 放行,ping 就能通**;**HTTP 的回应必须由用户态 Web 进程发出**——进程挂了,ping 照样通。
> **这就是"ping 通不代表服务活着"的根本原因**(内核 vs 用户态)。

**第 4 问 · 排查框架(方向对,颗粒度不够)**:

用户答"用户端 → 链路 → 传输层 → 应用层"四步方向对,但**每层用什么命令验证只给了一半**。完整排查表:

| 层 | 查什么 | 命令 | 不通说明 |
| --- | --- | --- | --- |
| **① 本地** | 浏览器/网卡/代理 | `ipconfig` / `ifconfig`、关代理 | 本机网络问题 |
| **② DNS** | 域名能否解析 | `nslookup` / `dig` | DNS 挂了 → **`ping` 也会失败**(因为要解析) |
| **③ 链路** | 网络层可达 | `ping` / `traceroute` | 路由问题、ICMP 被封 |
| **④ 端口** | 传输层能否握手 | **`telnet IP 443`** / `nc -zv IP 443` | 端口没开 / 防火墙拦截 |
| **⑤ TLS** | 证书是否正常 | `curl -v https://...` / `curl -k` | 证书过期 / 域名不匹配 |
| **⑥ Nginx** | 能否返回 | `curl -I`、`nginx -t`、access.log | Nginx 挂了 / 配置错 |
| **⑦ FastCGI** | 后端能否响应 | error.log、`ss -tnp` 查 10000~10012 | **502** |
| **⑧ 存储** | FastDFS/MySQL/Redis | 查容器进程、`fdfs_monitor` | **500** |

**用户漏了 ⑤ TLS 层和 ⑦⑧ 后端层,而这两层恰恰是项目最容易出问题的**:

- **⑤ TLS 层**:项目是 HTTPS 入口(443),自签证书会被浏览器直接拦。**`curl -k` 跳过证书校验,能区分"是证书问题还是服务问题"**。
- **⑦⑧ 后端层**:这里有**项目专属的诊断捷径——看 HTTP 状态码就能定位到层**:

  > - **502 Bad Gateway** → Nginx 收到了请求但**连不上 FastCGI** → 后端进程挂了 / 端口没监听
  > - **504 Gateway Timeout** → Nginx 连上了但 **FastCGI 没在超时时间内响应** → **后端在处理但太慢**
  > - **500** → FastCGI 返回了但业务代码报错 → 查业务逻辑 / MySQL / FastDFS

  **接第 8 题**:504 在这套架构里最常见的原因,就是 `spawn-fcgi` **单进程串行**导致的排队——请求排在队列里等前面的处理完,超过 Nginx 的 `fastcgi_read_timeout`(默认 60s)就返回 504。
  **这三条串起来就是"网页打不开"的完整诊断树**——不是背的,是从架构推出来的。

### 四、可复用的答题原则(本轮提炼)

1. **指标/数字不能是断言**。凡说"性能甜点""提升明显""并发够用",必须能给出测量方式,否则改成"工程折中 + 未做对照压测"。
2. **别用数量凑理由**。三条里两条同源,等于只有两条,面试官会当场点破。宁可只说两条、把第二条讲深。
3. **背结论不如说实测**。谁主动关闭连接、TIME_WAIT 堆在哪一侧 —— 这类问题答案是 `ss` 命令的输出,不是推理。
4. **场景优先级先行**。回答"为什么选 X"时,先讲这个场景把什么排在第一位(正确性 / 时延 / 成本),再讲 X 怎么满足它。
5. **项目侧结论必须能落到代码或配置**。"反向代理所以对方关闭"这种从架构名词推导行为的说法,最容易被一句"你确认过配置吗"击穿。
6. **分层是通解**。TCP(内核有序)/ HTTP(请求独立)/ 业务(分片要自己管)三层各有各的"次序",混为一谈就答错;排查亦然——链路、端口、TLS、应用各用不同工具。
7. **内核与应用的分工要说清**。内核负责建连与收数据,应用负责 accept 与 read;**应用没去取,不等于数据丢了**。

#### 第 2 题 · 文件上传的完整链路

**答对**:链路顺序完整,且**主动讲到了 Redis 会话结构**(`chunk:{md5}` Hash 存文件名/大小/片数/用户/进度)、appender 文件、每片独立临时路径。这是"真跑过"才会有的细节,加分。

**需收紧**:

1. 开头"**前端**计算文件 md5"——被追问"为什么不是后端算"会很难答。真实原因是**省带宽**(后端算意味着文件已经传完了,秒传就没意义了)。要能说出这个动机。
2. "**异步串行**上传分片"——用词自相矛盾,且与第 8 题的"阻塞 IO 串行排队"直接冲突。**改口为"客户端顺序 `await` 逐片上传"**。
3. 只说了正常路径,没说**失败时怎么回滚**——这正好是第 11 题挖出来的洞。

#### 第 3 题 · 秒传接口的越权风险(本轮最大概念错)

**用户答**:"其他用户肯定能通过 **md5 碰撞**获取文件,所以加了 token 校验。"

**纠正(必须记牢)**:

| | MD5 碰撞 | MD5 枚举 / 越权领取 |
| --- | --- | --- |
| 是什么 | 两个**不同文件**算出**同一个 md5** | 攻击者**随便编一个 md5 字符串**去调秒传接口 |
| 难度 | 几百万核时,实际项目**不用考虑** | **零成本**,写个循环就能刷 |
| 是否本项目风险 | **否** | **是** |

> **真正的漏洞**:秒传接口在"md5 存在且用户未持有"时,直接**建立持有关系 + 引用计数 +1**。也就是说,该接口**不要求上传者真的拥有文件内容,只要求他知道 md5**。而 md5 不是秘密——任何下载过该文件的人都能本地算出。**token 校验完全挡不住,因为攻击者本来就是合法登录用户。**
>
> **本质**:把"文件存在性查询"和"授予访问权"两个语义缝进了同一个接口 —— 这是**授权模型问题,不是加密强度问题**。

**用户给的两个修复方向都不成立**(已当场掰正):

- "后端重算 md5" —— **攻击者根本没上传内容,你拿什么重算?**
- "用非对称加密做文件指纹" —— 指纹必须能从文件内容**确定性导出**,任何持有文件的用户都能算出来,**换什么算法都一样**。

**正确方向**:要求上传方**证明自己真的持有这份内容**——服务端下发一段随机字节区间(如第 3MB~3.1MB 的哈希),客户端必须答对才允许建立引用。**这才是"秒传"和"越权领取"的分界线。**

#### 第 4 题 · 并发同 md5 上传的竞态 + 引用计数归零删除

**答得好**:承认竞态存在、提出**唯一约束 + 上传状态机(PENDING/UPLOADING/DONE)+ 行级排他锁**,思路是标准解法。

**三点补充**:

1. **"条件原子争夺上传权"要说得出 SQL**。不是"先读后判断",而是:
   ```sql
   UPDATE file SET status='UPLOADING' WHERE md5=? AND status='PENDING';
   -- 或 INSERT ... ON DUPLICATE KEY UPDATE
   ```
   判断依据必须是 **`affected_rows`**(1 = 抢到,0 = 别人在上传,转轮询),**不能是刚 SELECT 出来的值**,否则锁白加。

2. **有更简单的解法**:竞争失败方**干脆不参与**。`INSERT` 撞唯一键就当自己没上传,等对方 `status='DONE'` 后直接建引用。少一次上传、少一把锁、天然幂等。

3. **硬伤:"FastDFS 会为文件加读写锁"是错的**。FastDFS **没有读写锁**,它就是个文件存取服务,文件上传后不可变(除非 appender 模式)。**调 delete 它就真删**——下载中的请求读到半截或直接 404,它不保护你。

   **应用层解法**:
   - 引用计数归 0 后**不立即删**,标记"待删除"并延迟(如 24h)再真删,给在读者的窗口。这就是**软删除 + 冷数据清理**。
   - 或**永远不删真实文件**,只删引用,靠后台任务回收孤儿文件。
   - 补充:`storage.conf` 有 **`trash_path`**(删除的文件进回收站),这是 FastDFS 唯一沾边的保护,**但它不是锁,救不了正在读的请求**。

#### 第 5 题 · 负载均衡算法与那个"20%"(本轮信息量最大的一题)

**用户答**:算法从论文扒的、公式完整、有权重、有测试阶梯(1/10/50/100/200/300 线程)、**并诚实交代了"并发 <10 时新算法反而更慢"的拐点**,以及"源码修改与压测脚本用了 GPT 辅助"。诚实度值得肯定。

**四个洞(任何一个被追问都会穿)**:

**洞 1 · 两个概念的定义写反了(杀伤力最大,因为看起来像不懂自己在算什么)**

| 用户叫的名字 | 用户放进去的内容 | 实际是 |
| --- | --- | --- |
| **节点负载** | CPU 数量、CPU 频率、内存容量、磁盘容量、网络吞吐量 | 全是**静态能力** |
| **节点处理能力** | CPU 使用率、内存使用率、磁盘使用率、网络使用率 | 全是**当前负载** |

**洞 2 · 不同量纲的原始值直接加权平均,数学上不成立**

CPU 数量×频率是 GHz 级个位数、内存容量是几十 GB、网络吞吐是千兆。把 `3.2`、`64`、`1000` 按 0.2/0.3 相加 → **网络吞吐一项以绝对优势支配整个公式**,前三个因子等于白算。

> **必须做归一化**(min-max 到 [0,1] 或 z-score)。**论文里几乎肯定做了,是复述时漏了。** 这个洞比洞 1 严重——**它是方法论错误,不是命名问题**。

**洞 3 · 第三步"选概率最大的节点"让概率这一步变成废话**

概率定义是 `能力 / Σ能力`,那么"选概率最大的" = **确定性 argmax**,和概率、和随机毫无关系。负载因素此时只通过候选集准入生效,不再影响最终选择。

> **自相矛盾**:理论(含概率)与实现(argmax)只能成立一个。若论文原意是**加权随机采样(轮盘赌)**,那实现是 bug;若原意就是 argmax,那"计算概率"这一步该删掉。且 argmax 会让每轮倾向选同一个节点,**造成短时热点**,等它压力上来才掉出候选集——这是另一个该测的点。

**洞 4 · 单机 Docker 4 台 storage,等于这个算法无法被验证**

4 台 storage 全在一台物理机,**共享同一块磁盘、同一个 CPU、同一条 docker bridge 网络**。算法里的"磁盘性能因子"在实验中**恒为常数,扰动为 0**。

> 测出来的差异绝大部分来自**调度本身的开销**,而不是"负载分得更均匀"。**它证明的是"这个算法不比轮询差太多",而不是"它能优化磁盘性能因子"。** 这个口径要说清,否则一问就穿。

**洞 5 · 简历与口述不一致**

简历写"改进了**最大剩余空间算法**",口述对照组是"**轮询算法**"——这是 FastDFS 里**不同的两个东西**,面试官一眼能看出。**必须统一**。

#### 第 6 题 · shared_ptr

**答对**:控制块存引用计数、两个指针宽度、`make_shared` 一次分配、weak_ptr 存活时内存回收差异、引用计数原子但 shared_ptr 本身非线程安全(**双指针无法原子整体更新**)。

**补三点**:

1. **`make_shared` 的首要理由是异常安全**。`shared_ptr<T>(new T(...))` 里 `new` 与构造是两步,中间抛异常会泄漏(标准要求编译器消除,但作为函数参数传递时仍可能泄漏)。另外**控制块与对象同块 → 缓存局部性好,少一次指针跳转**。
2. **措辞要更精确**:weak_ptr 存活时,`make_shared` 是"**对象已析构、整块内存未归还**";`shared_ptr<T>(new T)` 是"**对象内存已归还,控制块那块还占着**"。是**程度差别,不是有无差别**。
3. **C++20 的那个东西叫 `std::atomic<std::shared_ptr<T>>`**(特化版本,基于 P0718)。**不是 `atomic_shared_ptr`**(那是更早的提案,没进标准)。低锁实现通常靠**双引用计数**(一个管对象、一个管控制块)。C++20 之前可用 `std::atomic_load/store` 自由函数。

#### 第 7 题 · epoll 与单线程 Reactor(本轮答得最好的一题之一)

**答对**:红黑树 O(log n) 增删改、就绪队列、回调触发、只拷就绪队列;LT/ET 行为差异;ET 必须配非阻塞 + 循环读到 `EAGAIN`;单线程 Reactor 会被慢操作/阻塞调用/高并发拖死。

**收紧三处**:

1. **epoll 快的根本原因要说透**:
   > 红黑树只省了**增删改**的代价。真正的分水岭是——**就绪状态由内核持久维护**,`epoll_wait` **不需要每次重新传入全套 fd 让内核重扫**,只拷就绪队列。
   > 而 select 每次调用既要把整个 fd 数组拷进内核、内核再 O(n) 轮询,返回时还把数组**原地改写成就绪子集** —— 所以下一轮循环**必须重新构建整个 fd 集合**。这才是根本原因。
   > 附带好处:**select 有 `FD_SETSIZE=1024` 硬上限**,epoll 没有。
2. **LT 的表述再收紧**:不是"一次没读完后面还会通知",而是**只要缓冲区仍有数据,每轮 `epoll_wait` 都会报告**。ET 的收尾条件是**循环 read 直到 `EAGAIN`**,不是"读够预期字节数"。**多线程下 ET 还要配 `EPOLLONESHOT`**,否则同一 fd 的事件可能被多个线程同时处理。
3. **单线程 Reactor 的解法要落到具体**:muduo 是 **one loop per thread** —— main reactor 只负责 accept,把新连接分给 sub reactor,每个 sub reactor 一个线程跑自己的 epoll;业务逻辑交给**线程池**,且跨线程投递任务**必须走 `runInLoop/queueInLoop` 的唤醒机制**,否则往别人的 event loop 里塞任务会有竞态。libevent 类似(`event_base` 多线程 + `evthread_use_pthreads`)。

#### 第 8 题 · TCP 三次握手 / TIME_WAIT / 项目并发

**答对**:历史连接问题(旧 SYN 导致冗余连接、三次握手靠客户端回 RST 消除)、TIME_WAIT 的两个理由、客户端端口耗尽更严重、**坦诚承认项目每接口 1 个 FastCGI 进程 + 阻塞 IO = 串行排队**。

**三处纠正**:

1. **"前两次握手确认双方序列号"是错的**(必须记准):
   > **第一次**:让服务端知道客户端 ISN。
   > **第二次**(SYN-ACK):让客户端知道服务端 ISN,同时 ACK 了客户端 ISN。
   > **第三次**:让服务端知道"客户端已收到我的 ISN 了"。
   > **三次各自确认一个方向,不是"前两次就确认完"。**
2. **TIME_WAIT 危害要精确**:
   > **服务端** TIME_WAIT 多,**端口不会不够**(监听端口固定,四元组靠对端区分),只占少量连接表项和内存,几万条也就几 MB。
   > **客户端** TIME_WAIT 才致命——占满 **ephemeral port**(Linux 约 28232~65535,约 3.7 万个),新连接建不起来,报 `Cannot assign requested address`。
   > 用户的结论对(客户端更严重),但"服务端内存 CPU 压力"是次要理由,**真正理由是端口池**。
3. **syncookies 补一句**:它是**半连接队列满时才启用**的降级方案,代价是**丢掉 SYN 里的 TCP 选项**(窗口缩放、SACK 等),**只是保命,不是根治**。

**第 3 问自相矛盾(必须改)**:第 2 题说"异步串行上传",这里说"阻塞 IO、串行排队"——**面试官最讨厌前后不一致**。**以本回答为准**:单进程 + 阻塞 IO = 真串行。

> **正确优化路径**:FastCGI 换多进程(`spawn-fcgi -C`),或后端换异步框架。**Nginx 那层根本不是瓶颈**——它是事件驱动的,扛几千并发没问题。

#### 第 9 题 · MySQL 索引

**术语硬伤(本轮最该改的一个)**:

| | 定义 |
| --- | --- |
| **复合索引** | 索引里**有多列** |
| **覆盖索引** | 查询需要的**所有列都能从索引里拿到,不需要回表** |

> **"建一个覆盖索引"这个说法不成立。** 你是不是覆盖索引,**取决于 SQL 怎么写**。`SELECT user_name FROM ...` 走 `(user_name, nick_name)` 是覆盖;`SELECT * FROM ...` 走同一个索引就不是覆盖,**必须回表**。面试官听到"建覆盖索引"必追一句"你的 SQL 是什么"。
> 用户后面写"**覆盖索引**违反了最左前缀"——同样是这个混淆,**应为"复合索引"**。

**逐条纠正**:

1. **`user_info(user_name, nick_name)` 大概率白建**。登录场景下 `user_name` 本身就该是 **UNIQUE** 主键或唯一索引,单列就够。加 `nick_name` 只有当查询**恰好只 select 这两列**才有意义。**准确说法**:登录走 `user_name` 唯一索引,等值查询、一次回表取全行,这是最优的。
2. **`md5 + 文件名` 建索引方向反了**。秒传查询是 `WHERE md5 = ?`,md5 放第一列是对的;但**第二列放文件名是错的**——`md5` 与 `文件名` **不是一对一**(同一内容可任意改名)。更关键的是:**这个索引真正该做的是 `UNIQUE(md5)`**——**唯一约束是正确性保证,普通索引只是附带**。
3. **索引失效清单缺两项高频项**:
   - **区分度低**(如 `status` 只有 0/1),优化器宁可全表扫也不走索引;
   - **优化器成本估算**——**即使建了索引,若优化器估计走索引比全表扫贵,它照样不走**。
4. **EXPLAIN 不能只看 `key: null`**,要看这几列:

   | 列 | 看什么 |
   | --- | --- |
   | `type` | `ALL` 全表 → `index` → `range` → `ref` → `eq_ref` → `const`(从左到右越来越好) |
   | `key` | 实际用了哪个索引 |
   | `key_len` | 用了复合索引的**前几列**(**最能看出最左前缀断在哪**) |
   | `rows` | 预估扫描行数 |
   | `Extra` | **`Using index` = 覆盖索引的标志**;还有 `Using filesort`、`Using temporary` |

5. **Redis 先挡一层方向正确**,但"缓存整个文件列表快照"有具体问题:
   - **单个巨型 HASH = big key**。字段数可能上百万,进出、RDB 持久化、主从同步都会卡。**应拆成"一个 md5 一个 key"**。
   - **"hash 能自动去重"这句不对**——HASH 字段名本来就唯一,这是数据结构特性,不叫去重能力。秒传判定用 **`SISMEMBER`(Set)或 `SETNX`** 更自然。
   - **心跳定时同步 = 数据可能不一致**。Redis 无但 MySQL 有 → 回源能兜住;但**反过来**(Redis 有、MySQL 已删)会**返回一个不存在的 file_id**,必须处理。
   - **层次别搞混**:Redis 只是**性能优化**,`UNIQUE(md5)` 才是**正确性保证**。**Redis 挂了不能导致上传失败;MySQL 少了唯一约束才是真错。**
   - 加分项:怕大量不存在的 md5 打穿 Redis(**缓存穿透**),可用**布隆过滤器**放最前面挡。

#### 第 10 题 · Redis 排行榜 / session / 缓存三兄弟

**答对**:三兄弟辨析准确(雪崩 = 大量 key 同时过期或宕机;击穿 = 单个热点 key 过期;穿透 = 查不存在的数据)、布隆过滤器用法、击穿的三种解法(逻辑过期 + 异步更新 / 互斥锁 / 限流)、雪崩的解法(随机偏移、限流、核心数据永不过期 + 后台刷新)。

**三处纠正**:

1. **命令错**:查排名应用 **`ZREVRANK key member`**,不是 `ZRANK`。
   > 排行榜按分数**降序**排,`ZRANK` 返回的是**升序**排名 —— **第一名用 `ZRANK` 查出来会是最后一名**,实际用会直接出 bug。
   > 对照:`ZREVRANGE key 0 9` 取 top10、`ZREVRANK key member` 查降序排名(0 起)、`ZSCORE key member` 拿分数。
   > 用户主动说明"只能看整个排行榜、没实现按文件查"是**好习惯**。但要准备好下一问"如果让你实现"——答案就是 `ZREVRANK`。

2. **session 设计有严重问题(本轮最大设计坑)**:
   > `SETEX user_name 86400 token` —— **key 用用户名,意味着一个用户只能有一个 session**。用户在公司登录、回家再登录,**前一个设备的 token 会被直接覆盖,前一设备下次请求就掉线**。**这不是安全,是功能缺陷。**
   > **正确设计**:key 用 **token 本身或 token 的哈希**(如 `session:<token>`),value 存 user_id 与过期信息;或 `session:<user_id>:<device_id>` 支持多端。**value 直接存明文 token 也不理想**,Redis 被读等于凭据泄漏。

3. **"登出是纯前端行为"必须改**:
   > 前端删 localStorage 只是"**客户端忘了自己是谁**",**服务端那把 token 依然有效**。若 token 被截获,攻击者**照样能用满 24 小时**。
   > **正确做法是服务端删除 Redis 的 key**,让 token **立即失效**(服务端注销 / token 吊销)。这正是 JWT 这类无状态 token 的经典缺陷(所以需要 token 黑名单)。**项目里 session 本来就存 Redis,直接 `DEL session:<token>` 就完事,没有理由不做。**

4. **缓存穿透补第三招**:把"查不到"也缓存起来(**存空值**,TTL 短一点如 60s)。"接口层拦截非法参数"只挡格式违法的,**挡不住攻击者拿合法格式但不存在的 md5 来刷**,所以**布隆过滤器 + 空值缓存才是主力**。

5. **用户把最重要的一条说漏了**:"除非 Redis 宕机,导致所有缓存失效" —— **这才是项目最该担心的场景**,用户却说"不用担心"。
   > **Redis 一挂:所有用户 session 全部失效、全体掉线;同时所有秒传请求穿透到 MySQL。** 这不是"雪崩的定义差别",**这是单点故障**——整套鉴权体系建立在 Redis 可用性上,且没有降级方案。
   > **必须能答**:本地二级缓存 / Redis 集群(主从 + 哨兵)/ session 落 MySQL 兜底。

#### 第 11 题 · 三份状态的一致性(项目收尾必问)

**第 1 问答得最好——是"推出来的",不是"背下来的"**:

> 用户用**依赖驱动**推导顺序:F先生成 file_id → 才能拼下载 URL → 才能填文件记录 → 才能建引用记录。**面试官要的就是这种推导。**

**但第 2~4 问有三个问题**:

**问题 1 · 用户忘了自己发明过的东西**。第 4 题提的"文件上传**状态机**(PENDING/UPLOADING/DONE)",其副产品恰好就是解决孤儿文件的钥匙,第 11 题却提出要全盘扫描。

| | 用户现方案(全盘扫描) | 状态机方案 |
| --- | --- | --- |
| 做法 | 空闲时枚举 FastDFS 所有文件,逐个查 MySQL 比对 | 上传前先写 PENDING 记录;成功改 DONE;MySQL 写失败就留在 PENDING |
| 清理 | `SELECT * FROM file WHERE status='PENDING' AND create_time < NOW() - INTERVAL 1 HOUR` |
| 难点 | **FastDFS 没有"列出所有文件"的 API**,只能直读 storage 文件系统目录或解析 binlog/`.dat` 索引,**脏且慢** | **一条索引查询搞定,不用碰 FastDFS 文件系统** |

> **这就是那个状态机设计值钱的地方——它同时解决了竞态和垃圾回收。面试时把这两题串起来讲,是明显加分项。**

**问题 2 · "MySQL 写成功但 FastDFS 失败在设计中不会出现"——说得太满**。

> 文件记录确实不会脏(file_id 是前置依赖,论证对)。**但 MySQL 写入是三步**:① 文件记录 ② 用户引用记录 ③ 用户持有数 +1。**任何一步失败都会脏。**
>
> 最典型:**文件记录写成功 → 写用户引用记录失败(超时/唯一键冲突/连接断)→ 用户收到上传失败,但文件记录已存在,引用计数是旧的**。
>
> **后果比孤儿文件严重**:下次**别人**上传同样 md5,秒传命中这条记录 → 给他建引用 → 用户"拥有"了一个**从没有人真正上传成功过**的文件,**下载直接 404**。这就是**幽灵记录**。
>
> **准确回答**:只要多步 MySQL 写**不用事务包住**就会出现;**放进一个事务里,要么全成要么全败**。

**问题 3 · 第 4 问只给结论没给理由(而面试官恰恰只要理由)**:

> **判断严重程度看两条:用户可见性 + 可自愈性。**
>
> | | 用户可见性 | 可自愈性 | 结论 |
> | --- | --- | --- | --- |
> | **孤儿文件**(FastDFS 成功、MySQL 失败) | 用户看不到,不影响正确性 | 后台任务能自动清掉,代价只是磁盘空间 | **可自愈** |
> | **幽灵记录**(MySQL 多步写不原子) | 用户直接看到损坏结果(下载 404 / 秒传给出不存在的文件) | 系统**无法自己发现**,必须人工介入 | **不可自愈** |
>
> **所以防幽灵记录优先,手段是事务;防孤儿文件是"省钱问题",可以慢慢做。**

**额外送分点 · 反范式字段一定会飘**:

> "用户文件持有数"是**反范式字段**(冗余存储,避免每次 `COUNT(*)`)。这类字段**长期一定会飘移**,无论多小心。
> **正确心态不是保证它绝对正确,而是定期用 `SELECT COUNT(*) FROM user_file WHERE user_id=?` 校正**,或干脆实时算、用索引扛。面试官问"这个计数会不会不准",答这句就是加分。

#### 第 12 题 · 零拷贝(答得好,但有一处硬错)

**答对**:传统 `read+write` 的拷贝与切换组成(2 次 DMA + 2 次 CPU 拷贝、4 次上下文切换);`sendfile` 2 次 DMA + 1 次 CPU、2 次切换;**`splice` 全部答对**(走管道传页引用、无 CPU 拷贝);**HTTPS 用不了 `sendfile` 的本质**(TLS 必须在用户态拿明文,`sendfile` 让数据根本不进用户态,二者冲突)。

**硬错 · 系统调用次数 vs 上下文切换次数搞混**:

> 用户答"`mmap+write` 系统调用次数还是 4 次" —— **错**。应为 **2 次系统调用、4 次上下文切换**(每次系统调用进出内核算 2 次切换)。
> **传统 `read+write` 也是 2 次调用 / 4 次切换** —— **两者在调用和切换上完全一样,唯一差别是省掉一次 CPU 拷贝。**

**漏掉的两点**:

1. **`mmap` 那个"看起来省了其实没省"的地方**:`mmap` 消除的是**内核页缓存 → 用户缓冲区**这次 CPU 拷贝,但**内核页缓存 → socket 缓冲区**这次**依然存在**。所以总共还是 **3 次拷贝(2 DMA + 1 CPU)**,不是零拷贝。且有隐性成本:首次访问触发缺页中断(反而要读盘)、`munmap` 开销、文件被截断时 SIGBUS —— **并不适合小文件高频传输**。
2. **`sendfile` 的升级版(SG-DMA)**:用户答的是**基础版**。若网卡支持 **scatter-gather DMA**,socket 缓冲区里只放**描述符**(记录数据在内存中的地址和长度),DMA 直接按描述符把数据从内核页缓存 gather 到网卡 —— **CPU 拷贝归零**,变成 **2 次全 DMA**。Linux 2.4 后配合支持 SG-DMA 的网卡走的就是这条路径,**这才是 `sendfile` 被叫做零拷贝的底气**。

**补一个约束**:`splice` 要求**两个 fd 中至少一个是管道**,不能直接 file→socket 一把梭,**必须绕管道** —— 这是**硬性约束**,不是可选设计。

**HTTPS 追问的加分答案**:Linux 4.13 引入 **kTLS(内核 TLS)**,把加解密下沉到内核,`sendfile` 就又能用了;OpenSSL 3.0 的 **`SSL_sendfile()`** 走的正是这条路。**这是这个八股的标准追问答案。**

**第 4 问(用户答"不清楚",已补)——代理场景 vs 静态文件场景的区别**:

> 区别在于**数据的来源不是文件,而是另一个 socket**。
>
> | 场景 | 数据源 | 机制 | 源码位置 |
> | --- | --- | --- | --- |
> | **静态文件**(Nginx 直读本地磁盘) | 普通文件 | **`sendfile`**(file → socket) | `ngx_linux_sendfile_chain.c` |
> | **反向代理**(数据来自上游 socket) | **socket** | **`splice`**(socket → pipe → socket) | 同上 |
>
> **`sendfile` 用不了是因为它要求源端必须是文件 fd。**
>
> **回到项目**:Nginx 挂 `fastdfs-nginx-module` 直读 storage 本地磁盘 → 走 **`sendfile`**;Nginx `proxy_pass` 到 tracker/storage 的 HTTP 接口 → 走 **`splice`**,**且必须 `proxy_buffering off`** —— 一旦开缓冲,数据被读进 Nginx 缓冲区,零拷贝路径退化成普通读写,全白费。

**最后一个坑(必记)**:

> 项目里**真正返回文件正文的是 FastCGI 进程**(把文件流经 FastCGI 转给 Nginx)。这条路走的是**普通 `write`,一次零拷贝都没有**,还额外引入"FastCGI 进程 → Nginx"的一次完整搬运。
> **标准回答**:"Nginx 处理静态文件那层是 `sendfile`,但我把下载走了 FastCGI,**反而破坏了这条路径 —— 这是我知道的一个优化点**。"

### 一、Redis 持久化

#### 主线口径(30 秒版)

> RDB 是**内存快照**,把某一时刻的全部数据写成一份二进制文件;AOF 是**命令追加日志**,把每条写命令追加到文件末尾。两者不是"谁更完整",而是**保存粒度不同**:RDB 两次快照之间的写会丢,AOF 按 `fsync` 频率决定丢多少。
> 两个都开启时,**重启优先用 AOF**,因为它的数据更接近崩溃点。Redis 4.0 之后引入**混合持久化**:文件头是 RDB 快照、后面是增量命令,重启时先快照载入、再重放增量。

#### 三个必被追问的点

**1. RDB 的 fork 与 COW**

> `bgsave` 时 Redis `fork` 出子进程,**子进程看到的是 fork 那一刻的一致内存视图**,由它写成 RDB。
> 父进程此时仍处理写请求,一旦要改某一页,触发 **Copy-On-Write** —— 在**副本页**上改。所以 **RDB 不含 fork 之后的任何新写入**。
> 代价:快照期间写入越频繁,**被复制的页越多,内存峰值越高**(极端情况接近翻倍)。被跳过的那些写,由下一次 RDB 或 AOF 兜住。

**2. AOF 重写(最容易漏 `rewrite buffer`)**

> 重写期间**父进程没有停下**:一边把新命令**继续追加进旧 AOF**,一边把这段时间的新命令缓存进内存的 **rewrite buffer**。
> 子进程写完新 AOF 后,父进程把 rewrite buffer 补到新文件末尾,最后 **`rename` 原子替换**。
> **这三步缺一不可**,否则重写期间的写入会整段丢失。

**3. 主从全量同步也走 RDB**

> **即使关了 RDB 持久化,主从首次全量同步仍然走 RDB** —— 二进制直接载入比逐条重放命令快得多,压缩后传输也省带宽。
> 之后的增量靠 **replication backlog** 补。Redis 7 支持 **diskless(无盘)复制**,不落盘直接流式发送。

#### 答题行为提醒

> **不要主动说"我项目里只是简单用了 Redis"** —— 这句会引导面试官按最低水平考你。改口径为"**项目中用到的是 Redis 的基础能力**",然后主动往下讲深度,让面试官来探。

### 二、HTTP 状态码 / 长连接 / Range 断点下载

#### 1. 状态码

**只背高频的那几个,别背全表。**

| 类 | 含义 | 高频项 |
| --- | --- | --- |
| 1xx | 信息性 | **100 Continue** —— 客户端先问"我要发大 body 你收不收",避免白发 |
| 2xx | 成功 | **200**、**204 No Content**、**206 Partial Content**(Range 命中) |
| 3xx | 重定向 | **301** 永久 / **302** 临时 / **304 Not Modified**(缓存命中) |
| 4xx | 客户端错 | **400**、**401**(未认证)vs **403**(认证了但没权限)、**404**、**405**、**413**、**416**、**429** |
| 5xx | 服务端错 | **500**、**502**、**503**、**504** |

**三个必答的区分**:

| 对比 | 分界 |
| --- | --- |
| **401 vs 403** | 401 = "**你没告诉我你是谁**"(缺凭据/凭据无效);**403 = "我知道你是谁,但你不许碰这个"**。项目口径:token 过期返 401,访问别人的文件返 403 |
| **301 vs 302** | 301 **永久**,浏览器缓存跳转,以后直接去新地址;**302 临时**,每次还问原地址。**做 HTTPS 跳转用 301 要小心** —— 浏览器记住后你改了目标它也不会再问 |
| **304** | **不返回 body**。协商缓存的产物:客户端带 `If-None-Match`(ETag)或 `If-Modified-Since` 来问"变了吗",服务端答"没变" → 304,**省掉整个 body 传输**（= 缓存命中在 HTTP 层的体现） |

> **项目相关**:`413` 正是 Nginx **`client_max_body_size 12m`** 触发时的返回码。传超限文件会拿到 **413,不是 500** —— 这个细节答出来很加分。

#### 2. 长连接

> HTTP/1.0 **默认短连接**,要长连接得显式写 `Connection: keep-alive`;**HTTP/1.1 默认长连接**,想断开反而要写 `Connection: close`。

**核心价值不是"省一次三次握手"**(那只省建连延迟),而是**保留 cwnd、ssthresh 和 RTT 估计** —— 后续请求直接在已探测好的拥塞窗口上跑,量级完全不同。(记录 03 已答对过。)

**服务端何时关**:`keepalive_timeout`(空闲多久关)+ `keepalive_requests`(最多服务多少请求)。项目里是 `nginx.conf` 的 `keepalive_timeout 65`。

**面试可主动说的诚实口径**:

> "我的 Nginx 客户端侧开了 keep-alive,但 **Nginx 到 FastCGI 那一侧没开** —— 配置里没有 `fastcgi_keep_conn`,默认是关的。所以每个请求都会新建一条后端连接,代价是反复建连和 TIME_WAIT 堆积。这是我后来才发现的一个优化点。"

#### 3. Range 断点下载(**与项目直接相关,重点准备**)

**请求与响应**:

```
GET /file/xxx
Range: bytes=0-1023          ← 客户端要前 1024 字节
```

| 情况 | 状态码 | 响应头 |
| --- | --- | --- |
| 正常支持 | **206 Partial Content** | `Content-Range: bytes 0-1023/5000000` |
| 范围越界 | **416 Range Not Satisfiable** | `Content-Range: bytes */5000000` |
| 服务端不支持 | **200**(回整个文件) | 无 `Content-Range` |

服务端声明支持靠 **`Accept-Ranges: bytes`**。

**两个追问答案**:

- **断点续传**:客户端记录已拿到的字节数 N,下次带 `Range: bytes=N-` 重新请求,服务端从第 N 字节返回,客户端**追加**到本地文件末尾。
- **多线程下载**:按 Range 切成若干段,每线程负责一段,**各自 seek 到自己的偏移写入同一个文件**。注意这是"多连接写同一本地文件的不同区域",**不是各写一份再合并**。

**必须搞清的区别 —— 别把"断点续传"和项目的"分片上传"混为一谈**:

| | HTTP Range 断点续传 | 项目的分片上传 |
| --- | --- | --- |
| 切分粒度 | **字节区间**(如 0-1023) | **应用层的块**(每片 10MB) |
| 谁切 | 客户端发个 Range 头,**HTTP 协议原生支持** | **纯应用层约定,HTTP 不认识"分片"** |
| 服务端视角 | **同一个资源、同一个请求**,只是要一部分 | **N 个完全独立的请求**,互不知道彼此存在 |
| 合并 | **不需要**,客户端自己往对应位置写 | **必须服务端合并**(`chunk_merge`) |

> **一句话:Range 是 HTTP 协议自带的"要一段"能力,分片是应用层自己发明的"分多次传完"。HTTP 里没有"分片上传"这个概念 —— 把两者说成一回事,面试官立刻知道你没分清层次。**

**可主动加的加分句**:

> "我项目的上传是自定义 API 做分片,没走 Range。但**下载其实可以用 Range 实现断点续传** —— 如果让我优化,我会给 `GET /file` 加上 `Accept-Ranges: bytes`,让客户端在弱网下续传,而不是从头再来。"

**最后一个易错点**:`Content-Length` 与 `Transfer-Encoding: chunked` **不能同时出现**。前者要求**提前知道**总长度,后者用于长度未知时流式发送。项目的分片上传是短连接 + 已知长度,走 `Content-Length`。
