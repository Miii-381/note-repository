# 游戏服务器开发学习笔记：从原理到落地

> 复习方法：每个主题都按“是什么 → 为什么 → 怎么做 → 面试表达/注意点”理解。技术选型没有唯一答案，必须结合游戏类型、实时性、规模和团队现状。

## 1. 游戏服务器开发所需技术栈

### 是什么

游戏服务端不是单一程序，而是一套支持登录、长连接、匹配、对局、社交、经济、排行榜、部署与监控的系统。

| 层级 | 常用技术 | 作用 |
|---|---|---|
| 通信 | TCP、UDP、KCP、WebSocket、Protobuf | 连接与消息传输 |
| 接入 | Go/Java/C++、Netty、gRPC | 鉴权、连接管理、路由、限流 |
| 业务 | Go、Java、C++、Actor | 匹配、房间、战斗、好友、公会 |
| 数据 | MySQL/PostgreSQL、Redis | 可靠存储、缓存、会话、排行榜 |
| 异步 | Kafka/RocketMQ/RabbitMQ、任务队列 | 削峰、日志、发奖、分析 |
| 运维 | Linux、Docker、Kubernetes、CI/CD | 部署、扩缩容、发布与回滚 |
| 可观测 | Prometheus、Grafana、日志系统、链路追踪 | 指标、告警、定位问题 |

### 为什么

游戏的核心难题是大量长连接、低延迟、状态频繁变化和资产正确性。MOBA/FPS 重点是房间隔离、同步与网络抖动；卡牌/放置类更重活动、经济系统和数据一致性。只会写接口不足以保证对局公平、发奖不重和服务可恢复。

### 怎么做

1. 先掌握 Linux、Git、TCP/UDP、序列化和一门主语言。Go 适合高并发服务；Java 生态成熟；C++ 常用于极致性能路径。
2. 实现最小闭环：登录鉴权 → Gateway 长连接 → 大厅/匹配 → 房间 → 结算 → 落库。
3. 用 Protobuf 定义协议；每条操作带玩家、房间、序列号和请求 ID，服务端做鉴权、顺序与幂等校验。
4. Redis 放会话、热点状态、实时榜；关系型数据库保存角色、订单、资产流水等最终事实。货币/道具必须使用事务、流水、幂等键，缓存不是唯一账本。
5. 同一房间状态应由单线程、Actor 或同一逻辑协程串行修改，减少锁竞争。
6. 压测连接数、消息频率、断线重连和峰值匹配，持续监控在线数、错误率、P99 延迟、GC、缓存命中率。

### 面试表达

“我会按接入、业务、数据、异步和运维分层。房间状态尽量串行执行；资产操作用事务、流水和幂等保证；Redis 用于热点状态而非唯一真相；上线前用压测和指标验证 P99 延迟与故障恢复。”

## 2. 如何用 AI 开发《王者荣耀》式匹配功能

### 是什么

匹配系统将排队玩家分配到房间，目标是在可接受等待时间内兼顾实力公平、位置偏好、组队对称、网络质量和留存体验。基础是 MMR/Elo/Glicko 隐藏分；AI 通常是预测模型和排序/优化策略，不是让大语言模型实时“决定谁和谁打”。

### 为什么

仅按段位差匹配会出现多目标冲突：追求速度会降低公平性，严格公平会使高分玩家久等；双排/五排、位置偏好和跨区 ping 还会限制组合。预测模型可从历史对局学习胜率、掉线/流失风险和网络体验，为可行候选对局排序。

### 怎么做

1. **先做规则基线。** 队列按模式、区服、组队人数、段位区间、位置意向分桶。等待开始时搜索窗口较窄，随等待时长逐步放宽 MMR 和位置限制；核心公平约束不能无限放宽。
2. **构建特征和模型。** 特征包括双方 MMR、置信度、英雄/位置熟练度、组队关系、近期表现、ping、版本和排队时长；可预测胜率、重开率、赛后流失风险。
3. **候选对局打分。** 一个简化目标：公平度 + 位置满足度 + 网络质量 − 等待成本 − 组队不对称惩罚。公平度可用预测胜率接近 50% 衡量，也应考虑模型不确定性。
4. **实时求解。** 先过滤硬约束（封禁、黑名单、模式、地域），再在小候选池中用贪心加回溯、分桶匹配或图匹配寻找组合。
5. **安全上线。** 模型超时或异常必须回退规则；灰度和 A/B 实验同时观察等待时长、胜率偏离、掉线率、留存与投诉，不能只优化匹配速度。
6. **公平性护栏。** 防止模型为了留存而持续给某类玩家不公平对局；按段位、地区、组队形态审计效果。

### LLM 的位置

LLM 可辅助分析投诉、总结异常匹配、生成测试和运营规则草案；不应位于实时决策热路径，因为延迟、成本、输出稳定性和可审计性都不合适。

### 面试表达

“先用 MMR 与逐步扩展窗口建立稳定基线，再把胜率、网络或留存风险预测作为候选排序特征。线上保留规则兜底、超时降级、灰度和 A/B 实验，优化的是公平、等待和体验的组合指标。”

## 3. RAG（检索增强生成）

### 是什么

RAG 让 LLM 回答前先检索外部知识库，再依据检索到的资料生成答案。典型链路是：文档采集 → 清洗切分 → 向量化/索引 → 查询检索 → 重排 → 拼接上下文 → 带引用回答。

### 为什么

游戏项目中的策划案、接口文档、数值说明和事故手册更新快且私有。直接问模型可能过时、编造或无法给出证据。RAG 使知识可更新、可追溯，成本远低于反复训练模型。

### 怎么做

1. 明确知识边界和权限。只接入已审核来源；检索必须继承原文档权限，不能借聊天入口越权。
2. 解析文档时保留标题、模块、版本、更新时间、来源、权限等元数据。按语义切成约 300–800 tokens 的块，保留少量重叠。
3. 使用混合检索：向量检索解决语义相近，BM25/关键词解决错误码、版本号、专有名词；合并后用 reranker 重排。
4. Prompt 明确“仅根据给定资料回答；资料不足就说不知道；给出来源”。上下文按相关性排序、去重并限制长度。
5. 建真实问题集，分别评估正确资料是否召回、回答是否正确、引用是否支撑、拒答是否恰当，以及延迟和成本。
6. 文档增量更新索引；记录匿名查询、命中文档和反馈，持续补齐低分问题。

### 常见误区

只换大模型而不修文档和检索；把全库塞进 Prompt；没有权限过滤；没有引用与拒答策略。实际项目中，大量“幻觉”根因是没有检索到正确资料。

## 4. LLM Wiki

### 是什么

LLM Wiki 是以项目文档为事实源、以可编辑 Wiki 为沉淀、以 RAG/工具调用为问答入口的知识系统。RAG 是检索技术，LLM Wiki 则还包含文档生产、审核、版本、权限、问答和反馈流程。

### 为什么

游戏团队跨策划、客户端、服务端、测试、运营，传统 Wiki 常常“写了却搜不到、更新没人知道”；纯聊天机器人又不可靠。目标是让成员快速找到可验证的答案，并把经验沉淀下来。

### 怎么做

- 统一页面模板：背景、适用版本、方案、接口/配置、风险、负责人、更新时间、关联资料。
- 给“草案、正式、废弃”打标签；检索时降低过期内容权重。
- 每次回答展示引用片段与原文链接；资料冲突时指出冲突，不能让模型擅自裁决。
- AI 可以生成草稿、摘要和更新建议；正式发布必须由负责人审核。
- 建无答案问题榜和低评分队列，反向补文档，并定期复审关键页面。

### 与 RAG 的关系

RAG 是回答时检索知识的技术能力；LLM Wiki 是围绕知识生产、审核、版本、权限、问答和反馈构建的完整系统。

## 5. 游戏寻路算法：拐点多怎么优化

### 是什么

寻路是在可行走区域中为单位找从起点到终点的路径。BFS 适合无权图，Dijkstra 适合非负权最短路，A* 在 Dijkstra 上加入启发式函数，是网格/NavMesh 游戏中最常见的方案。拐点多通常是网格路径产生的锯齿。

### 为什么

多拐点会造成角色频繁转向、视觉抖动、客户端插值困难，并可能增加碰撞和同步成本。提高寻路频率不能解决几何锯齿，反而增加 CPU 消耗。

### 怎么做

1. 先定位原因：仅四方向移动、障碍膨胀不够、没有转向代价，还是动态障碍导致频繁重算。
2. 网格允许八方向，横竖代价设为 1、斜向为 √2，并禁止从两个对角障碍之间“穿墙”。
3. 做**可视性裁剪**：尝试把当前点直接连到更远路径点，线段不碰障碍则删掉中间点。网格可用 Bresenham 或射线检测。
4. NavMesh 使用 **Funnel/String Pulling**，从通行门序列提取更短、更少拐点的路径；曲线插值后仍必须碰撞检测，不能切进墙体。
5. 在代价中加入轻量转向惩罚，状态可扩展为坐标加方向；它会扩大搜索空间，应只在有必要时使用。
6. 大地图用分层寻路：区域图给粗路径，局部网格/NavMesh 给细路径。
7. 静态障碍走全局路径；玩家、技能等动态障碍使用 RVO/ORCA 一类局部避障。确实堵死时才限频重规划。

A* 核心为 f(n)=g(n)+h(n)：g 是已走代价，h 是到终点估计。若 h 不高估真实剩余代价，A* 可保证最优解。

## 6. 路由器坏了与手机客户端崩溃：TCP 连接有什么不同

### 是什么

TCP 连接是两端协议栈维护的一份状态（序号、确认号、窗口、重传计时器等），不是一根物理线路。二者都会使对端最终认定离线，但检测路径不同。

### 路由器坏了/断网

手机进程和 socket 通常仍在，数据包却无法到达。服务端通常不会立刻收到断线通知：双方发送数据后收不到 ACK，会按重传计时器重传，直到达到超时/重试上限；也可能靠应用层心跳更早发现。网络短暂恢复时，若 TCP/NAT 状态都还在，连接可能继续；移动网络切换常导致状态丢失，因此仍应支持重连。

### 客户端崩溃

进程崩溃后，操作系统通常会关闭它持有的 socket，可能向对端发 FIN（正常关闭）或 RST（异常复位）。服务端收到后能较快清理连接。若手机同时死机、断电或网络不可达，服务端看起来仍像“无响应”，只能等超时。

### 怎么做

游戏协议用应用层 ping/pong，例如 3–10 秒一次，连续多次失败才判离线，避免网络抖动误踢。业务上将“逻辑会话”和物理 TCP 连接分离：断线保留战斗状态一个宽限期；重连后重新鉴权，用新连接原子替换旧连接，并按最后确认序列号补关键事件或下发快照。用连接代次/序列号拒绝旧连接迟到的操作。

## 7. 过期时间用什么数据结构？Redis ZSet 底层与复杂度

### 是什么

过期管理是在大量“对象 → 到期时间”中快速找到最早到期项并删除或触发任务。不能每秒扫描整个 Map，因为那是 O(N)。

| 场景 | 常用结构 | 核心特点 |
|---|---|---|
| 只需取最早到期项 | 最小堆（优先队列） | 堆顶最早到期 |
| 海量、跨度很大的定时器 | 时间轮/分层时间轮 | 插入与推进接近 O(1) |
| 要按时间范围查、取消或更新 | Redis ZSet | 按 score 有序，可范围读取 |
| 只需访问时判断是否失效 | 哈希表 + 惰性检查 | 简单但不准时清理 |

### 为什么与怎么选

最小堆的插入、更新、弹出是 O(log N)，查看最早元素 O(1)，适合中等规模且时间分布任意的任务。更新常用“插入新记录 + 版本号淘汰旧记录”，避免在堆中定位删除。

时间轮将未来时间切入槽位，指针每个 tick 前进，到槽时处理任务。单层适合短周期；分层时间轮以不同粒度覆盖秒、分钟、小时，适合大量连接超时。代价是精度受 tick 影响，槽内仍可能需要二次处理。

### Redis ZSet 的底层

ZSet 存储 member 与 score，例如 playerId 对应 expireAtMillis。Redis 按数据规模选择编码：

- **listpack：** 小集合使用，内存紧凑；查找/插入通常 O(N)。
- **dict + skiplist：** 大集合使用。dict 按 member 查 score 的平均复杂度为 O(1)；skiplist 按 score 排序、范围查询和定位的期望复杂度为 O(log N)。

| ZSet 操作 | 复杂度 | 用途 |
|---|---:|---|
| ZADD | O(log N) | 新增或更新到期时间 |
| ZSCORE | 平均 O(1) | 查询任务当前时间 |
| ZRANGEBYSCORE | O(log N + M) | 取截止当前时间的 M 个任务 |
| ZREM | O(log N) | 删除/取消任务 |
| ZPOPMIN | O(M log N) | 依次弹最早 M 项 |

### 用 ZSet 实现延时任务

写入时执行 ZADD expiry_queue expireAt taskId；延期则覆盖 score。消费者分批取 score 不大于当前时间的任务，再通过 Lua 脚本完成“取出并删除”，避免多消费者重复领取。业务执行仍必须幂等：消费者可能在执行后崩溃或超时重试，所以以 taskId 和状态机去重。Redis key 的 TTL 是惰性删除加定期删除，不承诺精确到点触发，不能等同可靠延时队列。

## 8. 游戏地图看到同屏玩家：用什么数据结构

### 是什么

AOI（Area of Interest，兴趣区域）系统决定某玩家应看到哪些实体、某次移动应广播给谁。若每次移动遍历全服玩家，复杂度为 O(N)，全量相互广播甚至会达到 O(N²)。

### 为什么

位置更新、怪物 AI、拾取、碰撞和状态广播都依赖可见集合。大地图多人在线时，必须先做空间粗筛，才能把计算和网络开销限制在“附近实体”。

### 怎么做：九宫格/均匀网格

最常见方案是把地图划为边长约等于视野半径或略小于它的格子，每个格子维护实体集合。实体映射到格子坐标为 floor(x / cellSize)、floor(y / cellSize)。

1. 用格子 ID 到实体集合的映射维护空间索引，实体自身保存位置和当前格子。
2. 实体未跨格时只更新坐标；跨格时计算旧视野与新视野的差集。
3. 进入新视野的发 spawn，离开视野的发 despawn，仍可见的才持续同步状态。
4. 九宫格仅是粗筛，边界实体还要按精确距离、视锥或遮挡规则过滤。
5. 副本、地图分线、区服先隔离，AOI 只在同一场景实例内运行。

### 其他结构

四叉树适合实体密度差异极大的大地图，但频繁移动更新较复杂；空间哈希是稀疏网格，适合大而稀疏的场景；R-tree 更偏数据库空间查询，未必适合高频移动。面试优先回答“AOI 九宫格，跨格才更新可见集合”。

## 9. 实时排行榜：用什么数据结构

### 是什么

排行榜要支持更新分数、取 Top N、查询个人名次与附近排名。典型选择是 Redis ZSet：score 放分数，member 放 playerId。

### 为什么

普通 Hash 查分快却没有顺序；数组每次更新再排序成本高。ZSet 兼顾成员定位与分数有序：更新 O(log N)，可快速取 Top N、个人名次与附近区间。

### 怎么做

- 更新：ZADD rank:season score playerId。若只允许分数增加，可用 Lua 脚本“读旧分并比较后更新”保证原子性。
- Top N：ZREVRANGE rank:season 0 N-1 WITHSCORES；个人名次：ZREVRANK；附近排名按 rank 为中心读一段范围。
- 昵称、头像等资料放用户资料缓存/数据库，榜单读出 ID 后批量补全，避免重复存储。
- 同分必须定义规则，例如二级排序或固定展示规则；不要随意把多个值拼进浮点 score，以免精度导致排序错误。
- Redis 维持实时榜，异步持久化快照与结算流水；赛季结束冻结快照，奖励发放必须幂等。
- 超大规模可按区服/分段分片再聚合 Top K。ZSet 不是唯一事实来源，关键分数必须来自可信服务端结算并配合反作弊。

## 10. KCP

### 是什么

KCP 是运行在 UDP 之上的可靠传输协议库，提供分片、序号、确认、重传、滑动窗口和拥塞控制。它把可靠性放到用户态，使应用能更主动控制重传与调度。

### 为什么

TCP 是严格有序字节流：早到的数据也可能因前面丢包而无法交给应用，称为队头阻塞。实时游戏里旧位置更新通常不如新位置重要；KCP 允许为游戏场景调节更新频率、窗口与快速重传。但它不是无条件比 TCP 快。

### 怎么做

1. 架构通常是 UDP socket → KCP 会话 → 游戏协议。以会话 ID 路由 UDP 包，再交 KCP 处理 ACK、乱序和重传。
2. 定时调用 KCP 的 update/check 驱动发送与重传；定时调度精度会影响延迟和 CPU。
3. 游戏层仍要做鉴权、心跳、断线重连、限速、幂等和加密/防篡改，KCP 不替代这些能力。
4. 关键操作、结算走可靠通道；高频位置/朝向可走不可靠“仅保留最新状态”的通道，避免过期包堆积。
5. 按真实网络压测 MTU、窗口、发送间隔、快速重传等参数。参数过激会放大拥塞和丢包。

网络良好或消息低频可靠时，TCP 更简单成熟且 TLS 生态完备。选择 KCP 意味着也要承担 NAT、抗攻击、监控与调参成本。

## 11. WebSocket

### 是什么

WebSocket 先通过 HTTP Upgrade 握手，随后在一个持久 TCP 连接上全双工通信。浏览器原生支持，适合网页小游戏、聊天、房间大厅和实时通知。

### 为什么

相比轮询，它减少重复 HTTP 请求与推送延迟；相比原始 TCP，更容易穿越常见的 HTTP/HTTPS 基础设施。它仍建立在 TCP 上，因此也具有可靠有序和队头阻塞特征。

### 怎么做

1. 使用 wss，握手阶段验证 token/会话，不能信任客户端传来的 playerId。
2. 协议包含消息类型、请求 ID、序列号、版本和 payload；JSON 调试方便，Protobuf 更省带宽。
3. 实现 ping/pong、最大帧长、频率限制、连接数限制和反压。慢客户端的发送缓冲持续增长时，应丢弃可丢旧状态或断开，不能无限占内存。
4. 连接放 Gateway，业务服务处理逻辑消息。断线恢复依赖逻辑会话，不能把业务状态绑死在一个 socket 上。

WebSocket 不是 UDP/KCP，也不是“更快的 HTTP”；它是适合浏览器双向长连接的应用层协议。

## 12. Linux 怎么看进程状态

### 是什么

进程状态表示任务正在运行、等待 CPU、等待 I/O、已停止或已退出等。排障不应只看“进程是否存在”，还要看 CPU、内存、线程、文件描述符、连接和内核日志。

| 目标 | 常用命令 | 关注点 |
|---|---|---|
| 找 PID 与状态 | ps -ef、ps aux、ps -o pid,ppid,stat,cmd -p PID | STAT、父进程、启动参数 |
| 实时资源 | top、htop | CPU、RES、线程数、load average |
| 看线程 | top -H -p PID、ps -L -p PID | 热点线程 |
| 看内存 | pmap -x PID、/proc/PID/status | RSS、匿名内存、线程数 |
| 看文件句柄 | lsof -p PID、ls /proc/PID/fd | socket/文件泄漏 |
| 看连接 | ss -antp、ss -uap | ESTAB、TIME-WAIT、端口 |
| 看卡点 | strace -p PID | read/write/futex/网络/I/O |
| 看系统问题 | journalctl、dmesg -T | OOM、磁盘与内核错误 |

### STAT 常见含义

- R：正在运行或等待 CPU。
- S：可中断睡眠，常见于等待网络、定时器或锁。
- D：不可中断睡眠，通常与磁盘或网络文件系统 I/O 等内核等待有关；长期存在需查底层 I/O。
- T：被停止或调试。
- Z：僵尸进程，已退出但父进程未回收；不能直接杀掉，应处理父进程的回收逻辑。

### 怎么排游戏服延迟

先看 top 判断 CPU 饱和还是 load 异常；再定位进程和线程。CPU 高时用 profiler/火焰图找热点；大量 D 状态时查磁盘、NFS、内核日志；连接异常时用 ss 看积压和状态；怀疑句柄泄漏时数 lsof。先采集现场，再决定是否重启。

## 13. 进程、线程、协程

### 是什么

| 概念 | 本质 | 特点 |
|---|---|---|
| 进程 | 资源分配与隔离单位 | 独立地址空间，隔离强，切换相对重 |
| 线程 | 操作系统调度 CPU 的单位 | 共享进程内存，可并行，仍需内核调度 |
| 协程 | 用户态协作调度单元 | 切换轻，适合大量 I/O 等待，需运行时配合 |

### 为什么

进程隔离不同服务；线程利用多核；协程以较少线程管理大量连接。它们可组合：多个容器/进程中，每个进程运行线程池或协程运行时。

### 怎么做

Gateway 通常用事件循环/协程处理大量连接，避免“一连接一线程”。房间可固定给一个线程、Actor 或逻辑协程串行执行，多个房间分散到 worker 利用多核。寻路、数据库、AI 推理等耗时任务放异步池，完成后把结果投递回房间上下文，不能由后台线程直接改房间状态。

协程不自动并行：单线程协程只提供并发，CPU 密集任务会卡住事件循环；线程也不是越多越好，过多会带来栈内存、上下文切换和锁竞争。

## 14. 线程安全

### 是什么

线程安全是多个线程以任意交错方式访问同一对象时，结果仍符合预期：不丢数据、不重复、不读到中间状态，并且在需要时满足可见性与顺序要求。

### 为什么

看似一行的 count++ 实际包含读、加、写；并发执行会丢更新。CPU 缓存以及编译器/处理器重排序也会让一个线程看不到另一个线程已经写入的值。游戏中会表现为重复扣道具、房间状态跳变、排行榜错乱、偶发崩溃。

### 怎么做

优先顺序是“减少共享 → 串行所有权 → 合理同步”。

1. **不共享：** 不可变对象、线程本地数据和消息传递最容易保证正确。
2. **单写者/Actor：** 同一房间状态只由所属 Actor 修改，其他线程只发消息；这是游戏服务最常用的办法。
3. **互斥锁：** 用 mutex 保护完整业务不变量，而不只是保护单行代码。多个锁应规定固定获取顺序，避免死锁。
4. **读写锁：** 读远多于写时才可能有收益；要注意写饥饿和升级锁复杂度。
5. **原子变量/CAS：** 适合计数器、状态标志等简单状态。高竞争下 CAS 会自旋，还要关注 ABA 问题。
6. **并发容器：** 只保证容器的单次操作安全，不能保证“查询后判断再修改”这一整段业务原子。

验证方式包括并发单测、重复压测和竞态检测工具。关键资产操作还应有请求幂等键、版本号、审计流水和对账能力，防止一次竞争升级为资产事故。

## 15. CAP 原理：在游戏服务器开发里怎么选择

### 是什么

CAP 讨论的是**网络分区发生时**，分布式系统无法同时保证强一致性 C 与每次请求都可用 A；实际系统必须容忍网络分区 P。

- **C（一致性）：** 更准确地说是线性一致性，所有节点像读写同一份最新数据。
- **A（可用性）：** 每个未故障节点都能在有限时间内对请求给出非错误响应。
- **P（分区容忍）：** 节点之间断网、丢包时仍有明确行为。

因此不是平时在 CA、CP、AP 三选一，而是分区时决定优先 C 还是 A。

### 为什么

Gateway、房间、缓存、数据库、跨服服务之间随时可能超时或断网。若没有业务分级，会造成双重扣款、重复发奖，或为了等待强一致而让所有对局不可用。

### 怎么做：按业务选择

| 场景 | 通常倾向 | 落地方法 |
|---|---|---|
| 充值、货币/道具扣减、赛季最终奖励 | 偏 CP | 事务、唯一订单、幂等、对账；无法确认时进入处理中 |
| 对局位置、朝向、非关键特效 | 偏 AP | 新快照覆盖旧状态，允许短时不一致 |
| 匹配队列、在线状态 | 可用性优先且可补偿 | 超时、重连和状态修正 |
| 聊天/通知 | 取决于产品要求 | 至少一次投递加去重，或离线补偿 |

CAP 不是全部。还必须处理超时、重试、幂等、补偿与读写一致性。例如支付超时不代表失败，正确做法是按订单号查最终状态，而不是盲目再扣一次。

### 面试表达

“我不为整个游戏贴 CP 或 AP 标签，而是看数据价值。资产与最终结算宁愿短暂不可写，也不能双花；位置同步可以用新状态覆盖旧状态，优先低延迟与可用；跨服务操作统一配合超时、幂等和补偿。”

## 16. 状态同步和帧同步

### 是什么

| 项目 | 状态同步 | 帧同步（Lockstep） |
|---|---|---|
| 服务端发送 | 位置、速度、血量等快照或增量 | 每个逻辑帧的玩家输入 |
| 客户端工作 | 插值、预测、校正 | 用相同输入与确定性逻辑模拟 |
| 服务端权威 | 常见为强权威模拟 | 可汇总输入、校验或同时权威模拟 |
| 典型场景 | FPS、动作、开放世界 | RTS、MOBA、策略对战 |

### 为什么

网络延迟不能消除，只能隐藏和修正。状态同步持续下发“结果”，对端侧确定性要求低；帧同步只传“输入”，带宽小、回放方便，却要求各端模拟严格一致。

### 怎么做：状态同步

1. 服务端按固定 tick 模拟权威世界，按频率向 AOI 内客户端发送快照或差量。
2. 客户端对较早的两个状态插值，缓冲网络抖动；本地玩家可先预测自己的输入效果。
3. 收到服务端权威状态后，确认已处理输入，回滚到权威状态并重放尚未确认输入，这叫 reconciliation。
4. 使用序列号、时间戳、基线快照和 delta 压缩；丢失差量时等待或请求完整快照恢复。

### 怎么做：帧同步

1. 规定固定逻辑帧率和确定性输入格式，玩家只提交移动、施法目标等指令。
2. 服务端收集某帧输入，排序后广播；所有客户端在相同帧号执行相同输入。
3. 保证确定性：固定随机种子、固定点/整数计算、固定遍历顺序，避免依赖本地时间、平台差异或不一致浮点运算；地图和配置版本也必须一致。
4. 对迟到输入规定策略：小窗口等待、预测空输入、回滚重演或超时判定。定期校验关键状态 hash，不一致则用快照纠正。
5. 断线重连下发关键帧快照与其后的输入流，客户端快速追帧。

帧同步不天然抗作弊：客户端仍可能伪造输入、改内存或加速。强对抗游戏需要服务端校验输入，必要时服务端也做权威模拟。许多产品使用混合方案：核心战斗帧同步，外围实体/AOI 用状态同步。

## 17. Actor 模型

### 是什么

Actor 模型把并发系统拆成独立 Actor。每个 Actor 拥有私有状态和邮箱，一次只处理一条消息；Actor 间不直接共享内存，而通过异步消息通信。核心是“状态所有权 + 串行消息处理”。

### 为什么

多线程直接共享玩家或房间对象会带来锁竞争、死锁和难复现的竞态。游戏天然可按玩家、房间、公会、场景划分所有者：让同一房间操作在一个 Actor 内串行执行，逻辑更像单线程代码。

### 怎么做

客户端消息先到 Gateway，再路由给 RoomActor；RoomActor 独占对局状态并广播，PlayerActor 管在线与个人短期状态，MatchActor 管队列，持久化通过异步消息完成。

1. **划分边界：** 一个可变状态只归一个 Actor；不要让两个 Actor 直接写同一对象。
2. **设计消息：** 消息带命令、来源、请求 ID、逻辑时间或序列号。Actor 校验当前状态后再做状态机转换。
3. **处理异步回调：** 数据库或寻路任务完成后，结果必须重新投递回所属 Actor；后台线程不能直接改它的状态。
4. **调度与分片：** 多个 Actor 映射到有限 worker 线程；按 roomId/playerId 一致性哈希路由，集群中可做分片迁移。
5. **背压与故障：** 邮箱必须限制容量、限流并定义丢弃策略；慢 Actor 不能无限积压。设计监督重启、状态快照、日志和重放；定时器也应投递 tick/timeout 消息，而非外部直接修改状态。

### 注意点与面试表达

Actor 解决的是局部共享内存并发，不会自动解决跨 Actor 的转账、跨房间匹配或分布式一致性；这些仍需要消息协议、幂等与补偿。Actor 太细会增加消息开销，太粗会形成热点，房间 Actor 往往是合适粒度。

“我让 RoomActor 独占房间状态，网络线程和异步回调只投递消息，避免直接加锁改战斗数据。局部串行保证线程安全；跨 Actor 通过请求 ID、幂等和补偿协调，并通过邮箱长度和慢消费者监控保障稳定。”

## 总结：把知识串成一条服务端链路

玩家点击匹配后，Gateway 用 TCP/WebSocket 或 UDP/KCP 维护连接、鉴权和心跳；Match Actor 用 MMR 规则与模型评分组队；Room Actor 管理一局状态；核心战斗根据需要采用状态同步、帧同步或混合方案；AOI 九宫格筛选广播对象；寻路用 A*/NavMesh 加路径平滑和局部避障；排行榜用 Redis ZSet；过期任务用堆、时间轮或 ZSet；资产与结算按 CAP 思维优先一致性，并用事务、幂等、对账保证正确；最后用 Linux 观测、指标、日志和压测保障线上稳定。

复习每个主题时都追问四件事：**它维护什么状态？网络/并发失败时怎样？性能瓶颈在哪？如何观测、降级和恢复？** 这比只背定义更贴近真实开发与面试。
