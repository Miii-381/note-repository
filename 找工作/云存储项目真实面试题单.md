# 云存储项目真实面试题单

> 整理依据：2026-09-07 版个人简历、`云存储真实面经.txt`、`真实面经.txt`，以及当前项目代码复核材料。
>
> 适用方向：C++ 开发、Linux/C++、服务器后端、嵌入式 Linux 应用层。AI 功能不在当前简历的项目描述中，本题单不收录 AI 项目题。
>
> 核心原则：面试官只看得到简历，不会凭空知道函数名、接口名、端口号或字段名。本题单只保留能由简历直接触发，或在真实面经中反复出现的问题。

## 一、筛选结论

面试官最喜欢追问的不是“某个函数叫什么”，而是以下五件事：

- 项目真实性：为什么做、谁做的、部署在哪里、有没有用户和数据。
- 系统链路：一次请求如何经过各组件，数据最后落在哪里。
- 技术取舍：为什么选择该方案，不选本地文件、对象存储或其他方案。
- 异常与并发：网络断开、服务宕机、重复请求、两个用户同时上传时会怎样。
- 指标与证据：“高性能”“优化”“负载均衡”和“性能测试”怎样证明。

对两份真实面经聚类后，和当前简历最相关的频率大致如下：

| 真实面经主题 | 出现倾向 | 简历触发点 |
| --- | --- | --- |
| 项目背景、架构、个人贡献 | 极高 | 独立开发、唯一项目 |
| 大文件分片、顺序、完整性、断点续传 | 极高 | 简历“项目难点”第 2 条 |
| FastDFS 原理、选型、节点故障 | 极高 | 项目标题和主要技术 |
| 秒传、MD5、并发上传同一文件 | 高 | 简历“项目难点”第 1 条 |
| MySQL、Redis 分工与跨存储一致性 | 高 | 项目主要内容第 4 条 |
| Nginx 作用、与 FastDFS/FastCGI 的关系 | 高 | 项目主要内容第 2、3 条 |
| 负载均衡改进、指标采集和性能测试 | 极高且高风险 | 简历明确宣称已改进、已实现、已测试 |
| 分享、转存、权限与删除 | 中 | 简历“项目难点”第 3 条 |

## 二、S：必练 18 题

这些题组成真实项目面试的主干。每题准备“30 秒结论 + 2 分钟展开 + 两层追问”即可。

### 1. 项目真实性与架构

1. 这是学习项目、课程项目还是实际业务？为什么选择做云存储？
2. 项目是独立开发还是团队开发？代码来源是什么，你真正完成了哪些部分？
3. 项目开发了多久，按什么流程推进？部署在哪里，有没有真实用户或上线数据？
4. 请用 1～2 分钟介绍项目背景、核心功能、整体架构和个人贡献。
5. 从客户端发起请求开始，Nginx、FastCGI、FastDFS、MySQL 和 Redis 分别承担什么职责？
6. FastDFS 已经实现文件存储，你在开源框架之外做了哪些有技术含量的工作？
7. 为什么选择 FastDFS，而不是直接存到 Web 服务器本地目录？
8. Nginx 和 FastCGI 分别解决什么问题？Nginx 如何与 FastDFS 配合完成文件访问？

### 2. 上传、秒传与分片

9. 请完整讲一遍小文件普通上传流程，文件正文、文件元数据和用户关系分别落在哪里？
10. 秒传的判断和处理流程是什么？为什么秒传不等于“什么都不做”？
11. MD5 是对完整文件还是分片计算？大文件计算摘要怎样控制内存，发生哈希碰撞怎么办？
12. 两个用户同时上传同一个文件会不会重复存储？怎样避免“先查询、后上传”的并发竞态？
13. 请完整讲一遍大文件从切片、上传、记录进度到合并的流程。
14. 分片是串行还是并发上传？如何保证顺序、完整性和失败后的断点续传？
15. 网络中断、服务重启、分片缺失或重复合并时分别怎么办？合并时内存不足又怎么办？

### 3. 数据、一致性与稳定性

16. MySQL 和 Redis 分别保存什么？哪些 Redis 数据可从 MySQL 重建，哪些丢失后会直接影响会话？
17. 一次上传同时涉及 FastDFS、MySQL 和 Redis，部分成功时怎样处理一致性、幂等、重试和孤儿文件？
18. 当前部署有哪些单点？Tracker 或 Storage 下线后分别会发生什么，怎样扩成高可用？

## 三、S0：简历措辞必然触发的 6 道验真题

这 6 题的频率未必比架构题更高，但危险性最高，因为它们直接来自简历中的强结论。

19. 你说“改进了 FastDFS 的原负载均衡算法”，具体改了哪个决策环节，改进前后怎样选择节点？
20. 磁盘性能和任务使用率分别怎样定义、采集、归一化和防抖？采样频率依据是什么？
21. 是否真的修改并编译过 FastDFS 官方源码？实现位于哪里，如何接入原请求路径，有没有提交记录？
22. 你说“实现了优化并进行了性能测试”，测试环境、数据集、并发模型、基线、指标和原始结果是什么？
23. 简历写“支持一定数量客户端连接和及时响应”，这个数量和响应时间实际是多少，怎样测出来？
24. 当前云存储主业务为什么主要是 C FastCGI 程序？它和你投递 C++ 岗之间是什么关系？

当前代码复核结论：项目是单机 Docker Compose 部署的独立学习项目，没有生产用户和可信系统压测；当前仓库没有动态负载均衡、LRU-K 或相应性能测试的实现证据。投递前应优先修改简历中的“已改进、已实现、已测试”等措辞。在简历修改前，面试时必须明确区分“当前实现”和“调研后形成的改进设计”。

## 四、A：答完主问题后可能出现的 8 道追问

25. 是否调研过 MinIO、对象存储或其他分布式文件系统？选择标准是什么？
26. Tracker、Storage、Group 和 Client 怎样协作？Group 间与同组 Storage 间分别是什么关系？
27. 为什么记录已上传的分片集合，而不是只记录已上传字节数？两种方案各适合什么场景？
28. 多个用户共享同一份文件正文时，秒传、转存、分享、取消分享和删除怎样维护数据关系？
29. 分享排行榜为什么适合使用 Redis ZSet？成员和分数应该怎样设计？
30. 文件分享后怎样隐藏真实存储路径，并限制身份、有效期和访问次数？
31. 项目里最难的问题或印象最深的 Bug 是什么？如何复现、定位、修复和验证？
32. 如果现在重新设计项目，你会先改哪三处？如何监控上传成功率、P95/P99 延迟和资源使用？

到这里停止扩题。小文件治理、跨机房容灾、签名 URL 细节、分布式事务协议等内容，仅在目标岗位明确相关或面试官已经沿主问题追问时再展开，不进入日常主背题单。

## 五、不作为真实面试主练的源码定位题

下列问题对代码复核有价值，但面试官仅凭当前简历无法直接知道这些内部事实。除非你在回答中主动说出相关细节，否则只需理解，不要优先背诵。

- 某条 API 的具体路径是什么，它内部有几个固定分支？
- Nginx 配置了多少条路由，分别映射到哪些端口或 FastCGI 程序？
- Redis Hash 的字段名、Key 前缀和字符串拼接格式是什么？
- 哪个函数调用 `fdfs_upload_file`，父子进程之间具体怎样传递结果？
- 临时分片具体位于哪个目录，当前代码以什么字符串格式记录已上传编号？
- 合并代码先调用哪个 FastDFS API、后调用哪个 API，在哪一步删除临时文件？
- 当前哪些具体接口漏掉了 Token 校验，哪个图片分享字段没有真正参与鉴权？
- 六张表或十三个进程的精确名称是什么？

这类题已经在原有两份清单中统一标记为 `【源码复盘】`。该标记不表示面试官永远不会追问，而是表示：只有候选人先透露相应实现，或面试官提前审阅代码，问题才会自然出现。

## 六、回答边界

- 先回答当前真实实现，再说明缺口，最后谈改进方案。
- 不把 FastDFS、Nginx 等开源框架自带能力说成个人实现。
- 没有原始测试数据就不报并发量、吞吐、延迟或提升比例。
- 不把单 Tracker、单 Storage 的部署说成高可用集群。
- 不把传统业务后端说成全部由 C++ 编写。
- 不把调研过的 LRU-K、动态调度或计划中的功能说成已完成成果。

复习完成标准：32 题不用逐字背答案。优先练熟前 24 题，能够画架构图、讲清数据流、指出失败窗口，并承接两层追问；后 8 题按岗位和面试走向补充。
