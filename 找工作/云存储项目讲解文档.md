# 云存储项目讲解文档

> 事实基准：`D:\Desktop\AI_YunCunChu` 当前代码与配置。
> 本文只回答一个问题：**这个项目现在是怎么工作的**。所有"当前实现"的结论都能在代码或配置里找到依据；所有"改进方向"都单独标注，不代表已经具备的能力。
> 用途：面试前快速查找某个功能的实现说明，或在被追问细节时定位到具体文件与行号。

## 一、项目定位与部署形态

这是一个运行在 Linux 上的学习型云存储（网盘）系统，用 Docker Compose 做单机部署。前端是 React，传统业务后端是 13 个常驻的 C FastCGI 程序，文件正文存在 FastDFS，元数据存在 MySQL，登录状态和分片会话存在 Redis。

需要先记住三个边界，它们决定了后面所有回答的准确性：

第一，这是**单机学习环境**，不是高可用集群。整个系统只有一台主机、一个 MySQL 实例、一个 Tracker、一个 Storage、一个应用容器。

第二，传统业务模块**主要用 C 编写**，不能用"后端全部是 C++"来概括。只有后来迭代的 AI 模块（`ai_cgi.cpp`、`common/dashscope_api.cpp`、`common/faiss_wrapper.cpp`）使用 C++。

第三，仓库里**没有** Storage 侧的 LRU-K 缓存、动态反馈负载均衡、业务线程池、数据库连接池和内存池的源码。这些话题可以讲原理和改进设想，但不能说成项目成果。

### 1.1 三个容器的真实组成

`docker/docker-compose.yaml` 只定义了三个服务，它们都在同一台主机上，接入自定义 bridge 网络 `my_net`（子网 `172.30.0.0/16`），每个容器有固定 IP。

| 容器名 | IP | 对外端口 | 容器内实际运行的东西 | 数据持久化 |
| --- | --- | --- | --- | --- |
| `tc_fcgi_mysql` | 172.30.0.2 | 3307 → 3306 | MySQL 8 | `mysql_data` 命名卷 |
| `tc_fcgi_nginx_fastdfs` | 172.30.0.3 | 80 → 80，443 → 443 | Nginx（2 个 worker）、1 个 Tracker、1 个 Storage、`ngx_fastdfs_module` | `fastdfs_data` 命名卷 |
| `tc_fcgi_app` | 172.30.0.4 | 10000–10012 | Redis（本机 127.0.0.1:6379）、13 个 FastCGI 常驻进程 | 只挂载了 `client.conf`，无数据卷 |

这里最容易讲错的一点是"三容器"的含义。Nginx、Tracker 和 Storage 并不是三个独立容器，而是**挤在同一个容器**里；FastCGI 和 Redis 也共用另一个容器。所以"三容器"指的是三个服务单元，不是三台机器，更不是三层高可用。

### 1.2 数据持久化的实际差别

三个容器的持久化情况完全不同，这个差别直接决定了故障后会发生什么。

MySQL 和 FastDFS 的数据分别落在 `mysql_data` 和 `fastdfs_data` 两个命名卷里，所以执行普通的 `docker compose down` 再启动，业务数据还在，只有显式删除卷才会丢失。

应用容器的情况相反。它的 Redis 和 `/tmp/chunks` 都在容器可写层，**没有挂载任何数据卷**。所以容器一旦重建（`docker compose down` 后再启，或加 `--force-recreate`），登录 Token 会全部失效、分片上传会话会全部丢失、未合并的分片文件也会消失，用户必须重新登录、重新上传。

### 1.3 健康检查覆盖不到的地方

Compose 为三个容器都配了健康检查，但检查范围很窄：

- MySQL 检查 `mysqladmin ping` 是否成功。
- Nginx 容器检查 `https://127.0.0.1:443/` 是否返回 2xx 状态码。
- 应用容器**只检查 10000 端口是否有进程在监听**（`lsof -i :10000`）。

这一点在项目实测中出过一次真实事故：`chunk_merge` 进程因为启动顺序问题崩溃退出、10011 端口没有监听，但应用容器依然显示为 healthy，因为健康检查只盯着 10000 端口。所以**容器状态为 healthy 不等于所有功能可用**。

## 二、Nginx 承担的职责

Nginx 是整个系统的唯一入口，`docker/nginx_fastdfs/nginx.conf` 里配置了它的全部行为。

### 2.1 四件事

第一是**协议与端口**。80 端口的请求会被 301 重定向到 443，443 使用仓库内的自签名证书，TLS 握手和加解密全部由 Nginx 完成，后端 CGI 只处理明文 HTTP。

第二是**静态资源与前端路由**。React 打包产物由 Nginx 直接返回，前端单页路由通过 `try_files` 回退到入口页。静态资源禁用了浏览器缓存（配置了 `Cache-Control: no-cache`）。

第三是**API 路由分发**。13 条 `/api/*` 路径各自通过 `fastcgi_pass` 转发到 `172.30.0.4` 上对应的端口。这是纯粹的路径分发，**配置里没有 `upstream`**，所以不能说项目做了应用层负载均衡。

第四是**文件正文下载**。`location ~/group([0-9])/M([0-9])([0-9])` 这一段把所有匹配 FastDFS 路径格式的请求交给 `ngx_fastdfs_module`，由它直接从本地磁盘读取 Storage 的文件并返回。这条路径**完全不经过 FastCGI、MySQL 和 Redis，也不做任何鉴权**。

### 2.2 进程模型与连接行为

Nginx 配置了 `worker_processes 2`，每个 worker 的 `worker_connections` 是 1024。它采用事件驱动模型，能够接住大量并发连接——但这只是 Nginx 自身的能力，后端能不能跟上取决于 FastCGI 那一侧，见下一节。

连接行为要分成两段看：

- **客户端到 Nginx**：`keepalive_timeout 65`，客户端侧开启了长连接。
- **Nginx 到 FastCGI**：配置里**没有 `fastcgi_keep_conn`**，该指令默认为关闭，所以 Nginx 每处理一个请求都会新建一条到后端的 TCP 连接，处理完就断开。代价是反复建连，并会在后端侧堆积 `TIME_WAIT`。

请求体大小由 `client_max_body_size 12m` 限制。这个值必须大于单片 10 MiB，否则单个分片就会被 Nginx 挡掉。如果客户端发送的请求体超过这个限制，Nginx 返回的是 **413**，而不是 500。

超时配置按接口分别设置：`/api/chunk_upload` 是 `fastcgi_read_timeout 300`（5 分钟），`/api/chunk_merge` 和 `/api/ai` 是 600（10 分钟）。其他接口使用默认的 60 秒。这几个值决定了后端排队多久会被判定为超时并返回 504。

## 三、13 个 FastCGI 程序

### 3.1 端口与路由的对应关系

`docker/fastcgi_app/start.sh` 逐个拉起 13 个程序，每个程序独占一个端口。

| 端口 | 程序 | 路由 | 是否校验 Token |
| --- | --- | --- | --- |
| 10000 | `login` | `/api/login` | 不需要（登录入口本身） |
| 10001 | `register` | `/api/reg` | 不需要（注册入口本身） |
| 10002 | `upload` | `/api/upload` | **没有** |
| 10003 | `md5` | `/api/md5` | 有 |
| 10004 | `myfiles` | `/api/myfiles` | 有（2 处） |
| 10005 | `dealfile` | `/api/dealfile` | 有（1 处） |
| 10006 | `sharefiles` | `/api/sharefiles` | **没有**（公共列表，可接受） |
| 10007 | `dealsharefile` | `/api/dealsharefile` | **没有** |
| 10008 | `sharepicture` | `/api/sharepic` | 部分：`share`、`normal` 有，`cancel`、`browse` 没有 |
| 10009 | `chunk_init` | `/api/chunk_init` | 有 |
| 10010 | `chunk_upload` | `/api/chunk_upload` | **没有** |
| 10011 | `chunk_merge` | `/api/chunk_merge` | 有（但不校验会话归属） |
| 10012 | `ai` | `/api/ai` | 有（属于后续迭代，不进入主口径） |

### 3.2 进程模型：并发度实际是 1

每个程序的主循环都是 `while (FCGI_Accept() >= 0)`：拿到一个请求、处理完、回到循环开头拿下一个。程序内部没有创建任何处理请求的线程，也没有线程池。IO 全部是阻塞式的，13 个源文件里没有出现 `select`、`poll`、`epoll` 或非阻塞 fd 的设置。

关键在于启动方式。`start.sh` 里所有命令都是：

```
spawn-fcgi -a 0.0.0.0 -p 10010 -f /app/bin_cgi/chunk_upload
```

**没有 `-C` 参数**。`spawn-fcgi` 的 `-C` 用于指定子进程数量，省略时只启动一个。所以每个端口只有 1 个进程，而且这个进程是阻塞式地串行处理请求。

这意味着：**同一个接口的第二个请求必须排队等第一个处理完**。比如上传一个 10 MiB 分片要写 FastDFS，耗时较长，这期间发送到 10010 端口的其他分片请求全部在排队。排队时间一旦超过 Nginx 的 `fastcgi_read_timeout`，客户端就会收到 504。

正确的表述是"项目运行了 13 个常驻 FastCGI 进程"，而不是"项目依靠 13 个进程实现了高并发"。

### 3.3 唯一与线程沾边的地方

公共日志模块 `common/make_log.c` 里定义了一个互斥锁 `ca_log_lock`，写日志之前加锁、写完解锁。这个锁保护的是**单个进程内部对日志文件的写入**，不是业务逻辑的并发控制。

同一个文件上半部分还有一段用 `pthread_create` 创建日志线程的代码，但整段被注释掉了，没有编译进程序。所以准确的说法是：业务逻辑单线程，日志模块里有一个活跃的互斥锁。

项目里确实用到多进程的地方有两类：一是执行外部命令（上传时调用 `fdfs_upload_file`、查询文件信息时调用 `fdfs_file_info`），用 `fork` 加 `execlp` 创建一次性子进程，用完即退出；二是 13 个 CGI 本身由 `spawn-fcgi` 拉起。

## 四、数据模型

### 4.1 六张主链路表

`docker/mysql/init.sql` 里共有 8 张表，其中 6 张属于传统云存储主线，2 张属于 AI 迭代。回答项目主体时讲这 6 张。

| 表 | 存什么 | 关键字段与约束 |
| --- | --- | --- |
| `user_info` | 用户账号 | `user_name` 唯一、`nick_name` 唯一；保存密码摘要和盐 |
| `file_info` | **一份物理文件** | `md5` 有唯一约束 `uq_md5`；保存 `file_id`、`url`、`size`、`type`、引用计数 `count` |
| `user_file_list` | **用户目录项** | 用户、MD5、文件名、分享状态 `shared_status`、下载量 `pv`；**没有唯一约束** |
| `user_file_count` | 冗余计数 | `user` 有唯一约束；普通用户存文件数，特殊用户名还被用来存公共分享总数 |
| `share_file_list` | 公开分享记录 | **没有任何唯一约束** |
| `share_picture_list` | 图床分享 | 有 `urlmd5` 和 4 位 `key` 字段；无唯一约束，`urlmd5` 也没有索引 |

### 4.2 为什么要拆成 `file_info` 和 `user_file_list`

这是整个数据模型的核心设计，也是理解秒传、转存和引用计数的前提。

`file_info` 代表**一份物理正文**，以 MD5 为主键去重。`user_file_list` 代表**某个用户的目录里有一个什么名字的文件**，通过 `user` 和 `md5` 关联到 `user_info` 和 `file_info`。

拆开之后，同一个 MD5 可以被多个用户同时持有：`file_info` 里只有一条记录，`user_file_list` 里有多条记录，`file_info.count` 记录被多少个人持有。这正是"文件正文只存一份、多个用户共享"的实现方式。

由此推导出的不变量是：**只有引用计数归零，才应该删除物理正文**。

### 4.3 约束不足带来的实际问题

初始化脚本没有外键，也没有给 `user_file_list` 和 `share_file_list` 建立能够阻止重复关系的唯一约束。代码是靠"先查一次、没有才插入"来防重复的，这在并发下会失效：两个请求同时查询、都查不到、都插入，就会产生重复记录。

`file_info` 的 `uq_md5` 唯一约束是**做对了的一处**，它挡住了最严重的一种脏数据——同一个 MD5 出现两条 `file_id` 互相矛盾的记录。

`user_file_count` 这类冗余计数字段长期一定会漂移，正确的心态不是保证它绝对准确，而是定期用 `COUNT(*)` 校正。

## 五、注册、登录与 Token

### 5.1 密码是怎么保存的

密码经过两次摘要，不是"无盐 MD5"。

1. React 前端先对明文密码做一次 MD5。
2. 注册服务端生成 8 个随机字节，编码成 16 位十六进制盐（`reg_cgi.c:133` 的 `generate_salt`）。**盐优先从 `/dev/urandom` 读取**，只有在打开失败时才退化成 `rand()`。
3. 服务端计算并保存 `MD5(salt + 前端MD5)`（`reg_cgi.c:237-248`）。
4. 登录时从 `user_info` 取出该用户的盐，用同样的方式计算 `MD5(salt + 客户端传入的pwd)` 并比对。

所以手工测试时**必须传明文密码的 MD5**，直接传明文会返回 `code1`。前端在 `Login.js` 里会先调用 `calculateMD5(password)` 再发请求。

这个方案仍然不适合生产环境：MD5 计算太快，没有密钥派生函数的计算成本，攻击者拿到用户表后仍可高效地离线爆破弱密码。它比"无盐 MD5"好，但正确方向是 bcrypt、scrypt 或 Argon2id。

### 5.2 Token 的生成与保存

登录成功后，`login_cgi.c:188` 的 `set_token` 按以下步骤生成 Token：

1. 用户名与 4 个 `rand()%1000` 的随机数拼接，随机种子是 `time(NULL)`。
2. 用 DES 加密（`DesEnc`）。
3. Base64 编码，避免出现不可见字符。
4. 对 Base64 结果再算一次 MD5，得到定长的 32 位十六进制字符串。

即 `MD5hex(base64(DES(username + 4×(rand%1000))))`。

生成后用 `SETEX username 86400 token` 写入 Redis（`rop_setex_string`）。**Key 就是用户名**，Value 是 Token，TTL 固定 86400 秒（24 小时）。

校验由 `common/util_cgi.c:272` 的 `verify_token` 完成：以请求中的用户名为 key 从 Redis 取出 Token，再用 `strcmp` 与请求携带的 Token 比较，取不到或对不上都返回失败。

### 5.3 三个容易答错的边界

**这不是 JWT。** JWT 依靠签名做无状态校验，服务端不需要查存储；当前实现必须到 Redis 读取会话状态才能判断 Token 是否有效。Redis 一丢，所有登录态立即失效。

**这不是滑动过期。** TTL 在写入时就固定为 86400 秒，后续任何一次校验都只读不续期。

**这是单会话语义。** Redis 始终以用户名为 key，同一用户再次登录时新的 `SETEX` 会直接覆盖旧 Token，旧设备立即失效。项目不支持多设备各自保留独立会话。

## 六、上传链路

上传有三条路径，由前端在文件大小上分流：先算 MD5 调 `/api/md5` 做秒传预检，未命中且不超过 10 MiB 走普通上传，超过 10 MiB 走分片上传。

### 6.1 秒传预检 `/api/md5`

前端用 SparkMD5 按 2 MiB 分块读取文件，计算出**整个文件**的 MD5（不是分片 MD5），然后把用户、Token、MD5、文件名发到 `/api/md5`。

服务端（`md5_cgi.c`）依次做两件事：

1. 查询 `file_info` 是否存在该 MD5。不存在说明服务器上还没有这份正文，无法秒传。
2. 存在则再查 `user_file_list`，看当前用户是否已经拥有同名同 MD5 的目录项。

根据结果返回三个码之一：`5` 表示用户已拥有、`0` 表示秒传成功、`1` 表示不能秒传需要真实上传。

秒传成功时，服务端不传输任何正文，只做三项数据更新：把 `file_info.count` 加一、往 `user_file_list` 插一条归属记录、更新 `user_file_count`。

> 注意：`md5_cgi.c` 源码注释里写的是 `004/005/006`，但实际返回的是 `5/0/1`（`return_status(HTTP_RESP_FILE_EXIST)` / `HTTP_RESP_OK` / `HTTP_RESP_FAIL`）。**以实际返回码为准**，前端 `images.js` 里判断的也是 `0`、`5`、`1`。

### 6.2 普通上传 `/api/upload`

适用于不超过 10 MiB 的文件。

前端发送 `multipart/form-data`，字段顺序是 `file`、`user`、`md5`、`size`——**这个顺序必须匹配后端 `recv_save_file()` 的解析顺序**，否则字段会错位。

服务端处理流程：

1. 一次性把整个请求体读进内存（`malloc(len)` + `fread`）。
2. 通过 `strstr` 定位 boundary，解析出文件正文的起止位置和各个字段。
3. 把正文写入本地临时文件。
4. 校验解析出的字节数是否等于客户端声明的大小——**只比长度，不重新计算正文 MD5**。
5. 再次查询数据库尝试去重（这一步无法阻止并发重复）。
6. 通过 `pipe()` + `fork()` + `execlp("fdfs_upload_file", ...)` 上传正文，父进程从管道读取 `file_id`。
7. 再执行一次 `fdfs_file_info`，然后删除本地临时文件。
8. 用配置里的 Storage Web 地址（`172.30.0.3:80`）拼接 HTTP URL，依次写入 `file_info`、`user_file_list`、`user_file_count`。

这里有一个必须说清楚的缺口：**`/api/upload` 没有 Token 校验**，`user` 字段直接取自 multipart 表单。也就是说上传者的身份完全由客户端自己声明。

### 6.3 分片上传

超过 10 MiB 的文件走分片链路，分三步。

**第一步：`/api/chunk_init` 初始化（10009）**

请求携带用户、Token、文件名、完整 MD5、文件大小和分片总数。服务端校验 Token 后，以 `chunk:{md5}` 为 key 在 Redis 建一个 Hash，字段包括 `filename`、`filesize`、`chunk_count`、`user`、`uploaded`，然后执行 `EXPIRE 86400`。同时在磁盘上创建 `/tmp/chunks/{md5}/` 目录，返回空的 `uploadedChunks`。

**第二步：`/api/chunk_upload` 逐片上传（10010）**

前端按 10 MiB 切片，对每一片发送 `POST /api/chunk_upload?md5=xxx&index=N`，正文是原始二进制。

服务端从 URL 参数解析出 `md5` 和 `index`，把整片读入内存，写入 `/tmp/chunks/{md5}/{index}`，**写盘成功之后**再把编号追加到 Redis 的 `uploaded` 字段。

顺序是"先落盘、再更新索引"，这个方向是正确的；反过来会产生"索引说有、磁盘上没有"的记录。

**第三步：`/api/chunk_merge` 合并（10011）**

前端全部传完后调用合并接口。服务端先校验 Token，从 Redis 读出 `chunk_count` 和 `filesize`，然后：

1. 调用 `bind_existing_file_to_user`，如果服务器上已有该 MD5 的物理文件，就直接建立归属关系并返回，跳过合并。
2. 调用 `verify_all_chunks`，逐个检查 `0` 到 `chunk_count-1` 的临时文件**是否存在**。
3. 把第 0 片通过 `storage_upload_appender_by_filename1` 上传，创建一个 FastDFS appender 文件，成功后立即 `unlink` 本地第 0 片。
4. 对第 1 到 N-1 片依次调用 `storage_append_by_filename1` 追加到同一个 `file_id`，**每追加成功一片就立即删除本地对应的分片文件**。
5. 全部成功后把文件信息写入 MySQL，删除 Redis 会话键，删除临时目录，返回 `code=0`。

**面试中容易被追问的内存问题**：合并过程**不会把整个文件读进内存**。它走的是 FastDFS 基于文件路径的接口（`_by_filename1`），每次只传一个分片的路径，由 FastDFS 客户端自己去读文件。所以合并 10 GB 的文件也不会因为内存不够而失败，这与"把分片全部读进内存再拼"的做法有本质区别。

### 6.4 上传链路的关键缺口

以下都是当前实现的真实边界，适合在被追问时主动说明。

- `/api/upload` 和 `/api/chunk_upload` 都没有 Token 校验。
- 服务端**不重新计算正文摘要**，只信任客户端提交的 MD5。普通上传只比长度，分片上传连长度都不比。
- 分片接口不校验 `index` 的上下界、不校验单片大小、不校验单片摘要，也不核对 Redis 会话是否存在及其所有者。
- `file_info`、`user_file_list`、`user_file_count` 三步写入是独立的 `mysql_query`，**没有事务**。任何一步失败，前面已执行的部分不会回滚，会留下孤儿正文或错误计数。
- FastDFS 写入成功而 MySQL 写入失败，会在 Storage 上留下无人引用的孤儿文件。

## 七、分片与断点续传

### 7.1 涉及的状态与存放位置

| 状态 | 存放位置 | 写入者 |
| --- | --- | --- |
| 已上传的分片编号 | Redis Hash `chunk:{md5}` 的 `uploaded` 字段（逗号分隔字符串） | `chunk_upload_cgi.c:149-163` |
| 文件名、大小、片数、用户 | 同一个 Hash 的其他字段 | `chunk_init_cgi.c:186-197` |
| 分片正文 | `/tmp/chunks/{md5}/{index}` | `chunk_upload_cgi.c:113-115` |
| 会话过期时间 | 整把 key 的 `EXPIRE 86400` | `chunk_init_cgi.c:200` |

这里要理解 Redis 数据的性质。它保存的两类数据性质完全不同：共享排行榜是 MySQL 的投影，丢了可以回源重建；而**分片会话是 Redis 自己是权威的中间状态**，MySQL 里没有任何等价记录。所以 Redis 一旦丢失，服务端就不知道这个文件传了多少片、还差哪几片，没有任何地方可以回查。

### 7.2 续传是怎么实现的

前端每次上传前都会先调 `chunk_init`。服务端发现 Redis 里已经有 `chunk:{md5}` 这把 key 时，就读取 `uploaded` 字段并返回给前端，前端把它解析成一个 Set，循环时跳过集合里已有的编号，只补传缺失的分片。进度条也从已上传数量开始算，所以续传时不会从零开始。

能这样做的前提是**分片编号可以复现**：MD5 算的是整个文件，同一个文件的 MD5 恒定，前端切片边界也就固定，第 3 片永远是同一段内容。

### 7.3 三个必须如实说明的边界

**第一，续传元数据"存了不校验"。** `chunk_init` 在 key 已存在时**只判断 key 是否存在，命中就无条件返回旧的 `uploaded`**。`filename`、`filesize`、`chunk_count` 虽然写进了 Redis Hash，但全项目从没有任何地方把它们读出来与本次请求比对（`chunk_count` 只在合并时被读取使用一次）。后果是：换了一个同名但大小不同的文件，服务端会直接续传，不会重新开始。

**第二，会话只按 MD5 命名，没有用户维度。** 两个不同用户上传相同内容时会共享同一个会话和同一个临时目录。

**第三，磁盘分片没有垃圾回收。** Redis 会话会在 86400 秒后过期，但 `/tmp/chunks` 目录**没有任何定时清理任务**（全项目只有 `start.sh:53` 的一句 `mkdir -p /tmp/chunks`）。键过期之后，磁盘上的目录和分片文件会一直保留。

因此，"支持断点续传"的准确表述是：**在应用容器存活、Redis 会话和 `/tmp/chunks` 都还在的 24 小时窗口内，客户端可以补传缺片**。它不支持跨容器重建恢复，因为 Redis 和临时目录都没有持久卷。

## 八、合并失败后会发生什么

这是整个项目最值得讲的一个失败窗口，因果链完整，适合在面试中展开。

### 8.1 四个失败点的处置完全不同

| 失败点 | 代码位置 | 本地分片 | Redis | FastDFS | 能否重试 |
| --- | --- | --- | --- | --- | --- |
| 分片完整性检查不通过 | `chunk_merge_cgi.c:577` | 保留 | 保留 | 未触碰 | 可以，补传后重试 |
| Redis 元数据读取失败 | `chunk_merge_cgi.c:557,565` | 保留 | 已失效 | 未触碰 | 需要重新初始化并全量重传 |
| **合并中途追加失败** | `chunk_merge_cgi.c:315-320` | **部分已被永久删除** | 保留且状态错误 | 留下孤儿文件 | **永久卡死** |
| 合并成功但 MySQL 写入失败 | `chunk_merge_cgi.c:603` | 全部已删除 | 保留 | 留下孤儿文件 | **永久卡死** |

> 表中不同失败点的行为差异，来自代码里对失败的处理方式不一致：完整性检查失败、Redis 读取失败这两处都是 `continue` 跳过本次请求，尚未开始任何破坏性操作；而追加失败只 `break` 跳出循环、落库失败则直接返回，这两处此前已经删除了部分或全部分片。

### 8.2 卡死的完整链条

问题出在删除动作与"合并成功"解耦了。

`chunk_merge_cgi.c:300` 在第 0 片上传成功后立即 `unlink` 本地文件；`chunk_merge_cgi.c:307-326` 的循环里，每片追加成功后也立即 `unlink`，而追加失败时只执行 `break`——既不删除 FastDFS 上的半成品，也不回滚已经删掉的本地分片。

以 8 个分片、第 3 片追加失败为例：

```
本地磁盘：  [0][1][2] 已删除 | [3][4][5][6][7] 还在
FastDFS：   appender 文件已含 0/1/2，成为无人引用的孤儿
Redis：     uploaded = "0,1,2,3,4,5,6,7"   ← 一个字都没有被修改
```

用户重试时，`chunk_init` 发现 key 存在，返回"全部分片已上传"；前端跳过所有分片直接调合并；而合并的第一步 `verify_all_chunks` 检查第 0 片时发现文件已经被删，检查必然失败。**用户自己走不出这个状态，只能等 24 小时后 Redis TTL 过期。**

根本原因是：**Redis 索引与磁盘实体之间没有任何一致性校验**。`uploaded` 记录的是"某一时刻这片写盘成功了"，但没有任何机制保证文件现在还在。而 `verify_all_chunks` 只在合并时执行，那时已经太晚。

### 8.3 两个附带问题

**落库的 size 不可信。** `store_fileinfo_to_mysql` 的 `size` 取自 Redis 里的 `filesize`（`chunk_merge_cgi.c:603`），**不是合并后的实际结果**。所以即使某一片追加静默失败，数据库里记录的仍是最初申报的大小，无法通过查库发现文件已损坏。

**`verify_all_chunks` 只检查存在性。** `chunk_merge_cgi.c:233` 只对每个编号做 `stat`，不校验单片长度、单片摘要或合并后的总大小。一个被网络截断的分片，`stat` 同样能查到文件在，检查就会通过，最终合并出一个损坏的文件而系统发现不了。

### 8.4 改进方向（不是当前能力）

最小改动是把所有 `unlink` 推迟到 MySQL 写入成功之后统一清理，并在追加失败时调用 `fdfs_delete_file` 回收半成品。代价是临时目录要多占一份完整文件的空间。

更彻底的做法是先在本地按顺序拼成完整文件，再一次性上传给 FastDFS，让流程变成单次操作。代价是需要与文件等大的临时磁盘空间。

另外需要补充一条：**全项目的 `fdfs_delete_file` 只在 `dealfile_cgi.c:401`（删除用户文件）和 `sharepicture_cgi.c:658`（取消图床分享）这两处被调用**，`chunk_merge_cgi.c` 里没有任何删除 FastDFS 文件的代码，所以合并失败留下的半成品永远不会被回收。

## 九、`uploaded` 字符串的三个问题

`uploaded` 的格式是逗号拼接的字符串，例如 `"0,1,2,3"`。它有三个层次的问题。

### 9.1 缓冲区上限约 2.83 GB

```c
char uploaded[1024] = {0};                              // chunk_upload_cgi.c:149
rop_hash_get(redis_conn, redis_key, "uploaded", uploaded);

char new_uploaded[1024] = {0};                          // chunk_upload_cgi.c:155
sprintf(new_uploaded, "%s,%d", uploaded, chunk_index);  // :156  没有长度检查
```

上限需要按实际位数累加计算，不能拿"一个数字 4 字节"去乘，因为位数是变化的：

| 分片数 N | 数字位数之和 | 逗号数 | 总长 | 结果 |
| --- | --- | --- | --- | --- |
| 283 | 10 + 180 + 549 = 739 | 282 | 1021 | 刚好放下 |
| 284 | 10 + 180 + 552 = 742 | 283 | 1025 | 需要 1026 字节，越界 |

按每片 10 MiB 计算，**上限是 283 片，约 2.83 GB**。这里索引 0–9 是 1 位数字，10–99 是 2 位，100 以上是 3 位。

需要注意的是失败形态：**越界写的是栈上的局部数组，所以结果不是返回错误，而是进程崩溃**。如果编译时开了 `-fstack-protector`，会直接 `abort()`。用户看到的现象是"传到一半失败"，前面那些分片残留在 `/tmp/chunks/{md5}/`。

读取侧同样越界。`common/redis_op.c:711-715`：

```c
len = reply->len > VALUES_ID_SIZE ? VALUES_ID_SIZE : reply->len;  // VALUES_ID_SIZE = 1024
strncpy(value, reply->str, len);
value[len] = '\0';        // len == 1024 时写入 value[1024]，越界 1 字节
```

### 9.2 索引层不幂等

```c
sprintf(new_uploaded, "%s,%d", uploaded, chunk_index);   // 直接拼接，不查重
```

同一个分片传两次，字符串会变成 `"0,1,5,5,2"`，再传一次变成 `"0,1,5,5,5,2"`。

要分三层来看这个问题：**文件层面是正确的**，因为落盘用的是 `open(..., O_CREAT | O_WRONLY | O_TRUNC, 0644)`，重传即覆盖；**索引层面是错的**，字符串越滚越长，会提前撞到上面那个 1024 上限；**功能上不出错**，因为前端用 `Set` 做了去重（`picture_bed/src/services/images.js`），但状态在持续劣化。

标准答案：**幂等性在文件层面靠 `O_TRUNC` 保住了，在索引层面没有。**

### 9.3 并发下会撕裂文件

两个客户端同时上传同一序号的同一片时，`open(O_TRUNC)` 之后是三段 `write` 循环（`chunk_upload_cgi.c:124-131`）。如果 A 写完 6 MB、B 截断并重写 3 MB、A 继续从 offset 6 MB 写，最终文件会变成"B 的前 3 MB + A 的后 4 MB"的撕裂内容。

**这个问题实际碰不到**，因为 `start.sh` 的 `spawn-fcgi` 没有加 `-C`，每个端口单进程串行 accept，两个请求会排队。

但这是运气而不是设计。一旦有人为了提速给 `chunk_upload` 加上 `-C 4`，这个洞立刻暴露。正确的做法是写临时文件再 `rename` 原子替换。

### 9.4 为什么不能简单地把缓冲区改大

分片编号是稠密的整数集合，直觉上"把 1024 改成 4096 就行了"是行不通的，有两个原因。

**第一，`VALUES_ID_SIZE` 不只是缓冲区大小，它同时是数组步长。** `include/redis_op.h:26` 定义 `typedef char (*RVALUES)[VALUES_ID_SIZE];`，而 `src_cgi/sharefiles_cgi.c:537` 用 `calloc(count, VALUES_ID_SIZE)` 做批量分配。这个常量一改，sharefiles 那边的批量内存会按比例放大——改成 64 KB，一次批量查询就要吃掉 64 MB。

**第二，读取侧是静默截断。** `redis_op.c:711-715` 的 clamp 逻辑不会报错，`rop_hash_get` 依然返回 0 表示成功。改成 `snprintf` 等于用静默的数据错误换掉崩溃，比现在好，但仍然是错的。

正确的方向是换数据结构。分片编号天然匹配 Redis 的 Bitmap：上传完一片执行 `SETBIT chunk:{md5}:uploaded {index} 1`，查询用 `GETBIT`。这样既没有长度上限（100 万个分片只占 125 KB），又天然原子、天然幂等，还顺带解决了重复追加的问题，而且完全不影响 `VALUES_ID_SIZE`。

如果只想止血不动结构，可以在 `chunk_init` 里加一条显式上限校验（`chunk_count > 283` 直接返回错误码），把崩溃变成明确的报错。

### 9.5 Redis 字符串本身的大小限制

Redis 单个 value 的上限是 **512 MB**，来自 Redis 自身协议和 SDS 设计，不是可配项。283 个分片撑死用到 1024 字节，差着五个数量级。内存开销也不必担心：SDS 头约 20 字节，每个 Hash field 的 dictEntry 约 50 字节。

所以"Redis 字符串有大小限制吗"这个追问的答案是：有，但和这个问题无关，瓶颈完全在应用层的固定栈数组。

## 十、文件列表、分享与转存

### 10.1 个人文件列表 `/api/myfiles`

接口通过 URL 的 `cmd` 参数区分操作：`count` 返回文件总数，`normal` 返回普通列表，`pvasc`/`pvdesc` 按下载量升序或降序。列表请求还需要 `start` 和 `count` 两个分页参数。

服务端校验 Token 后，用一条联表查询把 `user_file_list` 和 `file_info` 关联起来，取出文件名、MD5、URL、大小、类型等字段，编码成 JSON 返回。SQL 里的 `start` 和 `count` 是直接 `sprintf` 拼进 `limit` 子句的。

### 10.2 分享的实现

分享是**发布到公共窗口**，不是指定接收人的点对点授权。整个请求里没有 `receiver_user`、没有权限级别、没有有效期。

创建分享（`dealfile_cgi` 的 `cmd=share`，**这个分支校验 Token**）会依次更新三处状态：

1. 把 `user_file_list` 中该记录的 `shared_status` 改成 1。
2. 往 `share_file_list` 表插入一条分享记录。
3. 更新 Redis：往 `FILE_PUBLIC_ZSET` 有序集合加入成员，往 `FILE_NAME_HASH` 加入文件名映射。

有序集合的 member 是 `md5 + filename` 直接拼接的字符串（中间**没有分隔符**，理论上存在拼接歧义），score 是下载量。

分享**不会**增加 `file_info.count`，也不会复制 FastDFS 正文。它只是让这份正文出现在公共列表里。

### 10.3 Redis 与 MySQL 在分享链路中的角色

`share_file_list` 是持久化的事实来源，Redis 中的 ZSet 和 Hash 只是查询加速层。

这个关系在排行榜接口里体现得最清楚：服务端先用 `ZCARD` 取 Redis 里的成员数，再查 MySQL 里记录的公共分享总数，**两者不一致时**清空 Redis 的 `FILE_PUBLIC_ZSET` 和 `FILE_NAME_HASH`，然后从 `share_file_list` 全量重建。所以缓存丢了不影响正确性，回源即可。

### 10.4 转存 `/api/dealsharefile?cmd=save`

转存不重新上传正文。服务端先查询目标用户是否已拥有同名同 MD5 的文件，没有的话就新增一条 `user_file_list` 记录、把 `file_info.count` 加一、更新目标用户的 `user_file_count`。

结果是多个用户共享同一份物理正文，各自的目录里显示为自己的文件。

### 10.5 取消分享 `/api/dealsharefile?cmd=cancel`

反向操作：把 `shared_status` 改回 0、公共分享总数减一、从 `share_file_list` 删除记录、从 Redis 的 ZSet 和 Hash 中移除。

取消分享**不会**删除用户自己的拥有关系，**不会**减少 `file_info.count`，也**不会**删除正文。它只把文件从公共窗口撤下来。别人在你取消之前已经转存过的副本，不受影响。

### 10.6 分享链路的鉴权缺口

`dealsharefile_cgi` 整个模块没有调用过 `verify_token`。它的三个操作——`cancel`（取消分享）、`save`（转存）、`pv`（公共下载计数）——**都不需要登录即可调用**，前端也只发送用户名、MD5 和文件名，不发 Token。

这意味着调用者可以伪造用户名，尝试替别人取消分享，或向任意用户名转存。

图床模块 `sharepicture_cgi.c` 的情况类似但有分支差异：`share`（1103 行）和 `normal`（1126 行）校验了 Token，而 `cancel`（1140 行起）和 `browse`（1152 行起）**没有**。由于 `browse` 是公开接口且返回 `user` 字段，拿到分享链接后先调 `browse` 得到用户名，再构造 `cancel` 请求，就能取消他人的图床分享。

## 十一、下载与引用计数删除

### 11.1 下载为什么没有权限判断

下载走的是 FastDFS 直链。`myfiles_cgi` 和 `sharefiles_cgi` 会把完整的 URL 返回给前端，形如 `http://172.30.0.3:80/group1/M00/00/00/xxx`。浏览器拿到这个 URL 后直接请求 Nginx，匹配到 `location ~/group([0-9])/M([0-9])([0-9])`，由 `ngx_fastdfs_module` 读磁盘返回。

**这条路径不经过任何鉴权**。所以当前项目判断"能不能下载"的依据是**用户有没有下载链接**，而不是"用户有没有权限"。任何人只要拿到 URL，就能下载文件，不需要登录，也没有次数限制。

需要澄清一个容易混淆的点：`verify_token` 这个函数**本身是正确的**。它以用户名为 key 从 Redis 取 Token，和请求里的 Token 做 `strcmp`，取不到或对不上都返回失败，不存在空 Token 绕过的情况。问题在于**它被调用的位置不够全**。

### 11.2 下载计数与正文分离

`pv` 计数是通过单独的接口更新的：个人文件的下载量走 `dealfile?cmd=pv`（校验 Token），公共分享的下载量走 `dealsharefile?cmd=pv`（不校验 Token）。

但真正的文件下载是浏览器直接访问 FastDFS URL，**不经过应用层**。计数请求与正文请求完全独立，所以计数可以漏记、重复或伪造。`pv` 是访问统计，不是下载凭证。

另外，`pv` 的更新是"先 `select pv`，再 `update pv = 旧值+1`"，不是原子操作，并发下会丢计数。

### 11.3 删除与引用计数

删除文件（`dealfile_cgi.c` 的 `del_file`）的流程是：

1. 先判断这个文件是否已被分享（先查 Redis ZSet，未命中再查 MySQL 的 `shared_status`）。
2. 如果已分享，删除 `share_file_list` 里的记录、公共分享总数减一、从 Redis 的 ZSet 和 Hash 移除。
3. 查询调用者自己的 `user_file_count`（`dealfile_cgi.c:542`），取不到就报错返回。
4. 删除 `user_file_list` 里的归属记录（`dealfile_cgi.c:585`）。
5. 删除该用户的 AI 检索记录（`dealfile_cgi.c:595`），并**检查 `mysql_affected_rows`**（`dealfile_cgi.c:603`）。
6. 查询 `file_info.count`（`dealfile_cgi.c:610`），减一后更新（`dealfile_cgi.c:628`）。
7. 如果计数归零，删除 `file_info` 记录并调用 `remove_file_from_storage` 删除 FastDFS 上的物理正文（`dealfile_cgi.c:659`）。

### 11.4 这条链路上的越权风险

删除判断有两个缺口，把它们连起来会形成一条完整的越权链。

**缺口一：不检查文件归属。** 第 3 步只检查调用者自己在 `user_file_count` 表里有没有记录——只要这个用户拥有过任何文件就通过，**完全不管要删的这个文件是不是他的**。

**缺口二：删除归属记录之后不检查影响行数。** 第 4 步的 `delete from user_file_list` 之后没有检查 `mysql_affected_rows`。如果这个用户根本不拥有该文件，删除语句影响 0 行，代码不会察觉，继续往下走，第 6 步照样把 `file_info.count` 减一。

两者结合：任意一个登录用户，从分享列表里拿到一个 MD5 和文件名，反复调用删除接口，就能把别人文件的引用计数一路减到 0，触发物理删除，导致这个文件在全站都下载不了。

有一个细节可以侧面说明这是**疏漏而不是不懂**：同一个函数在第 5 步处理 AI 记录时**检查了** `mysql_affected_rows`，说明作者知道这个 API，只是在删除归属记录那一步漏掉了。

> 这段结论来自逐行阅读代码，**尚未在容器中实际构造请求验证**。面试时如果对方追问"你实际验证过吗"，应如实说明这是代码分析的结果。

## 十二、图床分享子系统

后端实现了 `share`、`normal`、`cancel`、`browse` 四类操作，但**当前 React 前端和服务层没有接入这个 API**，所以它不是现有前端的活跃功能。

创建分享时会生成三个值：`urlmd5 = MD5(filemd5 + 时间 + 随机数)`、一个 4 位十六进制的 `key`（提取码）、以及 `pv = 0` 的记录。

但保护逻辑没有闭环：**创建接口的响应只返回 `urlmd5`，不返回 `key`**；而 `browse` 分支只按 `urlmd5` 查询，**不校验 `key`**。所以数据库里虽然有"提取码"这个字段，访问过程中从来没有强制校验过它。

准确的回答是：图片分享有 `urlmd5` 这个不透明标识和 `key` 这个提取码字段，但**浏览链路没有强制提取码，取消分享也缺少鉴权**，属于未完成的权限边界。

## 十三、代码复核后的改进方向

以下都是"知道方向但没有落地"的内容，面试时不能说成已具备的能力。

**鉴权。** 为所有写接口补充统一鉴权，并由服务端根据 Token 推导用户身份，不再信任请求体里的用户名。

**内容完整性。** 服务端复算 SHA-256，建立内容占位状态（`UPLOADING`/`READY`/`FAILED`），摘要、大小和所有权都由服务端约束。

**事务与约束。** 为物理文件、用户关系、分享关系补充合适的唯一键，把相关的多步 MySQL 更新放进事务。

**分片上传重做。** 使用独立的 `upload_id` 而不是直接用 MD5，用 Bitmap 或唯一键原子记录分片状态，引入合并状态机和抢占机制，把临时目录和 Redis 挂上持久卷，并增加过期回收任务。

**跨存储一致性。** 建立 FastDFS 操作的 outbox 记录、重试和定期对账清理任务。

**下载授权。** 修复图床提取码闭环，用带签名的短期 URL 替代永久直链，避免绕过业务授权。

**输入校验。** 用一个统一的输入校验层处理长度、类型和格式，文件名走白名单，SQL 改用参数化查询。
