## 一、项目整体与架构

### 1. 介绍一下这个项目的架构，把一次上传请求的完整链路串起来

这是一个基于 FastDFS 的云存储系统，前端用 React，后端是 13 个 FastCGI 程序，中间用 Nginx 做入口和路由转发。

按请求真实走过的顺序讲会更清楚。以一次普通文件上传为例：

浏览器先把文件读进内存，同时计算整个文件的 MD5，然后把文件正文和用户信息打包成 `multipart/form-data` 发出去。请求到达 Nginx 之后，Nginx 根据 URL 匹配到 `location /api/upload`，通过 `fastcgi_pass` 转发给 10002 端口上的上传模块。

上传模块先解析 multipart 正文，把文件正文落到本地临时文件，然后调用 FastDFS 客户端把文件上传到 Storage，拿到一个 `file_id`。接着它把这个 `file_id` 拼成完整的 HTTP 下载地址，连同文件大小、类型、MD5 一起写进 MySQL 的 `file_info` 表，再往 `user_file_list` 表插一条归属记录，最后把用户的持有文件数加一。全部完成之后，模块把结果返回给 Nginx，Nginx 再返回给浏览器。

整个链路里，Nginx 负责路由和静态资源，FastCGI 负责业务逻辑，FastDFS 负责文件正文的存取，MySQL 存元数据，Redis 存登录态和分片会话。

需要说明的是，这个项目没有做服务分层，13 个 CGI 是并列的，每个对应一组接口。

### 2. Nginx 在这个项目里起什么作用？为什么不直接让前端访问 FastCGI

Nginx 承担四件事。

第一是统一入口。前端的请求全部发到 443 端口，由 Nginx 根据路径分发到不同的 FastCGI 端口，前端不需要知道后端有几个模块、分别在哪。

第二是承载 HTTPS。TLS 握手和加解密由 Nginx 完成，后端 CGI 只需要处理明文 HTTP。

第三是直接提供静态文件下载。FastDFS 提供了 `ngx_fastdfs_module`，Nginx 加载这个模块之后，可以直接从本地磁盘读 Storage 的文件并返回，请求不会进入 FastCGI。

第四是缓存控制和跨域头。项目里禁用静态资源的浏览器缓存、给每个接口加 CORS 头，都是在 Nginx 层配置的。

至于为什么不直接暴露 FastCGI：FastCGI 走的是自己的二进制协议，浏览器不认识；而且 FastCGI 进程本身不具备 HTTPS、静态文件服务、连接管理这些能力。所以中间这一层是必要的。

这里要补充一个理解边界：Nginx 能接住大量并发连接，但这不代表整个系统的并发能力高。后端每个端口只有一个进程，第 55 题会具体讲。

### 3. 一次请求从 HTTP 到 FastCGI 具体发生了什么

Nginx 解析完 HTTP 的请求行、请求头和请求体之后，根据 URI 匹配到对应的 `location`，然后进入 `ngx_http_fastcgi_module`。这个模块把请求的元数据（方法、URI、请求头等）编码成 `FCGI_PARAMS` 记录，把原始请求体编码成 `FCGI_STDIN` 记录，通过 TCP 发送到对应端口。

后端程序里链接了 `libfcgi`，主循环调用 `FCGI_Accept()` 时会解析这些记录，把元数据放进环境变量，把请求体放进标准输入。所以业务代码取参数用的是 `getenv("QUERY_STRING")`、`getenv("CONTENT_LENGTH")` 和 `fread(..., stdin)`。

业务处理完之后，程序用 `printf` 输出响应头和正文，`libfcgi` 把它包装成 `FCGI_STDOUT` 和 `FCGI_END_REQUEST` 返回给 Nginx，Nginx 再转成 HTTP 响应。

所以 FastCGI 是 Nginx 和业务进程之间的通信协议，不是另一个调度程序。本项目把 FastCGI 接入代码和业务代码编译在同一个可执行文件里。

### 4. 项目怎么构建的，有哪几个模块，你主要做了什么

三个容器：MySQL 单独一个；Nginx、Tracker、Storage 在同一个容器里；13 个 FastCGI 程序和 Redis 在第三个容器里。

13 个模块分别是 login、register、upload、md5、myfiles、dealfile、sharefiles、dealsharefile、sharepicture、chunk_init、chunk_upload、chunk_merge，以及后续迭代的 ai。

我做的主要是传统业务链路这部分：秒传判断、普通上传、分片上传与合并、文件列表、分享转存、引用计数删除，以及 Nginx 路由配置和 Docker 部署。

**这里要如实说明：这是学习型项目，我是在参考已有实现的基础上完成环境搭建、部署和问题排查，源码读过但没有从零亲手敲过。** 部署和排障过程是真实做的，比如处理过 CRLF 行尾导致容器反复重启、宿主机 80 端口被占用、`chunk_merge` 因启动顺序崩溃这三个实际问题。

### 5. 为什么选择 FastDFS，有没有调研过替代方案

选 FastDFS 主要是三个原因。

第一是它自带 Tracker 和 Storage 的角色划分，扩容的时候只需要新增 Storage 并注册到 Tracker，不用改业务代码。

第二是它提供 Nginx 模块，下载可以直接由 Nginx 读本地磁盘返回，路径短，不用经过应用层。

第三是它部署简单，单机就能跑起来，适合当时的学习环境。

调研这块我要如实说明：**我当时只做到了能把它跑起来并接入业务，没有做过横向对比测试**。我了解过 MinIO 和 Ceph 的存在，知道 MinIO 兼容 S3 接口、Ceph 有统一的 RADOS 对象层，但我没有实际部署过，也说不出它们在具体指标上的差异。如果问"为什么不用 MinIO"，我只能说当时的选型依据是 FastDFS 的 Nginx 模块和部署成本，不是对比测试的结果。

## 二、注册、登录与安全

### 6. 密码经过几次摘要？盐保存在哪里？

密码经过两次摘要，不是"无盐 MD5"。

前端先用 MD5 对明文密码算一次，把结果发给服务端。注册时服务端生成 8 个随机字节，编码成 16 位十六进制盐，保存在 `user_info.salt`，然后计算并保存 `MD5(salt + 前端MD5)`。登录时服务端取出该用户的盐，用客户端传来的 `pwd` 算 `MD5(salt + 客户端pwd)` 再比对。

所以手工测试时必须传明文密码的 MD5，直接传明文会返回 `code1`，因为前端会先调 `calculateMD5`。

盐的生成优先读 `/dev/urandom`，只有在打开失败时才退化成 `rand()`。

### 7. 为什么带盐的双层 MD5 仍不适合生产环境

随机盐可以避免相同密码得到相同的存储结果，但 MD5 计算速度太快，没有密钥派生函数提供的计算成本。攻击者一旦拿到用户表，仍然可以对弱密码做高效率的离线猜测。

当前项目确实做到了逐用户随机盐，但如果用于生产，还是要换成 bcrypt、scrypt 或 Argon2id。这属于改进方向，不是项目已经具备的能力。

### 8. Token 怎么生成？Redis 里 Key、Value 和 TTL 分别是什么？

登录成功后，`set_token` 先把用户名和 4 个 `rand()%1000` 的随机数拼接起来，然后依次做 DES 加密、Base64 编码、再算一次 MD5，最终得到长度固定为 32 位十六进制的字符串。

生成后用 `SETEX username 86400 token` 写入 Redis。**Key 就是用户名**，Value 是 Token，TTL 固定 86400 秒（24 小时）。校验时根据用户名读取 Token，用 `strcmp` 直接比较，读取操作不会刷新过期时间。

### 9. 为什么这个 Token 既不是 JWT，也不是滑动过期？

JWT 通常依靠签名在服务端做无状态校验，不需要查存储。当前实现必须到 Redis 读取会话状态才能确认 Token 是否有效，所以 Redis 一丢失，所有登录态立即失效，用户必须重新登录。

TTL 在写入时就固定为 86400 秒，后续访问不会延长有效期，所以它不是滑动过期。

### 10. 同一个用户再次登录会怎样？支持多设备独立会话吗？

Redis 始终以用户名作为 key，同一用户再次登录时，新的 `SETEX` 会覆盖旧 Token，旧设备上的 Token 立即失效。

所以当前实现表达的是**一个用户只保留一个有效会话**，不支持多设备各自维护独立会话。如果要支持，可以给每个会话保存一条独立记录，或者用独立的会话 ID 而不是用户名作 key。

### 11. 哪些写接口没有校验 Token？会造成什么越权？

我逐个接口核对过调用点。`/api/login` 和 `/api/reg` 作为入口本身不需要 Token，这是合理的。`/api/sharefiles` 是公共分享列表，不校验也可以接受。

问题在这几个：**`/api/upload`、`/api/chunk_upload`、`/api/dealsharefile` 完全没有调用过 `verify_token`**。图床模块 `/api/sharepic` 是分支遗漏——`share` 和 `normal` 有校验，`cancel` 和 `browse` 没有。

其中 `dealsharefile` 承担取消分享、文件转存和公共下载计数，缺乏校验意味着调用者可以伪造用户名，替别人取消分享或向任意用户名转存。`/api/upload` 的 `user` 字段直接来自 multipart 表单，也就是说**上传者的身份完全由客户端自己声明**。

### 12. SQL、日志和 CORS 还有哪些问题？

当前代码普遍使用 `sprintf` 拼接 SQL，没有预处理语句，而用户名和文件名又可能由用户控制，所以存在注入风险。**全项目只有 `ai_cgi.cpp:555` 调用过 `mysql_real_escape_string`**，那是我后来写的 C++ 模块；其余 12 个 C 模块一律裸拼。

login 模块会把请求里的密码字段直接写进日志。Nginx 给所有 `/api` 接口配了宽松的 CORS 规则，直接反射请求的 `Origin` 并允许携带凭证，没有来源白名单。这些都属于当前实现的安全缺陷。

### 13. 服务端应该怎样确认用户身份？

更合理的方式是让服务端根据自己签发的 Token 找到对应会话，再从会话里取得可信的用户身份，而不是直接相信请求体或查询参数里的用户名。

当前多数接口仍把用户名当作输入参数，Token 更像一个"是否允许继续执行"的开关。比如 `chunk_merge` 会直接用请求里传入的 `user` 去查数据库。所以统一身份推导方式，是后续安全改造的重点。

## 三、秒传与普通上传

### 14. 秒传是怎么实现的？和普通上传有什么区别？

普通上传是真的把文件正文传给服务端。秒传不传正文，只传一个 MD5，服务端查到这个 MD5 已经存在，就直接给当前用户建立一条归属记录。

前置动作是一样的：两者都需要客户端先算出整个文件的 MD5。

服务端在 `/api/md5` 里做两次判断：先查 `file_info` 看物理文件是否存在；存在的话再查 `user_file_list`，看当前用户是否已经拥有同名同 MD5 的目录项。根据结果返回三个码——`5` 表示用户已拥有，`0` 表示秒传成功，`1` 表示不能秒传、需要真实上传。

秒传成功时，服务端不传输任何正文，只做三项更新：把 `file_info.count` 加一、往 `user_file_list` 插一条记录、更新 `user_file_count`。

（源码注释里写的是 `004/005/006`，但实际返回的是 `5/0/1`，以实际返回码为准。）

### 15. 秒传为什么还要写用户关系和引用计数？

`file_info` 里只保留一份文件正文的信息，秒传不是再复制一份正文，而是让不同用户的目录项共同引用同一个物理文件。

所以服务端虽然不需要上传文件内容，但仍然要写 `user_file_list` 建立归属关系，并同步维护文件引用计数和用户文件计数。

### 16. MD5 是对整个文件算的吗？10GB 的文件也要全算一遍吗？

是对整个文件算的，**确实是全量计算**。

前端用的是增量式方式：按 2 MiB 分块读出来，每一块送进 MD5 上下文更新，最后取出结果。所以不需要一次性把 10 GB 读进内存，但**需要把 10 GB 完整读一遍**。

这意味着两个后果：大文件的秒传判断并不快，前端要花时间读完整个文件，这段时间用户是能感知到的；而且这个计算发生在上传之前，是纯客户端的开销。

放在服务端算是不行的：那就意味着文件已经传完了，秒传也就失去意义了。所以**放在前端算的本质原因是省带宽**，代价是客户端要花时间。

### 17. 换 SHA-256 能解决什么？不能解决什么？

SHA-256 能降低摘要碰撞的风险，也更符合现代安全规范。但它不能自动解决并发条件下的"检查—执行"竞态，也不能补上鉴权或事务。

而且要注意：这个项目真正需要防的不是数学意义上的哈希碰撞，而是**攻击者直接编造一个 MD5 字符串去调秒传接口**。这个成本是零，写个循环就能刷。换任何摘要算法都防不住这种攻击，因为问题在授权模型，不在算法强度。

### 18. 两个不同文件 MD5 碰撞了怎么办？

先说结论：**这个项目没有做防碰撞处理，因为在实际场景下 MD5 碰撞不需要考虑。**

要区分两种完全不同的东西。第一种是数学意义上的碰撞，也就是刻意构造两个内容不同但 MD5 相同的文件，这需要大量算力，而且生成出来的是有特定格式的垃圾数据，不是用户正常上传的文件。第二种是攻击者编造一个 MD5 字符串去调秒传接口，成本是零。

这个项目真正需要防的是第二种，而它现在的实现恰好防不住第二种，因为它只检查 MD5 是否存在，不验证请求方是否真的持有文件内容。

### 19. 两个用户同时上传同一个文件会怎样？

分几种情况。

**如果两个用户同时上传同一个文件、走普通上传**，两边都会完整走一遍流程：各自上传一份正文到 FastDFS，各自尝试往 `file_info` 插记录。因为 `file_info` 的 MD5 字段有唯一约束，第二个插入会失败。但当前代码**没有处理这个失败的情况**，也没有"竞争失败就复用已有记录"的逻辑。所以两个并发的相同文件上传会有一个报错，而且 FastDFS 上可能留下没人引用的孤儿文件。

**如果是同一个用户的同一个文件重复上传**，情况类似，`user_file_list` 因为没有唯一约束，可能会产生重复记录。

这就是典型的"先检查、后执行"竞态。上传后再补查一次 MD5 只能发现已经出现了重复，无法阻止两份正文被写入。要根本解决，需要建立唯一的内容记录，在上传前用 `UPLOADING`/`READY`/`FAILED` 状态占位，用原子操作决定由哪个请求负责真实上传。

### 20. 普通上传是否校验 Token、是否重新计算正文 MD5？

`upload_cgi` 没有调用 `verify_token`，所以普通上传接口不校验 Token。

`recv_save_file` 也只是比较解析出的正文长度和请求中声明的长度，**不会根据实际文件内容重新计算摘要**。换句话说，服务端直接信任了客户端提交的 MD5。

### 21. 为什么全量读取 multipart 请求体会带来内存问题？

`upload_cgi` 会先执行 `malloc(len)` 为整个请求体分配内存，再通过 `fread` 一次性读入并解析。文件越大，占用的内存越多。

当前项目已经让大文件走分片上传，所以这个接口主要处理不超过 10 MiB 的小文件，内存压力暂时可接受。这也是把上传拆成两条链路的原因之一。

### 22. `fork`、`exec` 和管道在上传模块里各自做什么？

项目没有把 FastDFS 的 API 直接嵌入上传模块，而是用了外部命令。

父进程先用 `pipe()` 创建管道，再 `fork()`。子进程用 `dup2(fd[1], STDOUT_FILENO)` 把自己的标准输出重定向到管道写端，然后 `execlp("fdfs_upload_file", conf_path, filename)` 启动 FastDFS 命令行程序。命令行的输出就是 `file_id`，直接写进管道。父进程从管道读端读到 `file_id`，用 `trim_space` 去掉首尾空白，然后 `wait(NULL)` 回收子进程。

之后还会再执行一次 `fdfs_file_info` 查询文件信息，同样是通过管道拿输出。

这是一种"FastCGI 程序调用外部命令、再通过管道读结果"的实现方式，进程模型更接近传统 CGI 与外部工具的组合。

### 23. FastDFS 上传成功但 MySQL 写入失败会怎样？

会在 Storage 上留下**孤儿文件**——正文已经写进去了，但没有任何数据库记录引用它，也没有任何机制会去清理它。

反过来，如果数据库记录写入了但 FastDFS 上传失败，用户关系就会指向一个实际不存在的文件，用户点下载会直接 404。

当前项目的多处数据库更新是由 `sprintf` 拼接后分别执行的，既没有外键约束，也没有覆盖完整链路的事务，所以中途失败时容易产生不一致的数据。

### 24. 上传同时和 MySQL、Redis、FastDFS 打交道，怎么保证要么全成功要么全失败？

**当前实现没有做到这一点，我要如实讲。**

上传流程确实要依次操作多个组件：FastDFS 存正文，MySQL 写文件记录和归属记录，Redis 存分片会话。这些操作是分步执行的，**没有用事务包起来，也没有补偿机制**。

具体来说，普通上传的写入分成三步：先往 `file_info` 插文件记录，再往 `user_file_list` 插归属记录，最后更新 `user_file_count`。三步各自独立执行，任何一步失败，前面已经执行的部分不会回滚。

我能说出这个问题的严重程度：如果是 `file_info` 写成功、`user_file_list` 写失败，用户会看到上传失败，但文件记录已经存在。下一次别的用户上传同一个 MD5 触发秒传，就会命中这条记录，从而"拥有"一个其实从来没上传成功过的文件，下载时直接 404。

如果要修，方向是把这几步写进一个 MySQL 事务，让它们要么全部提交要么全部回滚。**这是我知道但还没有落地的改进方向**，不是已经具备的能力。

## 四、大文件分片与断点续传

### 25. 大文件分片上传的完整流程是怎样的？

超过 10 MiB 的文件走分片链路，分三步。

**第一步是初始化。** 前端算出整个文件的 MD5，连同文件名、大小、分片总数发给 `/api/chunk_init`。服务端校验 Token 后，在 Redis 里建一个 Hash，键名是 `chunk:{md5}`，字段包括文件名、大小、分片总数、用户名和已上传编号，然后设置 24 小时的过期时间，同时在磁盘上创建分片临时目录 `/tmp/chunks/{md5}/`。

**第二步是逐片上传。** 前端按 10 MiB 切片，对每一片调用 `/api/chunk_upload?md5=xxx&index=N`，正文以二进制形式放在请求体里。服务端先把这一片写到 `/tmp/chunks/{md5}/{N}`，写成功之后，再把编号追加到 Redis 里那个 `uploaded` 字段。

注意这里的顺序：**先落盘，再更新索引**。如果反过来，就会出现"索引说有、磁盘上没有"的记录。

**第三步是合并。** 前端全部传完之后调用 `/api/chunk_merge`。服务端先逐个检查每一片对应的临时文件是否存在，确认齐全以后，用 FastDFS 的 appender 接口把第一片作为基础文件上传，后面每一片依次追加进去，每追加成功一片就删掉本地的那一片。合并完成之后把文件信息写进 MySQL，最后清理 Redis 里的会话键。

### 26. 分片合并时服务器内存不够怎么办？

**不会因为内存不够而失败**，因为合并过程没有把整个文件读进内存。

它用的是 FastDFS 基于文件路径的接口（`storage_upload_appender_by_filename1` 和 `storage_append_by_filename1`），每次只传一个分片的路径，由 FastDFS 客户端自己去读文件、追加到远端。所以哪怕合并 10 GB 的文件，进程本身的额外内存占用也就是几个文件路径字符串。

这和"把分片全部读进内存再拼成一个 buffer"的做法有本质区别。如果是后者，10 GB 的文件必然失败。

### 27. 断点续传是怎么实现的？

前端每次上传之前都会先调用 `chunk_init`。服务端发现 Redis 里已经有 `chunk:{md5}` 这个键，就把里面记录的已上传编号返回给前端，前端把它们解析成一个集合，循环时跳过这些编号，只补传缺失的分片。进度条也从已上传数量开始算，所以续传时不会从零开始。

能这样做的前提是**分片编号可以复现**。因为 MD5 算的是整个文件，同一个文件的 MD5 恒定，前端切片的边界也就固定，第 3 片永远是同一段内容。

### 28. 为什么记录分片编号，而不是只记录已上传的字节数？

因为分片编号是天然的对齐单位。前端的切片边界是由 `CHUNK_SIZE` 决定的，第 N 片对应的字节区间是 `[N×10MiB, (N+1)×10MiB)`，所以只要知道哪些编号传完了，就能直接算出还缺哪几段。

如果改成记录字节数，服务端就需要额外知道"这 N 个字节是完整的第几片"，而最后一片的长度和前面不一样，按字节续传还得再记录每个分片的实际长度。当前实现没有这个数据。

另外，编号集合天然适合去重和判断完整性，而单纯的字节数在乱序到达时会很难处理。

### 29. 当前"断点续传"能跨容器重建吗？

**不能。** 准确的说法是：在应用容器存活、Redis 会话和 `/tmp/chunks` 都还在的 24 小时窗口内，客户端可以补传缺片。

`/tmp/chunks` 位于 FastCGI 容器的可写层，没有挂载数据卷；Redis 同样没有数据卷。容器重建后，本地分片和 Redis 会话都会消失，服务端不再知道之前传到哪了，用户只能从头开始传。

### 30. Redis 会话过期后，磁盘上的分片会一起删除吗？

不会。Redis 只负责让 `chunk:{md5}` 这把 key 在 86400 秒后过期，`/tmp/chunks` 目录本身**没有任何垃圾回收或定时清理机制**。全项目只有 `start.sh` 里的一句 `mkdir -p /tmp/chunks`。

所以即使 Redis 会话已经消失，磁盘上的目录和分片文件仍会长期保留，逐渐形成孤儿文件。

### 31. 分片上传使用长连接吗？底层是什么协议？

要分成两段看。

客户端到 Nginx 这一段开了长连接，`nginx.conf` 里配了 `keepalive_timeout 65`。但 Nginx 到 FastCGI 那一段**没有开**，配置里没有 `fastcgi_keep_conn`，这个指令默认是关闭的，所以每个请求都会新建一条到后端的 TCP 连接，处理完就断开。

底层协议是 HTTP over TCP。上传的正文用的是 `POST` 加 `Content-Length`，因为前端切片之后长度是已知的，不需要用 `Transfer-Encoding: chunked`。

分片本身是**应用层的约定**，HTTP 协议里没有"分片"这个概念。13 个分片就是 13 个完全独立的 HTTP 请求，服务端之间互不知道彼此的存在。

### 32. 1000 个分片会一次性全部发给 Nginx 吗？

不会。前端是一个普通的 `for` 循环，每次 `await` 当前分片上传完成，才继续下一片。所以是**顺序发送**，任意时刻只会有 1 个分片请求在途，不会把 1000 个请求同时压给 Nginx。

### 33. 分片上传是并发还是顺序的？为什么这么设计？

当前是顺序的，前端逐片 `await`。

这样设计的一个直接好处是**天然避免了分片之间的相互干扰**，服务端不需要处理并发写入同一会话的竞态。分片上传接口本身没有加锁，`uploaded` 字段的更新也不是原子的，如果是并发上传这些问题会立刻暴露。

代价是总耗时等于所有分片串行传输的时间之和，大文件会比较慢。如果要改成并发，需要同时解决三件事：`uploaded` 的读-改-写竞态、分片写入的原子性、以及后端的并发处理能力（当前每个端口只有 1 个进程）。

### 34. 分片乱序到达会影响最终文件吗？

不会影响最终内容，因为每个分片写的是独立的文件路径。第 0 片写 `/tmp/chunks/{md5}/0`，第 1 片写 `/tmp/chunks/{md5}/1`，互相不覆盖，谁先落盘都不影响结果。合并的时候是按编号顺序读取的，磁盘上的物理顺序不等于写入顺序。

需要区分两个层次的"有序"：TCP 保证的是**同一个连接内的字节流有序**，这是传输层的事；而分片编号保证的是**应用层多个独立请求之间的顺序**。因为每个分片是一个独立的 HTTP 请求，可能走不同的 TCP 连接，所以传输层的保序帮不上忙，必须靠应用层自己用编号来对齐。

### 35. 合并前如何判断分片完整？当前代码实际检查了什么？

当前做法是在合并之前逐个调用 `stat` 检查每一片的临时文件是否存在，缺任何一片就返回失败，让前端补传。

但这个检查**只验证文件存在，不校验每个分片的大小和内容**。所以如果某个分片因为网络原因被截断了，`stat` 同样能查到文件在，检查就会通过，最终合并出一个损坏的文件，而系统发现不了。

当前前端是逐个 `await` 顺序上传的，所以截断分片不太容易出现。但如果改成并发上传，没有分片级别的校验就会变成实际问题。

### 36. 为什么边追加边删除本地分片会破坏失败重试？

因为删除动作把重试需要的原始数据提前扔掉了。

代码是每追加成功一片就 `unlink` 掉对应的本地分片。如果第 3 片追加失败，那么第 0、1、2 片的本地文件已经被删了，用户想重试就必须把这 3 片重新传一遍。

更严重的是，Redis 里的 `uploaded` 字段**从头到尾没有被更新过**，它仍然记录着"所有分片都传完了"。所以用户重试时，`chunk_init` 返回"全部已上传"，前端跳过所有分片直接调合并，而合并的第一步完整性检查就会因为第 0 片已被删除而失败。

**用户自己走不出这个状态**，只能等 24 小时后 Redis TTL 过期。这个问题的完整因果链在第九节。

### 37. 网络中断后当前能恢复到什么程度？

要按文件大小分两种情况。

**小文件走普通上传**，中断就意味着整个请求失败，临时文件可能残留在本地，**当前没有清理机制**，需要重新上传。

**大文件走分片上传**，已经传完的分片不会丢，因为它们已经落在磁盘上、编号也已经记进 Redis。用户重新上传时，`chunk_init` 会返回已上传的编号列表，前端跳过这些编号、只补传缺失的部分。

但有一个前提要说清楚：**续传的前提是 Redis 里的会话还在**。这个键设置了 24 小时过期，超过之后服务端就不再知道之前传到哪了。

### 38. 多个合并请求同时到达会怎样？

当前**没有合并锁，也没有状态机**，所以两个合并请求可以并发执行。

后果是两边都会去读同一个文件列表、都会调用 appender API。由于第一片是用 `storage_upload_appender_by_filename1` 创建新文件，两个请求会各自创建一个 FastDFS 文件，然后各自追加，最终产生两份完整的正文，但数据库里只会有 `file_info` 的一条记录（因为 MD5 唯一约束），另一份成为孤儿。

要修的话，需要在 Redis 里用一个原子操作（比如 `SET NX`）抢占合并权，并引入 `UPLOADING`/`MERGING`/`DONE` 状态机，让重复请求返回同一个结果。

## 五、MySQL 与 Redis

### 39. MySQL 和 Redis 分别存了什么？

按用途分两类来看比较清楚。

**MySQL 是权威存储**，存的是长期数据：`user_info` 存用户账号，`file_info` 存文件的 MD5、`file_id`、下载地址、大小、类型和引用计数，`user_file_list` 存用户和文件的归属关系，`user_file_count` 存每个用户持有的文件数，`share_file_list` 和 `share_picture_list` 存分享记录。这些数据即使 Redis 整个清空也能从 MySQL 恢复。

**Redis 存的是两类东西，性质不一样。**

一类是**缓存的加速副本**。共享文件排行榜就属于这一类，它存在有序集合里，是 `share_file_list` 表的一个投影。Redis 里没有这个键不代表文件没被分享，只代表缓存没命中，回查 MySQL 就能补上。

另一类是**Redis 自己是权威的中间状态**，这类数据在 MySQL 里没有对应记录。登录 Token 和分片上传会话都属于这一类。分片会话存的是文件名、大小、分片数、用户和已上传编号，这些信息 MySQL 里没有；临时分片正文存在 `/tmp/chunks` 下面，MySQL 里也没有。**所以 Redis 一旦丢失，服务端就不知道这个文件传了多少片、还差哪几片，没有任何地方可以回查。**

区分这两类的意义在于判断故障后果：缓存丢了回源重建就行，中间状态丢了只能靠重传或者超时清理兜底。

### 40. Redis 比 MySQL 快是什么原因？

主要有三点。

第一是**数据位置不同**。Redis 的数据全部放在内存里，MySQL 的数据最终落在磁盘上，即使有缓冲池，也会遇到需要真正读盘的情况。

第二是**数据结构和访问路径不同**。Redis 的读写是针对具体数据结构的直接操作，比如往有序集合里加一个成员；MySQL 要先解析 SQL 语句、再经过查询优化器生成执行计划、最后走 B+ 树索引查找。

第三是**协议和连接模型不同**。Redis 用的是简单的文本协议，而且是单线程处理命令，没有锁竞争；MySQL 有连接管理、事务、MVCC 这些机制要维护。

不过要补一句：这个项目用 Redis 的主要理由**不是因为它快**，而是因为有些数据本来就该放在内存里、并且需要过期时间。登录 Token 和分片会话都是临时状态，设 24 小时过期自动清理，用 MySQL 反而要自己做清理任务。

### 41. 怎么保证 MySQL 和 Redis 的数据同步？

**当前没有做同步机制，我要如实讲。**

项目里没有 binlog 订阅、没有消息队列、没有定时对账任务。Redis 和 MySQL 之间的一致性完全靠"写的时候按顺序都写一遍"来维持。

具体到分享链路，写入顺序是：先更新 MySQL 的 `user_file_list.shared_status` 和 `share_file_list`，再更新 Redis 的 ZSet 和 Hash。如果 MySQL 成功而 Redis 失败，缓存就落后了。

不过分享这条链路有一个补救机制：排行榜接口会先用 `ZCARD` 取 Redis 里的成员数，和 MySQL 里记录的公共分享总数比对，**数量不一致就清空 Redis 并从 `share_file_list` 全量重建**。所以缓存落后最终会被修正。

但登录 Token 和分片会话没有这个待遇，因为它们在 MySQL 里根本没有副本，丢了就是丢了。

### 42. 数据库表是怎么设计的？几张表之间怎么关联？

关联的核心是 MD5。

`file_info` 表用 MD5 作为唯一键，存文件本身的属性——`file_id` 是 FastDFS 返回的存储路径，`url` 是拼好的下载地址，`size` 和 `type` 是文件大小和类型，`count` 是引用计数，表示有多少个用户持有这个文件。

`user_file_list` 表存的是"哪个用户拥有哪个文件"，通过 `user` 和 `md5` 关联到 `user_info` 和 `file_info`。同一个 MD5 可以被多个用户持有，每一对组合在 `user_file_list` 里是一条记录，同时 `file_info.count` 加一。这就是引用计数的实现方式：文件正文只存一份，多个用户共享。

`user_file_count` 存每个用户持有的文件总数，是一个冗余字段，用来避免每次都做 `COUNT(*)`。

`share_file_list` 存分享记录，通过 `user` 和 `md5` 关联。用户在 `user_file_list` 里的 `shared_status` 字段标记是否已分享。

这里有两个我复核时发现的问题，可以主动说。

一是 **`user_file_list` 表没有针对 `(user, md5, file_name)` 的唯一约束**，而代码是靠"先查一次、没有才插入"来防止重复的。这个做法在并发下会失效：两个请求同时查、都查不到、都插入，就会产生重复记录。

二是 **`user_file_count` 这类冗余计数字段长期一定会漂移**，无论多小心。所以正确的心态不是保证它绝对准确，而是定期用 `COUNT(*)` 校正一次。

需要说明的是，`file_info` 的 MD5 唯一约束是**做对了的一处**，它挡住了最严重的一种脏数据：同一个 MD5 出现两条 `file_id` 互相矛盾的记录。

### 43. 项目里有没有 MySQL 查询优化的地方？

说实话，当前项目的表都很小，没有到需要优化的数据量，所以我没有做过真实的优化。但我能指出几个明显的地方。

第一，`file_info.md5` 有唯一索引，`user_file_count.user` 有唯一索引，`user_info.user_name` 也有，这几个是查询里最常用的，建得对。

第二，`user_file_list` 表上没有任何索引，而它是查询最频繁的表——文件列表接口按 `user` 过滤它，删除、分享、转存都要按 `(user, md5, file_name)` 查它。数据量上来之后这里会是第一个瓶颈，应该加联合索引。

第三是 `share_picture_list` 表的 `urlmd5` 字段没有索引，而浏览接口是按它查询的，数据量大了会全表扫描。

第四，分页查询用的是 `limit %d, %d` 加 `sprintf` 拼接，深分页时性能会退化，而且这个写法本身有注入风险。

## 六、分享、转存与下载

### 44. 分享功能是怎么实现的？

分享是在文件级别做的，用户对已持有的文件调用分享接口。

服务端先在同一条链路里更新三处状态：把 `user_file_list` 里这条记录的 `shared_status` 改成 1，往 `share_file_list` 表插一条分享记录，然后更新 Redis 里的共享文件列表和排行榜。其中 Redis 的部分包括一个有序集合用来排序，以及一个 Hash 用来存文件名的映射。

取消分享是反向操作，会把这些状态清理掉。删除文件的时候，如果这个文件处于已分享状态，也会一并清理分享记录。

**分享的权限判断这里有一个缺口，我要如实说。** 分享接口本身没有验证"这个文件是否属于当前请求的用户"。理论上可以为别人的文件建立一条属于自己的分享记录，并把公共分享计数加一。这个问题和第九节的越权删除是同一类原因——**很多操作只依赖请求里带的参数，没有真正校验归属关系**。

### 45. 共享排行榜用什么结构？member 和 score 是什么？

用的是 Redis 的有序集合（ZSet），键名是 `FILE_PUBLIC_ZSET`。

member 是 `md5` 和 `文件名` 直接拼接成的字符串，score 是下载量 `pv`。排序靠 ZSet 自己按 score 排，取排行榜用 `ZREVRANGE` 之类的命令按分数倒序取。

另外还有一个 Hash 叫 `FILE_NAME_HASH`，用来存 member 到文件名的映射，因为 member 是拼接出来的，单独看不知道文件名是多少。

要补充一点：member 是 `md5 + filename` **直接拼接、中间没有分隔符**的。理论上如果两个文件的 MD5 和文件名拼出来是同一个字符串，就会冲突。实际概率极低，但正确的做法是用一个不会出现在 MD5 里的分隔符，或者干脆只用 MD5。

### 46. 缓存里的数据不一致怎么办？

排行榜接口有一个**主动重建机制**。

服务端先用 `ZCARD` 取 Redis 有序集合里的成员数量，再查 MySQL 里记录的公共分享总数，然后比较这两个数。如果数量不一致，就清空 Redis 的 `FILE_PUBLIC_ZSET` 和 `FILE_NAME_HASH`，再从 `share_file_list` 表里按 pv 倒序全量读出、重新写入 Redis。

所以在这个设计里，MySQL 是持久化的事实来源，Redis 只是查询加速层，缓存坏了可以随时回源重建。

这也是判断 Redis 数据性质的一个方法：**能回源重建的是缓存，不能重建的是权威状态**。分享排行属于前者，登录 Token 和分片会话属于后者。

### 47. 分享、取消分享和转存分别修改哪些表和缓存？

| 操作 | MySQL | Redis |
| --- | --- | --- |
| 创建分享 | `user_file_list.shared_status` 置 1；插入 `share_file_list`；公共分享总数加一 | 加入 `FILE_PUBLIC_ZSET`；加入 `FILE_NAME_HASH` |
| 取消分享 | `shared_status` 置 0；删除 `share_file_list` 记录；公共分享总数减一 | 从 ZSet 和 Hash 中移除 |
| 转存 | `file_info.count` 加一；插入目标用户的 `user_file_list`；目标用户 `user_file_count` 加一 | 不涉及 |
| 删除（分享状态时） | 先清理分享记录，再删 `user_file_list`、递减 `file_info.count` | 从 ZSet 和 Hash 中移除 |

有一个区别要特别注意：**创建分享不会增加 `file_info.count`**，因为分享只是把原目录项标记为公开，物理引用没有变化。而**转存会增加**，因为目标用户新增了一条归属关系。

### 48. 转存为什么只新增关系，不重复保存正文？

因为正文以 MD5 为唯一键存在 `file_info` 里，多个用户的目录项可以共同引用它。

转存时服务端只是给目标用户新增一条 `user_file_list` 记录，把 `file_info.count` 加一，然后把目标用户的 `user_file_count` 加一。整个过程不上传、不下载、不生成新的 `file_id`。

所以多个用户保存同一个文件时，FastDFS 上实际只有一份正文。

### 49. 取消分享会影响别人已经转存的文件吗？

不会。

取消分享只做三件事：把分享者的 `shared_status` 改回 0、删除 `share_file_list` 里的记录、从 Redis 的公共列表移除。

它**不会**删除分享者自己的拥有关系，**不会**减少 `file_info.count`，也**不会**删除正文。别人在取消之前已经转存过的副本，是他们自己的 `user_file_list` 记录，引用计数也已经加过了，不受影响。

### 50. 做分享之后怎么隐藏文件的真实路径？

**当前实现没有隐藏，这一点我要承认。**

分享列表直接返回完整的下载 URL，这个 URL 是 `http://172.30.0.3:80/group1/M00/00/00/xxx` 的形式。前端的分享页面拿到这个 URL 之后直接渲染成下载链接。而 Nginx 里配了一条 `location`，凡是匹配 `group` 和 `M` 开头的路径，就直接交给 FastDFS 模块去读磁盘文件返回，**中间不经过任何鉴权**。

所以现在的实际效果是：任何人只要拿到这个 URL，就能下载文件，不需要登录，也没有次数限制。

要做到真正的隐藏和控制，常见的做法有两种。一种是**不暴露真实路径，改成一个后端接口**：分享链接指向 `/api/download?share_id=xxx` 这样的地址，由后端校验身份之后再决定是否跳转或者转发文件流。另一种是**用带签名的临时 URL**：服务端生成下载地址时附上过期时间和签名，Nginx 校验签名通过才放行。

这两种方案我都没有实现，属于知道方向但没落地的状态。

### 51. 已经分享出去的 URL，怎么控制用户能访问的次数？

**当前项目没有实现这个能力。**

因为下载走的是 FastDFS 直链，请求根本不经过应用层，服务端没有机会做计数和判断。项目里虽然有 `pv` 下载量字段，但那是通过一个单独的接口更新的，而且**正文下载和计数是两条独立的请求**——用户完全可以只下载不调计数接口，或者只调计数接口不下载。

如果要做的话，思路是把下载统一收到后端入口：分享链接指向一个带 `share_id` 的接口，服务端在数据库或 Redis 里用原子操作（比如 `DECR`）扣减剩余次数，扣减成功才返回文件流或者一个短期签名 URL。关键点是**计数和返回内容必须在同一次请求里完成**，否则还是会被绕过。

### 52. 怎么判断用户有权限下载某个文件？

**这个项目目前的判断依据是"用户有没有下载链接"，不是"用户有没有权限"。**

因为下载走的是 FastDFS 直链，请求根本不经过应用层，服务端没有机会做判断。真正做了权限判断的只有"我的文件列表"这类接口，它们是按 `user` 字段过滤 `user_file_list` 表来返回结果的。

需要澄清一个容易混淆的点：`verify_token` 这个函数本身是**正确的**。它以用户名为键从 Redis 取出 Token，和请求里带的 Token 做比对，取不到或者对不上都返回失败，不存在空 Token 绕过的情况。**问题在于它被调用的位置不够全**，有些接口根本没有调用它。

### 53. 图床分享的提取码实际生效了吗？

**没有生效。**

创建图片分享时，后端会生成一个 `urlmd5` 和一个 4 位十六进制的 `key`（提取码），存进 `share_picture_list` 表。但有两个问题：**创建接口的响应只返回 `urlmd5`，不返回 `key`**，所以用户根本拿不到提取码；而 `browse` 分支只按 `urlmd5` 查询，**完全不校验 `key`**。

所以数据库里虽然有这个字段，访问过程中从来没有强制校验过它。取消分享的分支也没有 Token 校验，而 `browse` 是公开接口且会返回 `user` 字段，所以拿到分享链接的人可以先查出分享者，再构造取消请求删掉别人的分享。

另外要说明：**当前 React 前端没有接入这套图片分享 API**，所以它不是线上活跃的功能，更像是写完了但没接完的后端模块。

## 七、并发、故障与高可用

### 54. 这个框架有没有用多线程多进程？

**业务逻辑都没有用，只有日志模块里有一处线程相关的代码。**

13 个 FastCGI 程序全部是单进程的单线程模型。每个程序的主循环就是 `while (FCGI_Accept() >= 0)`，拿到一个请求就处理完再回到循环开头。代码里没有创建过用于处理请求的线程，也没有线程池。

IO 模型是阻塞式的，13 个源文件里没有任何 `select`、`poll`、`epoll` 或者非阻塞 fd 的设置。

唯一和线程沾边的地方在公共的日志模块 `common/make_log.c`。文件里定义了一个互斥锁 `ca_log_lock`，写日志之前加锁、写完解锁。文件上半部分还有一段用 `pthread_create` 创建日志线程的代码，但**整段是注释掉的，没有编译进去**。所以现在这个锁保护的是每个进程内部对日志文件的写入，**不是业务逻辑的并发控制**。

项目里用到多进程的地方有两类。一类是执行外部命令，比如上传时调用 `fdfs_upload_file`、查询文件信息时调用 `fdfs_file_info`，用的是 `fork` 加 `execlp`，属于一次性的子进程。另一类是 13 个 CGI 本身由 `spawn-fcgi` 拉起，但每个端口只有一个实例。

所以准确的说法是：**项目运行了 13 个常驻进程，但每个进程内部是串行处理请求的，真正的并发度是 1**。

### 55. 后端的并发处理能力怎么样？

当前每个端口的并发度是 1。

13 个 FastCGI 程序是通过 `spawn-fcgi` 启动的，**没有指定 `-C` 参数**，也就是每个端口只有 1 个进程，而且这个进程是阻塞处理请求的——它先 `FCGI_Accept` 拿到一个连接，处理完之后才回去拿下一个。所以同一个接口的第二个请求必须排队等第一个处理完。

这一点要把因果讲清楚：**不是 Nginx 扛不住**，Nginx 用事件驱动模型能接住大量连接并转发；**瓶颈在后端每条路由只有一个进程在阻塞式地接活**。上传大文件分片时写 FastDFS 最耗时，这个端口的后续请求就全部在排队。排队时间超过 Nginx 的 `fastcgi_read_timeout`（分片上传那条路由设的是 300 秒）就会返回 504。

最小的改动是给 `spawn-fcgi` 加 `-C 4` 起多进程。**但这个改动会立刻引爆另外三个问题**：`uploaded` 字段的更新是"读出来、拼接、写回去"三步，多进程并发时会丢更新；同一片并发写入会因为 `O_TRUNC` 加分段 `write` 而撕裂文件；合并请求也可能并发执行。所以这几件事必须一起改。

### 56. 如果 FastDFS 的一个存储节点挂了会怎样？

这个要从项目的实际部署情况说起，**因为我在这个项目里的部署规模很小，所以能讲的是机制，不是真实故障演练的结果**。

FastDFS 里 Storage 会定期向 Tracker 上报心跳。如果一个 Storage 掉线，Tracker 在一段时间内收不到心跳，就会把它标记为不可用，之后分配上传位置时不会再选它。已经存在这个 Storage 上的文件，在它恢复之前访问不到。

同一个 group 内的 Storage 之间会互相同步文件，所以理论上同一 group 有多台 Storage 时，一台挂了文件还能从其他台读到。Tracker 也可以部署多个，客户端会轮流尝试。

但这个项目的实际部署**只有单机，Tracker 和 Storage 都只有一个实例**。所以严格讲，这个项目的部署形态**不具备高可用能力**，一旦这台机器挂掉，整个存储就不可用了。我能讲的是 FastDFS 本身提供的机制，而不是这个项目的实际保障能力。

### 57. 部署了几台服务器？用的是什么？

**单机 Docker 部署，就一台机器。**

Docker Compose 起了三个容器：MySQL 一个；Nginx、Tracker、Storage 在同一个容器里；13 个 FastCGI 程序和 Redis 在第三个容器里。Tracker 和 Storage 都是一个实例。

我用的是一台云服务器，不是虚拟机。

需要说明的是，"三个容器"不等于"三台服务器"，也不等于高可用。Nginx、Tracker、Storage 挤在同一个容器里，这个容器挂了，入口和存储就一起没了。

### 58. 健康检查能保证服务可用吗？

**不能，这一点项目里有过真实的教训。**

Compose 为三个容器都配了健康检查，但覆盖面很窄。MySQL 检查 `mysqladmin ping`；Nginx 容器只检查 443 端口是否返回 2xx；**应用容器只检查 10000 端口有没有进程在监听**。

我们遇到过一次：`chunk_merge` 进程因为启动顺序问题崩溃退出，10011 端口根本没有监听，但应用容器依然显示为 healthy，因为健康检查只盯着 10000 端口。结果就是所有分片合并请求都失败，但容器状态看起来一切正常。

所以容器显示 healthy 只说明预设的那一条检查通过了，不代表所有业务功能可用。排查时还需要用 `lsof -i` 逐个确认关键端口是否真的在监听。

### 59. 遇到过的实际部署故障有哪些？

有三个是我实际踩过并修好的。

**第一个是 CRLF 行尾导致容器反复重启。** 容器状态一直是 `Restarting (255)`，日志反复输出 `exec /app/start.sh: no such file or directory`，但文件其实在镜像里。原因是仓库里的文本文件用了 Windows 的 CRLF 行尾，`start.sh` 被 `COPY` 进镜像后首行实际是 `#!/bin/sh\r`，Linux 把解释器路径识别成了不存在的 `/bin/sh\r`。修法是把仓库里 88 个已跟踪的文本文件统一转成 LF，并加了 `.gitattributes` 用 `* text=auto eol=lf` 约束后续提交。**修改之后必须重新构建镜像**，因为带 CRLF 的旧文件已经进入镜像层了，只重启容器不会更新。

**第二个是宿主机 80 端口被系统 Nginx 占用。** 访问 `http://127.0.0.1` 时浏览器返回的是另一套 Nginx 的欢迎页，443 端口也没监听，Docker 始终无法发布端口。排查后发现宿主机上装了系统 Nginx 并占用了 80。执行 `systemctl stop nginx` 和 `systemctl disable nginx` 之后就正常了。这个事的教训是：出现"页面访问不到"或"访问到错误页面"时，要先确认宿主机端口被谁占了，可以用 `ss -tlnp` 看，不能只根据容器状态判断。

**第三个是 `chunk_merge` 启动后立即退出。** 现象是分片全部传完之后合并请求一直失败，`lsof -i:10011` 查不到任何监听，`docker logs` 只记录了 spawn 命令，日志文件里只有一行初始化信息。根因是 `start.sh` 先启动了 `chunk_merge`，之后才创建 `/fastdfs_data_and_log/client` 目录，而 FastDFS 客户端初始化要求配置里的 `base_path` 目录已经存在，目录不存在就会直接 abort。我做了可控复现来验证：先删掉目录再手动 spawn，10011 立刻起不来；重新创建目录后就恢复正常。修法是把 `mkdir -p` 移到所有 spawn 命令之前，然后重新构建镜像冷启动。

### 60. 调试程序时有没有遇到什么困难？怎么排查的？

我总结了一套方法。

首先，`docker compose ps` 显示的健康状态只能说明预设的健康检查通过了，不能证明业务功能可用。所以我们还需要用 `docker exec ... lsof -i` 逐个确认关键端口是否真的在监听。

其次，如果 FastCGI 这类常驻进程几乎没有产生日志，说明它可能压根没成功启动。这时候可以手动执行 `spawn-fcgi`，或者以前台方式直接运行目标程序，观察它卡在哪一步。

第三，当怀疑是环境或启动条件的问题时，做一个**可控复现**来缩小范围。比如刚才说的 `chunk_merge`，我先删掉它依赖的目录、重新 spawn，确认崩溃能稳定复现；再恢复目录、重新启动，观察进程是否恢复正常。这种对照能形成清晰的证据，比单纯猜代码原因可靠得多。

### 61. 如果让你设计高可用，你会怎么改？

我要先说清楚：**当前部署是单点的，这个方案我没有实现过，只是设计思路。**

按层级看。接入层可以在前面加一个负载均衡，跑多个 Nginx 实例。业务层把每个 FastCGI 程序起多个实例、监听不同端口，用 Nginx 的 `upstream` 做分发——但这一步的前提是先修掉 `uploaded` 的竞态和分片写入的原子性问题，否则并发一上来数据就错了。数据层 MySQL 做主从加故障转移；Redis 做哨兵或者集群模式，而且必须挂持久卷，否则会话还是会丢。存储层把 Tracker 部署成多个对等节点，Storage 按 group 划分，同一个 group 里放多台做副本。

还有一点容易被忽略：**分片临时目录和 Redis 都必须持久化**，否则即使前面都做了高可用，一次容器漂移就会让所有正在上传的大文件作废。

## 八、AI 功能（本轮不进主口径）

### 62. 项目里的 AI 功能是怎么做的？

这个模块属于项目的后续迭代，**我目前没有把它放进项目介绍和亮点里**，因为它和前面的传统云存储链路是两套东西。

简单说，它做的是"文件描述与语义检索"，不是完整的 RAG。`/api/ai` 支持 `describe`、`search` 和 `rebuild` 三类操作：图片调用 `qwen-vl-plus` 生成描述，DOCX 通过 `unzip` 抽取 XML，一些文本和代码格式读取前部内容；然后把这些文本用 `text-embedding-v3` 转成 1024 维向量，归一化后存进按用户划分的 FAISS `IndexFlatIP` 索引，默认取 Top 10、阈值 0.45。

它没有文档分块、混合检索、重排，也不生成带引用的答案，所以准确说是语义检索而不是 RAG。

如果面试官问为什么不做这个方向，我会说这是我有意识地把本轮复习范围收窄到传统业务链路上，AI 部分我了解实现方式，但暂不作为项目成果来讲。

## 九、我发现的缺陷（主动坦白区）

这一节的内容不适合等面试官挖出来再答，**主动说反而更好**，因为它证明我看得懂自己的代码。但也不要一次全倒出来，按对方问到的方向挑一两个讲。

### 缺陷 1 合并失败会让用户永久卡死

**现象**：大文件合并失败之后，用户重新上传会一直失败，直到 Redis 里的会话超过 24 小时过期，才能重新开始。

**原因**：合并函数是一边追加、一边删本地分片的。每成功追加一片就 `unlink` 掉那一片，但 Redis 里的 `uploaded` 字段**从头到尾没有被更新过**。所以失败之后的状态是：本地缺了几片，Redis 里却记着所有分片都传完了。

用户重试时，`chunk_init` 返回"全部已上传"，前端跳过所有分片直接调合并，而合并的第一步就是检查分片是否齐全——第 0 片已经被删掉了，检查必然失败。**这是一个自锁的状态，用户自己出不来。**

**另一个后果**是 FastDFS 上会残留一个不完整的 appender 文件。代码里在失败分支只做了 `break`，既没有回滚已经删掉的分片，也没有删除这个半成品文件。而且 `chunk_merge` 里根本没有调用过 `fdfs_delete_file`，所以这个半成品永远不会被回收。

**改进方向**：把删除分片的动作推迟到 MySQL 写入成功之后统一清理，这样中途失败时原始分片还在，用户可以直接重试。同时在失败时调用删除接口回收 FastDFS 上的半成品。

### 缺陷 2 已上传分片编号有大约 2.83GB 的上限

Redis 里的 `uploaded` 字段是一个逗号拼接的字符串，比如 `"0,1,2,3"`。接收它的缓冲区是 1024 字节的栈数组，而拼接用的是 `sprintf`，**没有做长度检查**。

我算过这个上限：索引 0 到 282 一共 283 个编号，字符串长度是 1021 字节，刚好放得下；到第 284 个分片，需要 1026 字节，就会越界。按每片 10MB 算，**283 片大约是 2.83GB**。

这里要注意的是，越界之后的失败形态**不是返回错误，而是进程崩溃**，因为写越界的是栈上的局部数组。

更好的做法是换一种数据结构。分片编号本身是一个稠密的整数集合，用 Redis 的 Bitmap 来存很合适：上传完一片就 `SETBIT` 一下，查询用 `GETBIT`。这样既没有长度上限，又天然支持重复上传（同一个位置重复置位没有副作用），还顺带解决了当前"同一片传两次会在字符串里重复累积"的问题。

### 缺陷 3 秒传接口的授权模型有问题

秒传接口在查到 MD5 存在、且当前用户还没有这个文件时，会**直接建立归属关系并把引用计数加一**。整个过程**不要求请求方真的持有文件内容**。

这意味着任何登录用户只要知道一个 MD5，就能把一个不属于自己的文件挂到自己名下，之后可以正常下载和分享。而 MD5 并不是秘密，任何下载过这个文件的人都能本地算出来。

**这个问题的本质是授权模型，不是加密强度。** 所以"后端重算 MD5"或者"换更强的哈希算法"都不是有效的修复方向——攻击者根本没有上传内容，重算什么；而指纹必须能从文件内容确定性地导出，换任何算法都一样。

有效的方向是**要求上传方证明自己真的持有文件**。比如服务端下发一段随机字节区间（例如第 3MB 到 3.1MB 的哈希），客户端必须答对才允许建立引用关系。这才是"秒传"和"越权领取"之间的分界线。

### 缺陷 4 删除操作可以越权递减引用计数

这个是我复核代码时逐行看出来的，因果链比较完整，适合展开讲。

删除文件的逻辑是这样的：先判断这个文件有没有被分享，如果被分享就先清理分享记录；然后删除 `user_file_list` 里的归属记录，递减用户文件数；接着**无条件**把 `file_info` 的引用计数减一；如果减到 0，就调用 FastDFS 的删除接口把物理文件删掉。

问题出在两个地方。

第一，**权限判断不检查文件归属**。它只检查调用者自己在 `user_file_count` 表里有没有记录，有就继续往下走，完全不管这个文件是不是他的。

第二，**删除 `user_file_list` 之后没有检查实际影响行数**。如果这个用户根本不拥有这个文件，删除语句影响 0 行，但代码不会察觉，照样把引用计数减一。

**把这两点连起来**：任意一个登录用户，从分享列表里拿到一个 MD5 和文件名，反复调用删除接口，就能把别人文件的引用计数一路减到 0，触发物理删除，导致这个文件在全站都下不了。

有一个细节可以侧面说明这是**疏漏而不是不懂**：同一个函数在处理 AI 记录的那段，**检查了** `mysql_affected_rows`。说明写代码的人知道这个 API，只是在删除归属记录那一步漏掉了。

**要补充一句**：这一条是我读代码分析出来的，**还没有在容器里实际构造请求验证过**。如果对方追问，我会如实说明这是代码分析的结论。

### 缺陷 5 分片上传接口可以匿名写任意路径

这条是两条独立发现组合起来的结果。

第一，`/api/chunk_upload` **没有 Token 校验**，任何人都能调用。

第二，这个接口从 URL 参数里取 `md5`，**不校验它是不是一个合法的 32 位十六进制字符串**，就直接拼进了文件路径：

```c
sprintf(chunk_path, "%s/%s/%d", CHUNK_TEMP_DIR, file_md5, chunk_index);
```

而解析 URL 参数的 `query_parse_key_value` 函数也**不对取值长度做任何检查**。

组合起来，构造 `?md5=../../../../etc&index=1` 这样的请求，就能把文件写到 `/tmp/chunks` 目录之外的任意路径，而且不需要登录。**这是这个项目最直接的一个可利用点。**

修法是两层的：接口加鉴权，同时校验 `md5` 必须是 32 位十六进制。

### 缺陷 6 定长栈数组配无界函数（系统性问题）

前面几个缺陷看起来是不同的问题，但我复核完之后发现它们**不是各自独立的，而是同一个习惯在不同地方重复出现**。

核心模式是"**定长栈数组配无界函数**"，具体有三种表现：

第一种是读取请求体。五个 CGI 用的是 `char buf[4*1024]` 配 `fread(buf, 1, len, stdin)`，其中 `len` 直接来自 `CONTENT_LENGTH` 环境变量，没有任何上限校验。**而 Nginx 挡不住这个**——`client_max_body_size` 设的是 12MB，远大于 4KB，所以发一个 5KB 的请求体就能打崩 CGI。

第二种是解析 JSON。多个模块用 `strcpy` 把 cJSON 的 `valuestring` 直接拷进定长数组，比如 `char user[128]`、`char md5[256]`。这里既没有检查长度，也没有检查 `valuestring` 是否为 NULL——**传 `{"user":123}` 这样一个数字而不是字符串，`strcpy(NULL)` 直接崩溃**，比传超长字符串更容易触发。

第三种是拼接字符串，就是缺陷 2 里的 `sprintf`。

所以如果面试官问"你的代码有什么问题"，我会说：**这个项目缺少一个统一的输入校验层。** 这三类问题里有相当一部分，是可以通过在入口处统一做长度校验、类型校验和身份推导来消除的。这比逐条报 bug 更能说明我看懂了问题的本质。

### 这些缺陷的共同点

除了上面说的输入校验，还有两个模式：

**调用了就当作成功了。** `sprintf` 的返回值不看，`mysql_query` 之后不看 `affected_rows`（少数例外），`malloc` 之后不判 NULL。

**身份来自请求参数，而不是来自登录态。** 上传接口的 `user` 字段直接取自表单，删除接口的归属判断只看请求里的参数。**这类问题的危险之处在于，攻击面从"已登录用户"扩大到了"任何人"。**

## 最后：这份文档该怎么用

面试时不要按顺序背。**按对方问到的方向，挑对应的那一节讲。**

回答的结构统一是：先给结论，再讲实现过程，最后说边界。如果这个问题涉及我发现的缺陷，讲完正常流程之后主动补一句"不过这里有一个我知道的问题"，然后**停下来等对方接**。

不要一口气把缺陷全讲完。讲一个、停住，对方如果继续追问，说明这个方向他感兴趣，再往下展开；如果他换话题，说明这个点已经够了。

**主动说出来的是加分，被挖出来的是减分。** 这两者的技术内容完全一样，区别只在于谁先开口。
