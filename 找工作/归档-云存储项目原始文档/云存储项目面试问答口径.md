## 使用说明

这份文档把面经里反复出现的提问归并成主题，每个主题给出一个可以直接开口讲的版本。

三点约定：

1. **可以答的**：代码里确实存在、我能说出实现细节的内容。
2. **要降级的**：简历写了但仓库里没有对应实现的内容，统一收在第七节，面试时主动说清楚。
3. **要坦白的**：我在复核中发现的缺陷，收在第六节。这些不是丢分项，主动说出来反而是加分项。

回答的顺序统一为：**先给结论，再讲实现过程，最后说边界或影响**。不要一上来就讲细节。

## 第一部分 项目整体

### Q1 介绍一下这个项目的架构，把一次上传请求的完整链路串起来

这个项目是一个基于 FastDFS 的云存储系统，前端是 React，后端是 13 个 FastCGI 程序，中间用 Nginx 做入口和路由转发。

我第一次讲的时候喜欢直接报组件名，后来发现应该按请求真实走过的顺序讲。以一次普通文件上传为例：

浏览器先把文件读进内存，同时计算整个文件的 MD5，然后把文件正文和用户信息打包成 `multipart/form-data` 发出去。请求到达 Nginx 之后，Nginx 根据 URL 匹配到 `location /api/upload`，通过 `fastcgi_pass` 转发给 10002 端口上的上传模块。

上传模块先解析 multipart 正文，把文件正文落到本地临时目录，然后调用 FastDFS 客户端把文件上传到 Storage 服务器，拿到一个 `file_id`。接着它把这个 `file_id` 拼成完整的 HTTP 下载地址，连同文件大小、类型、MD5 一起写进 MySQL 的 `file_info` 表，再往 `user_file_list` 表插一条归属记录，最后把用户的持有文件数加一。全部完成之后，模块把结果返回给 Nginx，Nginx 再返回给浏览器。

整个链路里，Nginx 负责路由和静态资源，FastCGI 负责业务逻辑，FastDFS 负责文件正文的存取，MySQL 存元数据，Redis 存登录态和分片会话。

需要说明的是，这个项目没有做服务分层，13 个 CGI 是并列的，每个对应一组接口。

### Q2 Nginx 在这个项目里起什么作用？为什么不直接让前端访问 FastCGI

Nginx 在这个项目里承担四件事。

第一是统一入口。前端的请求全部发到 443 端口，由 Nginx 根据路径分发到不同的 FastCGI 端口，前端不需要知道后端有几个模块、分别在哪。

第二是承载 HTTPS。TLS 握手和加解密由 Nginx 完成，后端 CGI 只需要处理明文 HTTP，这部分逻辑不用自己写。

第三是直接提供静态文件下载。FastDFS 提供了 `ngx_fastdfs_module`，Nginx 加载这个模块之后，可以直接从本地磁盘读 Storage 的文件并返回，请求不会进入 FastCGI。

第四是缓存控制和跨域头。项目里禁用静态资源的浏览器缓存、给每个接口加 CORS 头，都是在 Nginx 层配置的。

至于为什么不直接暴露 FastCGI：FastCGI 走的是自己的二进制协议，浏览器不认识；而且 FastCGI 进程本身不具备 HTTPS、静态文件服务、连接管理这些能力。所以中间这一层是必要的。

这里要补充一个我这边的理解边界：Nginx 能接住大量并发连接，但这不代表整个系统的并发能力高。后端每个端口只有一个进程，后面 Q17 会具体讲。

### Q3 为什么选择 FastDFS，有没有调研过替代方案

选 FastDFS 主要是三个原因。

第一是它自带 Tracker 和 Storage 的角色划分，扩容的时候只需要新增 Storage 并注册到 Tracker，不用改业务代码。

第二是它提供 Nginx 模块，下载可以直接由 Nginx 读本地磁盘返回，路径短，不用经过应用层。

第三是它部署简单，单机就能跑起来，适合当时的学习环境。

调研这块我要如实说明：**我当时只做到了能把它跑起来并接入业务，没有做过横向对比测试**。我了解过 MinIO 和 Ceph 的存在，知道 MinIO 兼容 S3 接口、Ceph 有统一的 RADOS 对象层，但我没有实际部署过，也说不出它们在具体指标上的差异。所以如果问"为什么不用 MinIO"，我只能说当时的选型依据是 FastDFS 的 Nginx 模块和部署成本，不是对比测试的结果。

## 第二部分 文件上传

### Q4 普通上传和秒传有什么区别

普通上传是真的把文件正文传给服务端。秒传不传正文，只传一个 MD5，服务端查到这个 MD5 已经存在，就直接给当前用户建立一条归属记录。

前置动作是一样的：两者都需要客户端先算出整个文件的 MD5。

差别在于后续。普通上传要把正文落到临时文件、上传到 FastDFS、再写库；秒传只需要查一次 `file_info` 表，然后往 `user_file_list` 插一条记录、把引用计数加一。所以秒传对同一个文件来说几乎是瞬时的。

这里有一个我后来才意识到的边界：**秒传接口只凭 MD5 就授予访问权，不要求请求方真的持有文件内容**。MD5 不是秘密，任何下载过这个文件的人都能本地算出来。所以严格讲，这个接口把"文件是否存在"和"是否授予访问权"两件事缝在了一起。这个问题的详细分析我放在第六节，因为它是这个项目最典型的一个设计缺陷。

### Q5 大文件分片上传的完整流程是怎样的

前端在文件超过 10MB 时走分片上传，分三步。

**第一步是初始化。** 前端算出整个文件的 MD5，连同文件名、大小、分片总数发给 `/api/chunk_init`。服务端在 Redis 里建一个 Hash，键名是 `chunk:{md5}`，字段包括文件名、大小、分片总数、用户名和已上传编号，然后设置 24 小时的过期时间，同时在磁盘上创建分片临时目录 `/tmp/chunks/{md5}/`。

**第二步是逐片上传。** 前端按 10MB 切片，对每一片调用 `/api/chunk_upload?md5=xxx&index=N`，正文以二进制形式放在请求体里。服务端先把这一片写到 `/tmp/chunks/{md5}/{N}`，写成功之后，再把编号追加到 Redis 里那个 `uploaded` 字段。

注意这里的顺序：**先落盘，再更新索引**。如果反过来，就会出现"索引说有、磁盘上没有"的记录。

**第三步是合并。** 前端全部传完之后调用 `/api/chunk_merge`。服务端先逐个检查每一片对应的临时文件是否存在，确认齐全以后，用 FastDFS 的 appender 接口把第一片作为基础文件上传，后面每一片依次追加进去，每追加成功一片就删掉本地的那一片。合并完成之后把文件信息写进 MySQL，最后清理 Redis 里的会话键。

面试里容易被追问的一点是内存占用：**合并过程没有把整个文件读进内存**。它走的是 FastDFS 基于文件路径的接口，每次只传一个分片的路径，所以合并 10GB 的文件也不会因为内存不够而失败。这一点和"把分片读进内存再拼"的做法有本质区别。

### Q6 断点续传是怎么实现的

前端每次上传之前都会先调用 `chunk_init`。服务端发现 Redis 里已经有 `chunk:{md5}` 这个键，就把里面记录的已上传编号返回给前端，前端把它们解析成一个集合，循环时跳过这些编号，只补传缺失的分片。

进度条也从已上传数量开始算，所以续传时不会从零开始。

能这样做的前提是**分片编号可以复现**。因为 MD5 算的是整个文件，同一个文件的 MD5 恒定，前端切片的边界也就固定，第 3 片永远是同一段内容。

这里有一个我复核时发现的边界，需要如实说明：**已上传的编号和磁盘上的文件之间没有一致性校验**。Redis 里记的是"这一片曾经写成功过"，但没有任何机制保证文件现在还在。合并阶段每追加成功一片就把它删掉，而 Redis 里的编号不会同步更新。所以一旦合并中途失败，前端会认为所有分片都传完了，重试时直接卡在完整性检查上。这个问题的完整因果链在第六节。

另外，`chunk_init` 在键已存在时**只判断键是否存在，不会比对这次的片数和文件大小是否和上次一致**。也就是说换了一个同名但大小不同的文件，服务端会直接续传，不会重新开始。

### Q7 大文件上传如何保证顺序性和完整性

这两件事要分开说，因为它们保障的手段完全不同。

**顺序性其实不需要保证。** 每个分片写的是独立的文件路径，第 0 片写 `/tmp/chunks/{md5}/0`，第 1 片写 `/tmp/chunks/{md5}/1`，互相不覆盖，谁先落盘都不影响结果。合并的时候按编号顺序读取即可，磁盘上的顺序不等于写入的顺序。

**完整性才是真正要保证的。** 当前做法是在合并之前逐个检查每一片的临时文件是否存在，缺任何一片就返回失败，让前端补传。

不过这里有一个当前实现的边界：**这个检查只验证文件存在，不校验每个分片的大小和内容**。所以如果某个分片因为网络原因被截断了，`stat` 能查到文件在，检查就会通过。合并出来的文件是损坏的，但系统发现不了。

当前前端是逐个 `await` 顺序上传的，所以这种截断分片不太容易出现。但如果改成并发上传，没有分片级别的校验就会变成实际问题。

### Q8 秒传的 MD5 是对整个文件算的吗？10GB 的文件也要全算一遍吗

是对整个文件算的，**确实是全量计算**。

前端用的是增量式的方式：把文件按块读出来，每一块送进 MD5 上下文更新，最后取出结果。所以不需要一次性把 10GB 读进内存，但**需要把 10GB 完整读一遍**。

这意味着两个后果。第一，大文件的秒传判断并不快，前端要花时间读完整个文件，这段时间用户是能感知到的。第二，这个计算发生在上传之前，是纯客户端的开销。

放在服务端算是不行的：那就意味着文件已经传完了，秒传也就失去意义了。所以**放在前端算的本质原因是省带宽**，代价是客户端要花时间。

如果问"能不能不全量算"，常见的思路是取文件头尾各一段加上文件大小做指纹，但那样会牺牲碰撞概率，属于用正确性换速度，这个项目没有采用。

### Q9 两个不同的文件 MD5 碰撞了怎么办

先说结论：**这个项目没有做防碰撞处理，因为在实际场景下 MD5 碰撞不需要考虑。**

需要区分两种完全不同的东西。

第一种是**数学意义上的碰撞**，也就是刻意构造两个内容不同但 MD5 相同的文件。这需要大量算力，公开的碰撞攻击针对的是 MD5 的特定构造方法，而且生成出来的两个文件都是有特定格式的垃圾数据，不是用户正常上传的文件。

第二种是**攻击者直接编造一个 MD5 字符串**去调秒传接口。这个成本是零，写个循环就能刷。

这个项目真正需要防的是第二种，不是第一种。而它现在的实现恰好防不住第二种，因为它只检查 MD5 是否存在，不验证请求方是否真的持有文件内容。所以问题不在"MD5 算法够不够强"，而在**授权模型**。

后面这个问题在第六节会展开。

### Q10 上传过程中同时和 MySQL、Redis、FastDFS 打交道，怎么保证要么全成功要么全失败

**当前实现没有做到这一点，我要如实讲。**

上传流程里确实要依次操作多个组件：FastDFS 存正文，MySQL 写文件记录和归属记录，Redis 存登录态和分片会话。这些操作是分步执行的，**没有用事务包起来，也没有补偿机制**。

具体来说，普通上传的写入分成三步：先往 `file_info` 表插文件记录，再往 `user_file_list` 插归属记录，最后更新 `user_file_count` 的文件数。三步各自独立执行，任何一步失败，前面已经执行的部分不会回滚。

分片上传的落库分支也是同样的结构。

我能说出这个问题的严重程度：如果是 `file_info` 写成功、`user_file_list` 写失败，那么用户会看到上传失败，但文件记录已经存在、引用计数是旧的。下一次别的用户上传同一个 MD5 触发秒传，就会命中这条记录，从而"拥有"一个其实从来没有上传成功过的文件，下载时直接 404。

如果要修，方向是把这几步写进一个 MySQL 事务，让它们要么全部提交、要么全部回滚。**这是我知道但还没有落地的改进方向**，不是当前已经具备的能力。

## 第三部分 数据存储

### Q11 MySQL 和 Redis 分别存了什么

按用途分两类来看比较清楚。

**MySQL 是权威存储**，存的是长期数据：`user_info` 存用户账号，`file_info` 存文件的 MD5、`file_id`、下载地址、大小、类型和引用计数，`user_file_list` 存用户和文件的归属关系，`user_file_count` 存每个用户持有的文件数，`share_file_list` 和 `share_picture_list` 存分享记录。这些数据即使 Redis 整个清空也能从 MySQL 恢复。

**Redis 存的是两类东西，性质不一样。**

一类是**缓存的加速副本**。共享文件排行榜就属于这一类，它存在有序集合里，是 `share_file_list` 表的一个投影。Redis 里没有这个键不代表文件没被分享，只代表缓存没命中，回查 MySQL 就能补上。

另一类是**Redis 自己是权威的中间状态**，这类数据在 MySQL 里没有对应记录。登录 Token 和分片上传会话都属于这一类。分片会话存的是文件名、大小、分片数、用户和已上传编号，这些信息 MySQL 里没有；临时分片正文存在 `/tmp/chunks` 下面，MySQL 里也没有。**所以 Redis 一旦丢失，服务端就不知道这个文件传了多少片、还差哪几片，没有任何地方可以回查。**

区分这两类的意义在于判断故障后果：缓存丢了回源重建就行，中间状态丢了只能靠重传或者超时清理兜底。

### Q12 Redis 比 MySQL 快，原因是什么

主要有三点。

第一是**数据位置不同**。Redis 的数据全部放在内存里，MySQL 的数据最终落在磁盘上，即使有缓冲池，也会遇到需要真正读盘的情况。

第二是**数据结构和访问路径不同**。Redis 的读写是针对具体数据结构的直接操作，比如往有序集合里加一个成员；MySQL 要先解析 SQL 语句、再经过查询优化器生成执行计划、最后走 B+ 树索引查找。这中间的每一步都是开销。

第三是**协议和连接模型不同**。Redis 用的是简单的文本协议，而且是单线程处理命令，没有锁竞争；MySQL 有连接管理、事务、MVCC 这些机制要维护。

不过要补一句：这个项目用 Redis 的主要理由**不是因为它快**，而是因为有些数据本来就该放在内存里、并且需要过期时间。登录 Token 和分片会话都是临时状态，设 24 小时过期自动清理，用 MySQL 反而要自己做清理任务。

### Q13 数据库表是怎么设计的，几张表之间怎么关联

关联的核心是 MD5。

`file_info` 表用 MD5 作为唯一键，存文件本身的属性——`file_id` 是 FastDFS 返回的存储路径，`url` 是拼好的下载地址，`size` 和 `type` 是文件大小和类型，`count` 是引用计数，表示有多少个用户持有这个文件。

`user_file_list` 表存的是"哪个用户拥有哪个文件"，通过 `user` 和 `md5` 两个字段关联到 `user_info` 和 `file_info`。同一个 MD5 可以被多个用户持有，每一对组合在 `user_file_list` 里是一条记录，同时 `file_info.count` 加一。这就是引用计数的实现方式：文件正文只存一份，多个用户共享。

`user_file_count` 存每个用户持有的文件总数，是一个冗余字段，用来避免每次都要对 `user_file_list` 做 `COUNT(*)`。

`share_file_list` 存分享记录，表和用户列表之间通过 `user` 和 `md5` 关联。用户在 `user_file_list` 里的 `shared_status` 字段标记是否已分享。

这里有两个我复核时发现的问题，可以主动说。

一是**`user_file_list` 表没有针对 `(user, md5, file_name)` 的唯一约束**，而代码是靠"先查一次、没有才插入"来防止重复的。这个做法在并发下会失效：两个请求同时查、都查不到、都插入，就会产生重复记录。

二是 **`user_file_count` 这类冗余计数字段长期一定会漂移**，无论多小心。所以正确的心态不是保证它绝对准确，而是定期用 `COUNT(*)` 校正一次。

需要说明的是，`file_info` 的 MD5 唯一约束是**做对了的一处**，它挡住了最严重的一种脏数据：同一个 MD5 出现两条 `file_id` 互相矛盾的记录。

## 第四部分 分享与权限

### Q14 分享功能是怎么实现的

分享是在文件级别做的，用户对已持有的文件调用分享接口。

服务端先在同一条链路里更新三处状态：把 `user_file_list` 里这条记录的 `shared_status` 改成 1，往 `share_file_list` 表插一条分享记录，然后更新 Redis 里的共享文件列表和排行榜。其中 Redis 的部分包括一个有序集合用来排序，以及一个 Hash 用来存文件名的映射。

取消分享是反向操作，会把这些状态清理掉。删除文件的时候，如果这个文件处于已分享状态，也会一并清理分享记录。

**分享的权限判断这里有一个缺口，我要如实说。** 分享接口本身没有验证"这个文件是否属于当前请求的用户"。理论上可以为别人的文件建立一条属于自己的分享记录，并把公共分享计数加一。这个问题和第六节的越权删除是同一类原因——**很多操作只依赖请求里带的参数，没有真正校验归属关系**。

### Q15 分享之后怎么隐藏文件的真实路径

**当前实现没有隐藏，这一点我要承认。**

分享列表直接返回完整的下载 URL，这个 URL 是 `http://存储地址/group1/M00/00/00/xxx` 的形式。前端的分享页面拿到这个 URL 之后直接渲染成下载链接。而 Nginx 里配置了一条 `location`，凡是匹配 `group` 和 `M` 开头的路径，就直接交给 FastDFS 模块去读磁盘文件返回，**中间不经过任何鉴权**。

所以现在的实际效果是：任何人只要拿到这个 URL，就能下载文件，不需要登录，也没有次数限制。

要做到真正的隐藏和控制，常见的做法有两种。一种是**不暴露真实路径，改成一个后端接口**：分享链接指向 `/api/download?share_id=xxx` 这样的地址，由后端校验身份之后再决定是否跳转或者转发文件流。另一种是**用带签名的临时 URL**：服务端生成下载地址时附上过期时间和签名，Nginx 校验签名通过才放行。

这两种方案我都没有实现，属于知道方向但没落地的状态。

### Q16 怎么判断用户有没有权限下载某个文件

**这个项目目前的判断依据是"用户有没有下载链接"，不是"用户有没有权限"。**

因为下载走的是 FastDFS 直链，请求根本不经过应用层，服务端没有机会做判断。真正做了权限判断的只有"我的文件列表"这类接口，它们是按 `user` 字段过滤 `user_file_list` 表来返回结果的。

需要澄清一个容易混淆的点：`verify_token` 这个函数本身是**正确的**。它以用户名为键从 Redis 取出 Token，和请求里带的 Token 做比对，取不到或者对不上都返回失败，不存在空 Token 绕过的情况。**问题在于它被调用的位置不够全**，有些接口根本没有调用它。这个问题我在第六节细说。

## 第五部分 并发与故障

### Q17 两个用户同时上传同一个文件，会有并发问题吗

会有，需要分几种情况说。

**如果两个用户同时上传的是同一个文件、走的是普通上传**，那么两边都会完整地走一遍流程：各自上传一份正文到 FastDFS，各自尝试往 `file_info` 插记录。因为 `file_info` 的 MD5 字段有唯一约束，第二个插入会失败。但当前代码**没有处理这个失败的情况**，也没有做"竞争失败就复用已有记录"的逻辑。所以两个并发的相同文件上传，会有一个报错，而且 FastDFS 上可能留下没人引用的孤儿文件。

**如果是同一个用户的同一个文件重复上传**，情况类似，`user_file_list` 因为没有唯一约束，可能会产生重复记录。

**如果问的是后端的并发处理能力**，那答案是当前并发度是 1。13 个 FastCGI 程序是通过 `spawn-fcgi` 启动的，**没有指定 `-C` 参数**，也就是每个端口只有 1 个进程，而且这个进程是阻塞处理请求的——它先 `FCGI_Accept` 拿到一个连接，处理完之后才回去拿下一个。所以同一个接口的第二个请求必须排队等第一个处理完。

这一点要讲清楚因果：**不是 Nginx 扛不住，Nginx 用 epoll 能接住大量连接并转发；瓶颈在后端每条路由只有一个进程在阻塞式地接活**。上传大文件分片时写 FastDFS 最耗时，这个端口的后续请求就全部在排队。排队时间超过 Nginx 的 `fastcgi_read_timeout` 就会返回 504。

最小的改动是给 `spawn-fcgi` 加 `-C 4` 起多进程。**但这个改动会立刻引爆另一个问题**：Redis 里 `uploaded` 字段的更新是"读出来、拼接、写回去"三步，多进程并发时会丢更新。所以这两件事必须一起改。

### Q18 上传过程中网络中断了怎么办

要按文件大小分两种情况。

**如果是小文件走普通上传**，中断就意味着整个请求失败，临时文件可能残留在本地，**当前没有清理机制**，需要重新上传。

**如果是大文件走分片上传**，已经传完的分片不会丢，因为它们已经落在磁盘上、编号也已经记进 Redis。用户重新上传时，`chunk_init` 会返回已上传的编号列表，前端跳过这些编号、只补传缺失的部分。这就是断点续传的实际作用。

不过这里有一个边界要说清楚：**续传的前提是 Redis 里的会话还在**。这个键设置了 24 小时的过期时间，超过之后就会失效，服务端不再知道之前传到哪了，用户只能从头开始传。而磁盘上的分片临时文件**没有任何定时清理任务**，会一直留着占用空间。

另外，如果中断发生在前端已经收到分片上传成功的响应、但还没发出合并请求的时候，用户在过期时间之内重试是可以正常续上的。

### Q19 如果 FastDFS 的一个存储节点挂了会怎样

这个要从项目的实际部署情况说起，**因为我在这个项目里的部署规模很小，所以能讲的是机制，不是真实故障演练的结果**。

FastDFS 里 Storage 会定期向 Tracker 上报心跳。如果一个 Storage 掉线，Tracker 在一段时间内收不到心跳，就会把它标记为不可用，之后分配上传位置时不会再选它。已经存在这个 Storage 上的文件，在它恢复之前访问不到。

同一个 group 内的 Storage 之间会互相同步文件，所以理论上同一 group 有多台 Storage 时，一台挂了文件还能从其他台读到。Tracker 也可以部署多个，客户端会轮流尝试。

但这个项目的实际部署**只有单机，Tracker 和 Storage 都只有一个实例**。所以严格讲，这个项目的部署形态**不具备高可用能力**，一旦这台机器挂掉，整个存储就不可用了。我能讲的是 FastDFS 本身提供的机制，而不是这个项目的实际保障能力。

### Q20 这个项目有没有用多线程多进程

**业务逻辑都没有用，只有日志模块里有一处线程相关的代码。**

13 个 FastCGI 程序全部是单进程的单线程模型。每个程序的主循环就是 `while (FCGI_Accept() >= 0)`，拿到一个请求就处理完再回到循环开头。代码里没有创建过用于处理请求的线程，也没有线程池。

IO 模型是阻塞式的，13 个源文件里没有任何 `select`、`poll`、`epoll` 或者非阻塞 fd 的设置。

唯一和线程沾边的地方在公共的日志模块 `common/make_log.c`。文件里定义了一个互斥锁 `ca_log_lock`，写日志之前加锁、写完解锁。文件上半部分还有一段用 `pthread_create` 创建日志线程的代码，但**整段是注释掉的，没有编译进去**。所以现在这个锁保护的是每个进程内部对日志文件的写入，**不是业务逻辑的并发控制**。

项目里用到多进程的地方有两类。一类是执行外部命令，比如上传时调用 `fdfs_upload_file`、查询文件信息时调用 `fdfs_file_info`，用的是 `fork` 加 `execlp`，属于一次性的子进程，用完就退出，不是常驻的工作进程。另一类是 13 个 CGI 本身由 `spawn-fcgi` 拉起，但每个端口只有一个实例。

所以准确的说法是：**项目运行了 13 个常驻进程，但每个进程内部是串行处理请求的，真正的并发度是 1**。

## 第六部分 我发现的缺陷（主动坦白区）

这一节的内容不适合等面试官挖出来再答，**主动说反而更好**，因为它证明我看得懂自己的代码。但也不要一次全倒出来，按对方问到的方向挑一两个讲。

### 缺陷 1 合并失败会让用户永久卡死

**现象**：大文件合并失败之后，用户重新上传，会一直失败，直到 Redis 里的会话超过 24 小时过期，才能重新开始。

**原因**：合并函数是一边追加、一边删本地分片的。每成功追加一片就 `unlink` 掉那一片，但 Redis 里的 `uploaded` 字段**从头到尾没有被更新过**。所以失败之后的状态是：本地缺了几片，Redis 里却记着所有分片都传完了。

用户重试时，`chunk_init` 返回"全部已上传"，前端跳过所有分片直接调合并，而合并的第一步就是检查分片是否齐全——第 0 片已经被删掉了，检查必然失败。**这是一个自锁的状态，用户自己出不来。**

**另一个后果**是 FastDFS 上会残留一个不完整的 appender 文件。代码里在失败分支只做了 `break`，既没有回滚已经删掉的分片，也没有删除这个半成品文件。

**改进方向**：把删除分片的动作推迟到 MySQL 写入成功之后统一清理，这样中途失败时原始分片还在，用户可以直接重试。同时在失败时调用删除接口回收 FastDFS 上的半成品。

### 缺陷 2 已上传分片编号有大约 2.83GB 的上限

Redis 里的 `uploaded` 字段是一个逗号拼接的字符串，比如 `"0,1,2,3"`。接收它的缓冲区是 1024 字节的栈数组，而拼接用的是 `sprintf`，**没有做长度检查**。

我算过这个上限：索引 0 到 282 一共 283 个编号，字符串长度是 1021 字节，刚好放得下；到第 284 个分片，需要 1026 字节，就会越界。按每片 10MB 算，**283 片大约是 2.83GB**。

这里要注意的是，越界之后的失败形态**不是返回错误，而是进程崩溃**，因为写越界的是栈上的局部数组。

更好的做法是换一种数据结构。分片编号本身是一个稠密的整数集合，用 Redis 的 Bitmap 来存很合适：上传完一片就 `SETBIT` 一下，查询用 `GETBIT`。这样既没有长度上限，又天然支持重复上传（同一个位置重复置位没有副作用），还顺带解决了当前"同一片传两次会在字符串里重复累积"的问题。

### 缺陷 3 秒传接口的授权模型有问题

秒传接口在查到 MD5 存在、且当前用户还没有这个文件时，会**直接建立归属关系并把引用计数加一**。整个过程**不要求请求方真的持有文件内容**。

这意味着任何登录用户只要知道一个 MD5，就能把一个不属于自己的文件挂到自己名下，之后可以正常下载和分享。而 MD5 并不是秘密，任何下载过这个文件的人都能本地算出来。

**这个问题的本质是授权模型，不是加密强度。** 所以"后端重算 MD5"或者"换更强的哈希算法"都不是有效的修复方向——攻击者根本没有上传内容，重算什么；而指纹必须能从文件内容确定性地导出，换任何算法都一样。

有效的方向是**要求上传方证明自己真的持有文件**。比如服务端下发一段随机字节区间（例如第 3MB 到 3.1MB 的哈希），客户端必须答对才允许建立引用关系。这才是"秒传"和"越权领取"之间的分界线。

### 缺陷 4 删除操作可以越权递减引用计数

这个是我复核代码时逐行看出来的，因果链比较完整，适合展开讲。

删除文件的逻辑是这样的：先判断这个文件有没有被分享，如果被分享就先清理分享记录；然后删除 `user_file_list` 里的归属记录，递减用户文件数；接着**无条件**把 `file_info` 的引用计数减一；如果减到 0，就调用 FastDFS 的删除接口把物理文件删掉。

问题出在两个地方。

第一，**权限判断不检查文件归属**。它只检查调用者自己在 `user_file_count` 表里有没有记录，有就继续往下走，完全不管这个文件是不是他的。

第二，**删除 `user_file_list` 之后没有检查实际影响行数**。如果这个用户根本不拥有这个文件，删除语句影响 0 行，但代码不会察觉，照样把引用计数减一。

**把这两点连起来**：任意一个登录用户，从分享列表里拿到一个 MD5 和文件名，反复调用删除接口，就能把别人文件的引用计数一路减到 0，触发物理删除，导致这个文件在全站都下不了。

有一个细节可以侧面说明这是**疏漏而不是不懂**：同一个函数在处理 AI 记录的那段，**检查了** `mysql_affected_rows`。说明写代码的人知道这个 API，只是在删除归属记录那一步漏掉了。

### 这些缺陷的共同点

我在复核完之后发现，这些缺陷**不是各自独立的问题，而是同一个习惯在不同地方重复出现**。主要有三种：

1. **有缓冲区的地方就有无界的函数**。读取请求体是 `char buf[4*1024]` 配 `fread(buf, 1, len, stdin)`，`len` 直接来自 `CONTENT_LENGTH` 环境变量；解析 JSON 是用 `strcpy` 把字段拷进定长数组；拼接字符串用 `sprintf`。这三处全都没有做长度校验。

2. **调用了就当作成功了**。`sprintf` 的返回值不看，`mysql_query` 之后不看 `affected_rows`，`malloc` 之后不判 `NULL`。

3. **身份来自请求参数，而不是来自登录态**。上传接口的 `user` 字段直接取自表单，删除接口的归属判断只看请求里的参数。**这类问题的危险之处在于，攻击面从"已登录用户"扩大到了"任何人"。**

所以如果要概括一句话，我会说：**这个项目缺少一个统一的输入校验层**。这三类问题里有相当一部分，是可以通过在入口处统一做长度校验、类型校验和身份推导来消除的。

## 最后：这份文档该怎么用

面试时不要按顺序背。**按对方问到的方向，挑对应的那一节讲**。

回答的结构统一是：先给结论，再讲实现过程，最后说边界。如果这个问题涉及我发现的缺陷，讲完正常流程之后主动补一句"不过这里有一个我知道的问题"，然后**停下来等对方接**。

不要一口气把缺陷全讲完。讲一个、停住，对方如果继续追问，那说明这个方向他感兴趣，再往下展开；如果他换话题，说明这个点已经够了。

**主动说出来的是加分，被挖出来的是减分。** 这两者的技术内容完全一样，区别只在于谁先开口。
